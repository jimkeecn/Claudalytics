## Details

### 🟢 Sonnet 5.5 cache-read reprice ($0.20 → $0.10 / Mtok)

**Changelog:** *"Updated `/cost`, the status line, `--max-budget-usd` and the SDK's cost figures to price Sonnet 5.5 cache reads at $0.10 per million tokens (was $0.20)."*

**Repo reality:** The cost dashboards read `cost_usd` straight out of Claude Code's native `api_request` OTel logs — e.g. `sum(toFloat64OrZero(LogAttributes['cost_usd']))` and `cost_usd / (output_tokens/1000)` in `otel-overview.json`. A grep for per-token price constants / multiplication (`* 0.`, `/ 1000000`, `price`, `rate`) across `docker-stack/**` (excluding the dashboard JSON) returns **nothing** — the repo never computes cost from tokens × rate. So the halved cache-read price is applied entirely upstream and the pipeline keeps working without changes.

**The catch:** Any cost trend / cost-per-1k panel will show a **discontinuity on/after 2026-10-09** that reflects the price change, not a usage change. For a telemetry pipeline whose whole point is cost visibility, a maintainer should know this so a dip isn't misattributed. The clean mitigation is a dashboard annotation (or a note in the cost panel descriptions) marking the reprice date — no schema or query change needed.

### 🟢 git_commit_id now populated on quiet/`-C` commits (bug fix #38)

**Changelog:** *"Fixed OpenTelemetry `tool_result` events missing `git_commit_id` after `git commit -q` or `git -C <dir> commit`."*

**Repo reality:** The repo consumes `tool_result` events heavily (tool success rates, skill/MCP usage, agent fan-out — all filter `LogAttributes['event.name'] = 'tool_result'`), but a repo-wide grep for `git_commit_id` matches **only** this dashboard's unrelated lines, never as a queried attribute. Nothing ingests or displays `git_commit_id` today. The upstream fix means this attribute is now more reliably present — a potential future enrichment (e.g. correlate tool activity to commits), but **no current code path changes**.

> Side note: the project CLAUDE.md asks that completed JIRA cards include git commit info. That's a human/workflow convention, unrelated to the OTel `tool_result.git_commit_id` attribute — this fix does not affect it.
