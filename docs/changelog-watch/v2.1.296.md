## Details

### 🟢 `git_commit_id` on OTel `tool_result` events (Improvement)
Changelog (Bug fixes): *"OpenTelemetry `tool_result` events include `git_commit_id` after `git commit -q` or `git -C <dir> commit`."*

- This attribute lives on Claude Code's **native** OpenTelemetry `tool_result` log events (`service.name = claude-code`). Claudalytics' pipeline instead emits its own hook-derived logs (`service.name = claude-hooks`, `event.name = hooks.*`) via `otel-emitter.ts`, and every materialized view filters on `event.name = 'hooks.PostToolUse'` etc. Native `claude-code` events — even if they reach the same collector — are not matched by any MV, so there is **no break and no silent data change**.
- Opportunity: `field-mapping.ts` already special-cases Bash `PostToolUse` (it extracts `bash_urls`). A `git commit` could be detected there and its commit SHA parsed from the Bash `tool_response.stdout`, emitted as e.g. `git.commit_id`, to power a "commits per session/project" view. This is optional and additive; defer unless a dashboard needs it.
- No change to `EVENTS_TO_EMIT`, tool-name mapping, or existing attribute keys is required.

### 🟢 Read tool `allow_large` option (Info)
Changelog (Added): *"An `allow_large` option for the Read tool to read a large text file in one call."*

- Affects only the shape of Read's `tool_input`. `mapHookToAttributes` reads `tool_input.file_path` for Read and stringifies the whole `tool_input`; a new optional key is tolerated with no behavior change. The `ReadInput` interface in `hook-events.ts` (`file_path`, `offset?`, `limit?`) could gain `allow_large?: boolean` for type accuracy, but this is cosmetic.
