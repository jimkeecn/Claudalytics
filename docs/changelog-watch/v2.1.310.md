## Details

### 🟢 Monitor tool — generic capture works, two optional follow-ups
Claude Code 2.1.310 adds a new first-class `Monitor` tool. Impact on Claudalytics:

- **Ingestion: safe.** `mapHookToAttributes` (`field-mapping.ts:122-214`) writes `attrs["tool_name"]` for *every* PreToolUse/PostToolUse event regardless of tool, so `Monitor` events are emitted to `otel_logs` and fan into `blocked_tools` (`007_blocked_tools_mv.sql`) without any change. No MV filters it out, no dashboard query breaks.
- **No dedicated mapping.** Unlike `Read`/`Edit`/`Write`/`Agent`/`WebSearch`/`WebFetch`/`Bash`, there is no per-tool attribute extraction for `Monitor`, so its `tool_input` (e.g. the watched condition / until-loop) is only stored as the raw `tool_input` blob. This is expected for any untracked tool — adopt only if Monitor usage becomes worth a dashboard.
- **Blocked-tools false positives (data quality, Low).** `blocked_tools` infers "blocked" as PreToolUse-with-no-PostToolUse (`completed=0`, queried with FINAL). The Monitor tool is designed to run long / in the background with large gaps between Pre and Post; such in-flight invocations will transiently read as `completed=0` and can inflate "blocked tool" counts on any dashboard built on `blocked_tools`. No fix required unless Monitor sees heavy use; if so, consider excluding `tool_name = 'Monitor'` from blocked-tool panels or widening the "pending" grace window.

> No High or Mid severity findings this release — nothing breaks ingestion, materialized views, OTel attributes, env vars, or the health-check response schema.
