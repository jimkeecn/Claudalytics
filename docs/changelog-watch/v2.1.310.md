## Details

### 🟢 Monitor tool added (Improvement / Low) — `docker-stack/hooks-server/src/field-mapping.ts`

The changelog's first "Added" line introduces the **Monitor tool** and plugin monitors. This is a new first-class Claude Code tool, so it will appear in `tool_name` on `PreToolUse` and `PostToolUse` hook events.

Why this is **not** a break:
- `EVENTS_TO_EMIT` in `field-mapping.ts` is keyed on *event names* (`PreToolUse`, `PostToolUse`, …), not tool names. The `Monitor` tool still fires those events.
- The `PreToolUse`/`PostToolUse` cases set `attrs["tool_name"]` unconditionally for any tool, and only *add* extra attributes for a known subset (`Read`, `Edit`, `Write`, `Agent`, `WebSearch`, `WebFetch`, `Bash`). An unknown tool simply gets the generic `tool_name` + `tool_input` and is still ingested.
- `plugin/hooks/hooks.json` forwards every event via `forward-hook.sh`; there is no per-tool filter.
- The specialized materialized views that *do* filter by tool name (`005_file_mutations_mv.sql` → `Edit`/`Write`/`Bash`, `011_websites_visited_mv.sql` → `WebFetch`/`WebSearch`/`Bash`, `003_credential_exposures_mv.sql` → `Read`) correctly ignore `Monitor`, which is neither a file mutation, a web visit, nor a credential read. No MV misclassifies it.

Optional adoption (not required): if `Monitor`'s `tool_response` carries useful fields (e.g. monitor cadence, duration, or trigger metadata), a `Monitor`-specific branch could be added to the `PostToolUse` case in `field-mapping.ts`, mirroring the existing `Agent`/`WebSearch` branches, plus a dashboard panel to track monitor usage. Until Monitor's response schema is published, generic capture is sufficient and correct.
