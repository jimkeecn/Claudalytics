## Details

### 🟢 Improvement — `claude_code.safety_event` native OTel event

**What changed.** 2.1.307 adds a native OpenTelemetry event, `claude_code.safety_event`, "emitted for each tool call that a permission rule, auto mode, a safety check, a hook, or the sandbox stopped, prompted, or sent back."

**Why it matters for Claudalytics.** This is a *native Claude Code OTel event* (a log), not a Claude Code **hook** event. It therefore does **not** flow through the plugin's hook-forwarding path (`plugin/hooks/hooks.json` → `forward-hook.sh` → hooks-server), and its absence breaks nothing — the hooks-server (`docker-stack/hooks-server/src/field-mapping.ts`, service name `claude-hooks`) only maps the 26 hook events in `EVENTS_TO_EMIT` and never expected to receive it.

The opportunity: the repo **already consumes native `claude_code.*` telemetry** in the dashboard — `otel-overview.json` queries `claudalytics.otel_metrics_sum` for `claude_code.lines_of_code.count`, `claude_code.commit.count`, and `claude_code.active_time.total`. That means Claude Code's own OTel exporter is already (optionally) pointed at the same collector/ClickHouse. The new `safety_event` would arrive on that same native path as a log/event, giving a **direct, authoritative "this tool call was blocked/prompted/returned" signal**.

Today, blocked-tool detection is only *inferred* in `docker-stack/clickhouse/init/007_blocked_tools_mv.sql`: a `PreToolUse` with no matching `PostToolUse`/`PostToolUseFailure` (`completed=0` after `FINAL`). That heuristic also flags interrupted/crashed calls, not just policy blocks, and it overlaps imperfectly with the `PermissionRequest`/`PermissionDenied` hook events the repo already stores. Adopting `safety_event` could make blocked/prompted tracking precise and distinguish *why* a call was stopped (permission rule vs. sandbox vs. hook vs. safety check).

**Scope of adoption (net-new, not a fix).** Nothing is broken, so this is backlog, not urgent:
- Confirm/verify the field schema of `claude_code.safety_event` against a real emitted event before building on it (the changelog gives the trigger conditions, not the attribute keys).
- Decide whether to ingest it via the native OTel metrics/logs path (already wired for `claude_code.*` metrics) rather than the hooks path.
- Optionally add a ClickHouse view and a Grafana panel (e.g. "blocked/prompted tool calls by reason"), complementing or cross-checking `blocked_tools`.

**No change required to avoid breakage** — this entry is logged as an enhancement candidate only.
