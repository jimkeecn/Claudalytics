Lesson 03 · A3 · Module A — Hello agent

Streaming answers (SSE)

★★ Haiku

What you'll learn

When a Claudalytics Copilot user asks "What projects do I have?", the agent may run a ClickHouse query and then write a long answer. Today the user waits with a spinner for the whole turn, then sees the full text appear at once — even when the first words were ready seconds earlier. Streaming removes that wait by running the agent with RunStreamingAsync and sending each token to the client the moment the model produces it, over a Server-Sent Events (SSE) connection.

This lesson adds a /chat/stream endpoint. It maps four kinds of streaming update to four named SSE event types: session, token, tool_call, and done. You will learn why each event type exists, how to tell them apart in code, and the two mistakes that break SSE without throwing any exception. Approval handling (approval_request) is added later in C3/lesson10. A3's stream is approval-free.

📘 Teach

The streaming run and the update stream

MAF's AIAgent exposes two run methods. You already know the blocking one from A1:

  • RunAsync(message, session) — awaits the full turn, returns an AgentResponse.
  • RunStreamingAsync(message, session) — returns an IAsyncEnumerable<StreamingChatMessageUpdate>. Each item in the sequence is one partial update emitted as soon as the model produces it.

A StreamingChatMessageUpdate carries two things you care about:

  • update.Text — a non-empty string when the model emitted text tokens in this update. This is the partial word or phrase you forward immediately.
  • update.Contents — a list of typed content items. The one that matters here is FunctionCallContent (a tool the model chose to call). A second content type, ToolApprovalRequestContent, is introduced later in C3/lesson10 for tools that need human sign-off before execution; A3 does not handle it.

The SSE wire format is small. Each event is two lines followed by a blank line. 

event: token
data: {"text":"Hello, "}

event: token
data: {"text":"world!"}

event: done
data: {}

The client reads each event:/data: pair and reacts right away. It does not wait for the rest. The most important detail is the flush after every write. ASP.NET buffers the response body by default. Without an explicit FlushAsync, the "stream" becomes one slow response that arrives all at once.

The four SSE event types

The app uses exactly four event names on /chat/stream. Once you know what triggers each one, the checks inside the update loop are easy to read.

Event When Key payload field
session Once, before the stream starts — carries the session id the client should echo on follow-ups. sessionId
token For each update where update.Text is non-empty. text
tool_call For each FunctionCallContent in update.Contents. name, arguments
done Once, after the await foreach completes normally. (empty object)

An error event is emitted in the catch block instead of done when the run throws.

Build it

  1. Add the SseEvent helper

    Every SSE write does the same two things. It serializes the payload as JSON, then flushes the response body so the bytes leave the server now. The streaming loop in step 3 calls this helper many times, so put it in one place. Add it as a file-scope static class at the bottom of Program.cs, after app.Run();, next to the other file-level helpers.

    🔧 Note

    Required using (not in implicit usings): Add using System.Text.Json; at the top of Program.cs. JsonSerializer lives in this namespace and is not covered by the default ASP.NET implicit-usings set.

    Program.cs 
    internal static class SseEvent
{
    private static readonly JsonSerializerOptions JsonOptions =
        new(JsonSerializerDefaults.Web);

    public static async Task WriteAsync(
        HttpResponse response, string eventName, object data, CancellationToken ct)
    {
        await response.WriteAsync(
            $"event: {eventName}\ndata: {JsonSerializer.Serialize(data, JsonOptions)}\n\n", ct);
        await response.Body.FlushAsync(ct);
    }
}

    The double newline (\n\n) after data: is the SSE record separator. It tells the browser's EventSource that this event is complete. If you omit it, the client stalls until the connection closes. The FlushAsync pushes the bytes through ASP.NET's response buffer. Without it, tokens queue in memory and the client receives them all at once when the run finishes. That is a normal response, not a stream.

  2. Wire up the session before the stream opens

    The /chat/stream endpoint reads the request body, then resolves or creates a session with the GetOrCreateSessionAsync helper from A2. It sets the SSE response headers and sends a session event first. The client reads that sessionId and stores it. It sends the id back on the next message so the agent keeps the same multi-turn memory.

    🔧 Note

    Steps 2 and 3 are one MapPost handler split across two code snippets. Step 2 opens the lambda and step 3 finishes it. The closing }); appears at the end of step 3. Paste both snippets consecutively in Program.cs — between the other app.Map… calls (after var app = builder.Build(); and before app.Run();) — to form one complete app.MapPost("/chat/stream", …); call.

    Required usings (add at the top of Program.cs if not already present):

    • using Microsoft.Extensions.AI; — required for FunctionCallContent, the typed content item inspected inside the streaming loop. This namespace is not in the default implicit-usings set.

    Assumed prior symbols (carry forward from A1/A2): ChatRequest, AgentSession, GetOrCreateSessionAsync. All three must already exist in Program.cs from lessons A1 and A2. (PendingApproval and StoreApproval are introduced later in C3/lesson10 — they are not needed here.)

    Program.cs 
    app.MapPost("/chat/stream", async (HttpContext context, AIAgent agent,
    ConcurrentDictionary<string, AgentSession> sessions, CancellationToken ct) =>
{
    var request = await context.Request.ReadFromJsonAsync<ChatRequest>(ct);
    if (request is null || string.IsNullOrWhiteSpace(request.Message))
    {
        context.Response.StatusCode = StatusCodes.Status400BadRequest;
        return;
    }

    var (sessionId, session) =
        await GetOrCreateSessionAsync(request.SessionId, agent, sessions, ct);

    context.Response.Headers.ContentType = "text/event-stream";
    context.Response.Headers.CacheControl = "no-cache";
    await SseEvent.WriteAsync(context.Response, "session", new { sessionId }, ct);

    Setting Content-Type: text/event-stream and Cache-Control: no-cache are both required by the SSE spec. Without the content-type header, proxies and load balancers may buffer the entire response.

  3. Drive the streaming loop

    Now drive the stream. Call RunStreamingAsync and read each update with await foreach. Inside the loop, check update.Contents for typed content items first, then check update.Text for token text. Send the matching SSE event for each one. After the loop ends normally, send done. If the run throws, send error instead. The client uses done to know the turn is finished and stop listening.

    🔧 Note

    This snippet continues and closes the app.MapPost lambda opened in step 2. The final }); closes both the lambda body and the MapPost call — do not add a second one.

    Program.cs 
        try
    {
        await foreach (var update in
            agent.RunStreamingAsync(request.Message, session, cancellationToken: ct))
        {
            foreach (var content in update.Contents)
            {
                if (content is FunctionCallContent call)
                {
                    await SseEvent.WriteAsync(context.Response, "tool_call",
                        new { name = call.Name, arguments = call.Arguments }, ct);
                }
            }

            if (!string.IsNullOrEmpty(update.Text))
                await SseEvent.WriteAsync(context.Response, "token",
                    new { text = update.Text }, ct);
        }

        await SseEvent.WriteAsync(context.Response, "done", new { }, ct);
    }
    catch (Exception ex)
    {
        await SseEvent.WriteAsync(context.Response, "error",
            new { message = ex.Message }, ct);
    }
});

    Why check Contents before Text? A single update can carry both. The model can emit a tool call and some text in the same chunk. The contents loop handles the structured tool call. The text check then runs after it. Both can send an event for the same update, and that is correct.

  4. Why the session event goes before the try block

    The session event is written before the try block, not inside it. The client needs the session id even if the run fails right away. Suppose the session write were inside the try and the agent threw on the first token. The client would then get only an error event with no id. It could not retry the turn in the same session. Writing session first makes sure the id always reaches the client.

How the update stream maps to the agent's tool loop

The timing of the events explains what you see in the terminal. One full agent turn with a tool call produces updates in about this order:

  1. Zero or more token events — the model's "thinking aloud" text before it decides to call a tool (some models emit this, some do not).
  2. A tool_call event — the model committed to calling a function.
  3. Silence — MAF executes the tool locally; no updates flow during execution.
  4. More token events — the model's answer after seeing the tool result.
  5. done.

If the agent calls multiple tools (e.g. schema lookup then a SQL query), the tool_call / silence pattern repeats before the final answer tokens arrive. The done event is always last and is emitted exactly once.

Verify

✅ Gate — do not advance until green

Start with Testing environment (mandatory ritual from A1): 

dotnet run -- --environment Testing

Console must print Hosting environment: Testing.

Send a streaming request with curl — watch tokens arrive incrementally: 

curl -s -N -X POST http://localhost:8124/chat/stream \
  -H "Content-Type: application/json" \
  -d '{"message": "What projects do I have?"}'

The -N flag disables curl's own output buffering so you see each SSE event as it arrives. Expected output shape (exact text will differ): 

event: session
data: {"sessionId":"a3f1..."}

event: tool_call
data: {"name":"list_projects","arguments":{}}

event: token
data: {"text":"You have "}

event: token
data: {"text":"three projects: "}

event: token
data: {"text":"claudalytics, ..."}

event: done
data: {}

Green checks:

  • The session event arrives first, before any token.
  • At least one tool_call event appears (the agent called list_projects or equivalent).
  • Multiple token events arrive, each with a small text fragment — not one giant blob.
  • The stream ends with done, not just a closed connection.

Negative test — detecting buffering:

If you see only one token event containing the entire answer followed immediately by done, the response is being buffered. Check two things:

  1. Is FlushAsync called after every WriteAsync in SseEvent? If it is missing, tokens queue in ASP.NET's buffer and are released all at once when the connection closes.
  2. Is there a reverse proxy (nginx, YARP, Kestrel behind IIS) between your curl and the app? Proxies often buffer SSE unless configured with proxy_buffering off or equivalent.

Follow-up with the session id from step 1:

curl -s -N -X POST http://localhost:8124/chat/stream \
  -H "Content-Type: application/json" \
  -d '{"message": "Which of those is most expensive?", "sessionId": "a3f1..."}'

The answer should reference the projects from the first turn. The same multi-turn memory from A2 works here because RunStreamingAsync takes the same AgentSession parameter as RunAsync.

⚠️ Pitfalls
  • One giant token blob, then done → missing FlushAsync in SseEvent.WriteAsync. ASP.NET buffers the response body; without an explicit flush after every write, all events are held in memory and sent together when the run finishes. Add await response.Body.FlushAsync(ct) after WriteAsync.
  • Client hangs after the last token, never closes → the done event was never emitted. This happens when the done write is inside the try but after a statement that threw, bypassing it. The done write must be the last statement in the try block, and the catch must emit error instead. Browsers implementing EventSource will reconnect indefinitely on a missing done.
  • No tool_call events, but the answer mentions tool results → the tool was called via RunAsync (the non-streaming path) somewhere higher up, or the endpoint is silently routing to a non-streaming handler. Confirm the request is hitting /chat/stream and not /chat.
  • Session id not received by the client → the session event is inside the try block after the streaming call began, so an early error discards it. Move the session write to before the try block — it must be the very first write after the headers are set.
  • Proxy / load balancer buffers the stream → set Content-Type: text/event-stream and Cache-Control: no-cache on the response before the first write. Most proxies respect these headers to disable buffering. In nginx add proxy_buffering off; for SSE routes.
