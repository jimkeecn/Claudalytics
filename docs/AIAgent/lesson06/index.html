Lesson 06 · B3 · Module B — The graph

An agent is just a node

★★ Haiku

What you'll learn

Right now the Claudalytics Copilot investigation ends by dumping raw probe rows. A person asks "what does this mean?" and the pipeline has no answer, because nothing turns the numbers into words. This lesson drops an LLM agent into the graph as one node. The node reads the typed probe data and writes a short report, so the run finishes with prose a person can read.

The mental model is simple. An agent is just a node. You extend Executor<T>, receive a typed input, call agent.RunAsync, and yield the result. The graph shape and the event stream from B2 stay the same. Only the last node gets smarter.

To get there you add three message records (Findings, DeepDiveRequest, DeepDiveDecision), a ValidatorExecutor that does the fan-in, and a SynthesisExecutor that holds the agent. You also create InvestigationWorkflow.cs as the real home of the graph's Build method, which retires the B1 scaffolding files ProbeWorkflow.cs and CollectorExecutor.

📘 Teach

MAF's intelligence spectrum: every workflow node sits between "pure deterministic code" (free, instant) and "full LLM agent" (flexible, expensive). You choose how much intelligence each step deserves. The SQL probes need none; the synthesis step needs exactly enough to turn tabular numbers into coherent prose.

API surfaces introduced in this lesson:

  • Executor<TInput> — unchanged base class; inject the agent via the constructor (DI works exactly as in any service).
  • [YieldsOutput(typeof(T))] — terminal-node declaration; the framework rejects undeclared yield types at runtime, so this attribute is mandatory.
  • context.YieldOutputAsync(value, ct) — pushes the final value to the workflow output stream and ends the run.
  • agent.RunAsync(prompt, ct) — single-turn LLM call returning .Text. Use a dedicated writer agent here, not the main analyst; it must never ask a follow-up question (see the prompt contract below).

The prompt contract for agent-in-workflow: the model's first response is the workflow's output. There is no channel for a follow-up question to get answered. System instructions must include: "Your response is the final product. Do not ask questions or request more data."

Pipeline shape after this lesson

PlanExecutor
    │  (3× ProbeJob)
    ▼  fan-out
ProbeExecutor × 3
    │  (3× ProbeResult)
    ▼  fan-in barrier
ValidatorExecutor        ← NEW: deterministic; builds Findings; routes spike branch
    │  (Findings)             (DeepDiveRequest goes to deepDive directly — no human gate in B3)
    ▼
SynthesisExecutor        ← NEW: holds AIAgent → markdown report
    │  [YieldsOutput]
    ▼  workflow output: string

Build it

  1. Define the new message records in InvestigationModels.cs

    The graph needs typed messages to pass between nodes. Findings is the record the validator builds and the synthesis node reads. DeepDiveRequest and DeepDiveDecision belong to the cost-spike branch, which the validator and the deep-dive stub reference but do not fully use yet. Append these three records to Workflows/InvestigationModels.cs (the file from B1 that already holds InvestigationRequest, ProbeJob, and ProbeResult). No new usings are needed.

    Workflows/InvestigationModels.cs — append after the ProbeResult record 
    /// <summary>Aggregated, validated probe results.</summary>
public sealed record Findings(int Days, List<ProbeResult> Results, bool CostSpike, List<string> ValidationNotes);

/// <summary>Deep-dive branch request, sent by the validator on a cost spike.</summary>
public sealed record DeepDiveRequest(string Reason);

/// <summary>Deep-dive branch decision, returned by the approval port in F2.</summary>
public sealed record DeepDiveDecision(bool Approve);

    DeepDiveRequest and DeepDiveDecision are introduced here because the validator's [SendsMessage] attributes and the DeepDiveExecutor stub (Step 3) reference them. The human-approval PORT that routes the request to a human and waits for the decision is added in F2.

  2. Add the writer agent's system instructions

    The synthesis node needs an agent to call. That agent is a writer, not the main analyst. It has one job. It receives structured data and returns markdown prose. Add a Writer constant inside the existing Instructions class in Agents/Instructions.cs, after the System constant. The System and SchemaDoc constants were added in A1, so the usings and namespace are already there.

    Agents/Instructions.cs — inside the Instructions class 
    public const string Writer = """
    You are a technical writer for an observability report.
    You receive structured probe data (TSV) and validation notes.
    Write a short markdown investigation report: headline numbers,
    then findings, then 1-3 recommendations.
    Use ONLY the numbers present in the data — do not invent figures.
    If data is thin, say so honestly.
    Your response is the final product. Do not ask questions or request more data.
    """;

    The last sentence is the prompt contract. The model's first reply is the workflow's output. There is no channel for a follow-up question to get an answer, so the agent must never ask one.

  3. Add ValidatorExecutor, DeepDiveExecutor stub, and SynthesisExecutor to InvestigationExecutors.cs

    Append all three executors to Workflows/InvestigationExecutors.cs. The usings at the top of that file already include using Microsoft.Agents.AI; and using Microsoft.Agents.AI.Workflows; from B1. Order matters for teaching: Validator first (fan-in logic), then DeepDive stub (spike branch placeholder), then Synthesis (the LLM node).

    ValidatorExecutor — deterministic fan-in

    The validator sits behind the fan-in barrier. It collects all three ProbeResult messages, checks each one, and builds the Findings record that the synthesis node reads next. It collects the results in an instance field. In this B3 form the cost-spike check is not built yet, so CostSpike is always false and Days is a placeholder zero. B4 (L07) wires the real values through context state and adds spike detection. The ⚠ marker on the field flags a bug that B4 explains. The field does not survive checkpoint and resume.

    Workflows/InvestigationExecutors.cs — append 
    [SendsMessage(typeof(Findings))]
[SendsMessage(typeof(DeepDiveRequest))]
public sealed class ValidatorExecutor() : Executor<ProbeResult>("validator")
{
    private const int ExpectedProbes = 3;
    private readonly List<ProbeResult> _accumulated = []; // ⚠ B4 shows why this field breaks on resume

    public override async ValueTask HandleAsync(
        ProbeResult result, IWorkflowContext context, CancellationToken cancellationToken = default)
    {
        _accumulated.Add(result);
        if (_accumulated.Count < ExpectedProbes) return;

        var notes = _accumulated
            .Where(probe => !probe.HasData)
            .Select(probe => $"Probe '{probe.Name}' returned no usable numbers — finding rejected, not interpreted.")
            .ToList();

        var findings = new Findings(
            Days: 0,
            Results: [.._accumulated],
            CostSpike: false,
            ValidationNotes: notes);

        await context.AddEventAsync(
            new InvestigationProgressEvent("Validation complete — forwarding findings."), cancellationToken);

        await context.SendMessageAsync(findings, cancellationToken: cancellationToken);
    }
}

    [SendsMessage(typeof(DeepDiveRequest))] is declared even though this B3 form never sends it. The builder validates all edges at Build() time — declaring the type now means the deep-dive edge added in Step 4 is accepted without error. The validator will actually send DeepDiveRequest only after B4 adds spike detection.

    DeepDiveExecutor — stub for the spike branch

    Step 4 wires the deep-dive executor into the graph. The builder checks every declared edge at Build() time, so this stub must exist for the validator's [SendsMessage(typeof(DeepDiveRequest))] edge to be accepted. In B3 the body is a stub. It reads the findings from shared state, falls back to an empty record if the state is missing, and forwards the findings to the synthesis node. The full expensive-query body is added in F2.

    Workflows/InvestigationExecutors.cs — append 
    [SendsMessage(typeof(Findings))]
public sealed class DeepDiveExecutor() : Executor<DeepDiveDecision>("deepdive")
{
    public override async ValueTask HandleAsync(
        DeepDiveDecision decision, IWorkflowContext context, CancellationToken cancellationToken = default)
    {
        var findings = await context.ReadStateAsync<Findings>(
            "findings", scopeName: "investigation", cancellationToken)
            ?? new Findings(0, [], false, ["Findings state was missing."]);

        await context.AddEventAsync(
            new InvestigationProgressEvent("Deep-dive stub — forwarding findings."), cancellationToken);

        await context.SendMessageAsync(findings, cancellationToken: cancellationToken);
    }
}

    SynthesisExecutor — the agent node

    The synthesis executor is the only LLM node in the graph. It reads the Findings the validator sent. Its shape is the same as every other executor. It extends Executor<T> and implements HandleAsync. The difference is the body. It calls writer.RunAsync instead of running plain code.

    The first part of the body turns the typed Findings into plain text the agent can read. It joins each probe's rows into one block and joins the validation notes into another.

    Workflows/InvestigationExecutors.cs — append 
    [YieldsOutput(typeof(string))]
public sealed class SynthesisExecutor(AIAgent writer) : Executor<Findings>("synthesis")
{
    public override async ValueTask HandleAsync(
        Findings findings, IWorkflowContext context, CancellationToken cancellationToken = default)
    {
        await context.AddEventAsync(
            new InvestigationProgressEvent("Synthesizing the report."), cancellationToken);

        var probesText = string.Join("\n\n",
            findings.Results.Select(probe => $"## {probe.Name}\n{probe.Rows}"));
        var notesText = findings.ValidationNotes.Count == 0
            ? "(none)"
            : string.Join("\n", findings.ValidationNotes);

    The second part calls the writer agent with one prompt. The prompt carries the probe text, the notes, and the day count. The agent returns markdown, and YieldOutputAsync pushes that text out as the workflow's final output. Close the method and class after this block.

    Workflows/InvestigationExecutors.cs — same method 
            var response = await writer.RunAsync($"""
            Write a short markdown investigation report over the last {findings.Days} days of
            Claude Code telemetry. Cost spike detected: {findings.CostSpike}.

            Probe data (TSV):
            {probesText}

            Validator notes (mention them honestly):
            {notesText}

            Shape: headline numbers, findings, then 1-3 recommendations. Use only the
            numbers in the data above.
            """, cancellationToken: cancellationToken);

        await context.YieldOutputAsync(response.Text, cancellationToken);
    }
}

    [YieldsOutput(typeof(string))] is required. Without it the framework throws a runtime error that names the executor and the undeclared type.

  4. Construct the writer agent inline in InvestigationWorkflow.Build()

    The synthesis node needs the writer agent passed to it. Do not register the writer in DI. Registering it as AddSingleton<AIAgent> would collide with the main analyst, which is already registered under the same type. DI would then inject whichever one was registered last. Instead, build the writer inline inside InvestigationWorkflow.Build(), which is the pattern the app uses. No new NuGet packages are needed. All dependencies were added in A1. Place this after the code resolves apiKey and creates client.

    Workflows/InvestigationWorkflow.cs — inside Build() 
    var writer = client.AsAIAgent(
    model: ModelTiers.Analyst(config),
    instructions: Instructions.Writer,
    name: "InvestigationWriter");

    client.AsAIAgent(model:, instructions:, name:) is the three-param overload. Passing instructions: sets the system prompt without a ChatClientAgentOptions wrapper object — you use exactly this form.

  5. Create Workflows/InvestigationWorkflow.cs with the full B3 graph

    This file is the real home of the InvestigationWorkflow.Build method. Create it as a new file. It replaces the B1 scaffolding ProbeWorkflow.cs. The first part builds the file header, the writer agent, and one instance of each node. These nodes are the same ones you wrote in the earlier steps.

    Workflows/InvestigationWorkflow.cs new file 
    using AiAgent.Agents;
using AiAgent.Tools;
using Anthropic;
using Microsoft.Agents.AI;
using Microsoft.Agents.AI.Workflows;

namespace AiAgent.Workflows;

/// <summary>The investigation graph (B3 form). No human-approval port yet; that is added in F2.</summary>
public static class InvestigationWorkflow
{
    public static Workflow Build(IConfiguration config, ClickHouseClient clickHouse)
    {
        var apiKey = config["ANTHROPIC_API_KEY"]
            ?? throw new InvalidOperationException("ANTHROPIC_API_KEY is not set.");

        IAnthropicClient client = new AnthropicClient { ApiKey = apiKey };
        var writer = client.AsAIAgent(
            model: ModelTiers.Analyst(config),
            instructions: Instructions.Writer,
            name: "InvestigationWriter");

        var plan = new PlanExecutor();
        ProbeExecutor[] probes =
        [
            new("probe-0", clickHouse),
            new("probe-1", clickHouse),
            new("probe-2", clickHouse),
        ];
        var validator = new ValidatorExecutor();
        var deepDive = new DeepDiveExecutor();
        var synthesis = new SynthesisExecutor(writer);

        var builder = new WorkflowBuilder(plan);

    The second part wires the edges. The fan-out edge routes each ProbeJob from the plan to one probe. The fan-in barrier holds the validator until all three probes have delivered. The normal path sends Findings from the validator to the synthesis node. The last two edges are the spike branch. The validator sends DeepDiveRequest to the deep-dive stub, and the stub sends the findings on to synthesis. Both spike edges must be declared now, even though B3 never fires them, so the builder accepts the validator's [SendsMessage(typeof(DeepDiveRequest))] at Build() time. There is no human gate on this branch yet. The approval port that pauses the run for a person is added in F2.

    Workflows/InvestigationWorkflow.cs — same method 
            builder.AddFanOutEdge<ProbeJob>(plan, probes.Select(p => (ExecutorBinding)p),
            (job, targetCount) => [(job?.Slot ?? 0) % targetCount]);

        builder.AddFanInBarrierEdge(probes.Select(p => (ExecutorBinding)p), validator);

        builder.AddEdge<Findings>(validator, synthesis, _ => true);

        builder.AddEdge<DeepDiveRequest>(validator, deepDive, _ => true);
        builder.AddEdge(deepDive, synthesis);

        return builder.WithOutputFrom(synthesis).Build();
    }
}

🔄 Evolution arc

This lesson completes Arc 1, from the B1 collector to the B3 synthesis node. The naive collector joined raw TSV and returned it. That was enough to prove the fan-in worked. It breaks the moment a person asks "what does this mean?" The pipeline cannot answer. The synthesis node is the fix. The v1 vs v2 tabs below show what changed.

v1 vs v2

The v1 collector is shown only to expose the problem — you would not ship it. The end state: 

// v1 — naive concatenating collector — do not ship
[YieldsOutput(typeof(string))]
public sealed class CollectorExecutor() : Executor<ProbeResult>("collector")
{
    private readonly List<string> _accumulated = [];  // ⚠ breaks on checkpoint/resume (B4)

    public override async ValueTask HandleAsync(
        ProbeResult result, IWorkflowContext context, CancellationToken cancellationToken = default)
    {
        _accumulated.Add($"## {result.Name}\n{result.Rows}");
        if (_accumulated.Count < 3) return;

        // Concatenate and emit — no intelligence.
        await context.YieldOutputAsync(string.Join("\n\n", _accumulated), cancellationToken);
    }
}

Why it breaks: Output is raw TSV — no interpretation, no recommendations, not usable by a human. The instance field _accumulated also breaks on checkpoint/resume (the subject of B4).

The v2 synthesis node receives an assembled Findings record from ValidatorExecutor — one message, one LLM call, one yield. No instance field; accumulation is done checkpoint-safely in the validator via context.ReadOrInitStateAsync (added in B4).

Workflows/InvestigationExecutors.cs 
[YieldsOutput(typeof(string))]
public sealed class SynthesisExecutor(AIAgent writer) : Executor<Findings>("synthesis")
{
    public override async ValueTask HandleAsync(
        Findings findings, IWorkflowContext context, CancellationToken cancellationToken = default)
    {
        var probesText = string.Join("\n\n",
            findings.Results.Select(probe => $"## {probe.Name}\n{probe.Rows}"));

        var response = await writer.RunAsync($"""
            Write a short markdown investigation report over the last {findings.Days} days ...
            Probe data (TSV): {probesText}
            Use only the numbers in the data above.
            """, cancellationToken: cancellationToken);

        await context.YieldOutputAsync(response.Text, cancellationToken);
    }
}

Verify

✅ Gate — do not advance until green

dotnet run -- --environment Testing
curl -s -X POST http://localhost:8124/investigate \
  -H "Content-Type: application/json" \
  -d '{"days": 7}'

All three must be true:

  1. Response body is prose markdown — headers, sentences, numbers. Not a raw TSV dump.
  2. Numbers in the report match the probe data exactly. If cost-trend shows 0.12 as the highest-cost day, the report must say 0.12 — not a hallucinated figure.
  3. The event timeline from the B2 driver shows the same graph shape: probe executors in one superstep, validator next, synthesis last. Adding an agent node does not change topology.

Negative test: Remove the probe data from the synthesis prompt (pass an empty probesText) and rerun. The model will produce a plausible-sounding report with invented numbers — it still completes successfully. This is the hallucination baseline. If your grounded and ungrounded reports look identical, the prompt is not constraining the model to the data — tighten the instructions. Put the probe data back before advancing.

⚠️ Pitfalls
  • Workflow output is a question, not a report → Writer agent instructions are missing the prompt contract sentence. Add: "Your response is the final product. Do not ask questions or request more data."
  • Runtime error naming SynthesisExecutor and string → [YieldsOutput(typeof(string))] attribute is missing from the class.
  • Report numbers don't match the probes → findings.Results is empty when synthesis runs. The validator is not populating the Findings record — add a debug event in ValidatorExecutor logging the result count.
  • Wrong agent injected into SynthesisExecutor → You registered the writer as AddSingleton<AIAgent> in Program.cs. DI resolves the last registered AIAgent and SynthesisExecutor gets whichever wins the registration order race. Fix: construct the writer inline in InvestigationWorkflow.Build() (as shown in Step 4) and pass it directly to new SynthesisExecutor(writer) — no DI lookup at all.
  • Build error: undeclared edge type DeepDiveRequest → ValidatorExecutor is missing [SendsMessage(typeof(DeepDiveRequest))], or the AddEdge<DeepDiveRequest>(validator, deepDive) call in InvestigationWorkflow.Build() is absent. Both must be present even though the spike branch is never triggered in B3.
