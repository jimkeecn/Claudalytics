Lesson 07 · B4 · Module B — The graph

State that survives death: checkpoints & resume

★★★ No LLM

What you'll learn

An investigation can run for several minutes. It sends out many ClickHouse queries, called probes. Later, in F2, it can also stop and wait hours for a person to approve a step. If the process crashes, restarts, or is stopped in the middle, you do not want to start again from zero. Starting again means running every probe again, paying for every LLM call again, and losing an approval the user already gave. B4 makes a run survive a restart and continue from where it stopped. That is the goal of this lesson. The rest of the page shows how to do it.

An executor looks like a normal object. So it feels natural to collect fan-in results in a field like private List<T> _collected = []. This works while the process keeps running. It breaks when the process restarts in the middle of a run. MAF saves workflow state to disk at the end of each superstep and reloads it on resume. But it cannot save an instance field, because it does not know the field exists. On restart the field is empty again, so the result is wrong or empty. The fix is simple: do not keep state in your own fields. Put every value that must survive into the workflow context. Use the private scope for one executor, or a named shared scope for values that many executors read. Once state lives in the context, FileSystemJsonCheckpointStore saves and restores it for you at each superstep.

📘 Teach

The main idea: the workflow context is the only storage that lasts during a run. Everything else is temporary.

  • IWorkflowContext.ReadStateAsync<T>(key, scopeName?) — read a value from the context. Omit scopeName to use the executor's private scope; pass a name (e.g. "investigation") for a scope shared across executors in this run.
  • IWorkflowContext.ReadOrInitStateAsync<T>(key, factory) — read, or initialise with a default if absent. Essential for accumulators that start empty on the first invocation.
  • IWorkflowContext.QueueStateUpdateAsync(key, value, scopeName?) — queue a write. Writes are applied atomically at the superstep boundary, then included in the checkpoint.
  • FileSystemJsonCheckpointStore(DirectoryInfo) — persists each checkpoint as a JSON file named {runId}_{checkpointId}.json.
  • CheckpointManager.CreateJson(store, null) — wraps the store. Pass it to InProcessExecution.RunStreamingAsync to enable checkpointing.
  • InProcessExecution.ResumeStreamingAsync(workflow, checkpointInfo, manager) — rebuild the graph (always fresh; a Workflow is owned by exactly one runner) and resume from the given checkpoint.

Why two phases: queue then apply

The runtime does not write state right away. It collects the writes and applies them together at the end of the superstep. This matters at a fan-in, where several probe executors send results to ValidatorExecutor at the same time. If the writes all happened at once, they could overwrite each other. When you call QueueStateUpdateAsync, the write is only staged. It is applied when the superstep closes. The checkpoint is then saved from that result. This is why each executor reads with ReadStateAsync at the start, instead of keeping state in a field. The value you read is always the last saved value. It is never a half-finished value from another executor.

  1. Step 1 — Understand why v1 breaks on resume

    Read this version of ValidatorExecutor carefully. Every test passes. Three probes arrive, the list reaches three items, and the findings go to synthesis. Now imagine the process is stopped between the fan-in superstep and the synthesis superstep. The checkpoint saved before the fan-in keeps the probe results in context state. But the _collected list lives only in memory. On resume the executor is built again with an empty list. The count never reaches 3 again, so the validator never sends anything. 

    // ❌ ValidatorExecutor v1 — illustrative (do NOT ship this)
[SendsMessage(typeof(DeepDiveRequest))]
[SendsMessage(typeof(Findings))]
public sealed class ValidatorExecutor() : Executor<ProbeResult>("validator")
{
    private const int ExpectedProbes = 3;

    // Instance field: invisible to the checkpoint serialiser.
    // Works in a single process run; LOST on kill+resume.
    private readonly List<ProbeResult> _collected = [];

    public override async ValueTask HandleAsync(
        ProbeResult result, IWorkflowContext context, CancellationToken cancellationToken = default)
    {
        _collected.Add(result);  // ← vanishes on restart

        if (_collected.Count < ExpectedProbes)
            return;

        var days = await context.ReadStateAsync<int>("days", scopeName: "investigation", cancellationToken);
        var costSpike = DetectCostSpike(_collected.FirstOrDefault(p => p.Name == "cost-trend")?.Rows);
        var findings = new Findings(days, _collected, costSpike, []);

        await context.QueueStateUpdateAsync("findings", findings, scopeName: "investigation", cancellationToken);
        await context.SendMessageAsync(findings, cancellationToken: cancellationToken);
    }
}

    1 · Keep the list in context, not in a field. ReadOrInitStateAsync returns an empty list on the first call. On resume it returns the saved list from the checkpoint. After each add, the list is written back. This is why the count survives a restart. It is the main fix in v2. If fewer than three probes have arrived, the executor returns and waits.

        {

    4 · The spike check. This is a pure function. It reads the cost-trend rows. It flags the latest day when its cost is more than 1.5 times the average of the earlier days. If there is only one day of data, it flags a cost above $5. It is kept separate from HandleAsync so you can unit-test it without starting a workflow.

    ValidatorExecutor v2 (4 of 4): DetectCostSpike helper 
        private static bool DetectCostSpike(string? costTrendRows)
    {
        if (costTrendRows is null) return false;

        var costs = costTrendRows.Split('\n').Skip(1)
            .Select(line => line.Split('\t'))
            .Where(cells => cells.Length >= 2
                && double.TryParse(cells[1], System.Globalization.NumberStyles.Any,
                    System.Globalization.CultureInfo.InvariantCulture, out _))
            .Select(cells => double.Parse(cells[1], System.Globalization.CultureInfo.InvariantCulture))
            .ToList();

        if (costs.Count == 0) return false;
        var last = costs[^1];
        if (costs.Count == 1) return last > 5;

        var priorAverage = costs[..^1].Average();
        return last > priorAverage * 1.5;
    }
}

    The key difference: collected is now read from the context at the start of every call. So the runtime can restore it from a checkpoint if the process was stopped between supersteps. No field is used.

  3. Step 3 — Expand InvestigationService from B2 to add checkpointing

    Open the existing Workflows/InvestigationService.cs created in B2. Do not create a new file. The B2 shell already holds WorkflowEventDto, InvestigationStatus, the minimal constructor, StartAsync, DriveAsync, and ToDto. This step widens it to support checkpointing and in-process approval responses.

    Why each change is needed. Checkpointing needs three things: a place to save snapshots (_store), an object that makes a snapshot at each superstep (_checkpointManager), and a folder to hold the files (_checkpointDir). That is why there are three fields, not one. Resume must match a paused run with the exact request that blocked it. A plain StreamingRun does not hold that request. So the value in _pending becomes a (Run, Request) pair. The constructor now sets up checkpointing. If you do not give a CheckpointManager to the runner, nothing is saved to disk. A run that saved nothing cannot resume.

    Changes to make: add three new fields (_checkpointManager, _store, _checkpointDir), widen the _pending dictionary's value type from StreamingRun to the (StreamingRun Run, ExternalRequest Request) tuple, replace the no-checkpoint constructor with the checkpoint-aware one, and add RespondAsync. The workflow factory becomes () => InvestigationWorkflow.Build(config, clickHouse) (upgraded from the B2 ProbeWorkflow.Build).

    🔧 Note

    New using required in this file: using Microsoft.Agents.AI.Workflows.Checkpointing; (in addition to using Microsoft.Agents.AI.Workflows; from B1 and using System.Collections.Concurrent;). WorkflowEventDto and InvestigationStatus are already defined in B2 — do not redefine them.

    1 · The fields. The factory builds a fresh Workflow per run; the three checkpoint members persist and locate snapshots; _pending maps a run id to its live run plus the request currently blocking it — that pair is the tuple widening.     public sealed class InvestigationService
{

    private readonly DirectoryInfo _checkpointDir;

    2 · The constructor wires checkpointing. Ensure the checkpoint directory exists, build the file store over it, wrap that in a JSON CheckpointManager. The workflow is stored as a factory, not an instance — a Workflow is owned by exactly one runner, so every run and resume needs a fresh one.

    Workflows/InvestigationService.cs — constructor 
        public InvestigationService(IConfiguration config, Tools.ClickHouseClient clickHouse, ILogger<InvestigationService> logger)
    {
        _logger = logger;
        var dir = new DirectoryInfo(config["CHECKPOINT_DIR"] ?? "checkpoints");
        dir.Create();
        _checkpointDir = dir;
        _store = new FileSystemJsonCheckpointStore(dir);
        _checkpointManager = CheckpointManager.CreateJson(_store, null);

    3 · Start and in-process respond. StartAsync runs a brand-new investigation: fresh run id, streamed through the checkpoint manager so snapshots get written, then drained by DriveAsync. RespondAsync answers an approval while the run is still live in this process — pop the pending handle, send the decision, resume draining. No live handle (e.g. after a restart) returns null so the route can redirect the caller to /resume. Leave the class open here — Step 4 adds the remaining members and the closing brace.

    Workflows/InvestigationService.cs — StartAsync + RespondAsync 
        public async Task<InvestigationStatus> StartAsync(int days, CancellationToken ct)
    {
        var runId = Guid.NewGuid().ToString("N");
        var run = await InProcessExecution.RunStreamingAsync(
            _workflowFactory(), new InvestigationRequest(days), _checkpointManager, runId, ct);
        return await DriveAsync(runId, run, [], ct);
    }

    public async Task<InvestigationStatus?> RespondAsync(string runId, bool approve, CancellationToken ct)
    {
        if (!_pending.TryRemove(runId, out var pending))
            return null;

        await pending.Run.SendResponseAsync(pending.Request.CreateResponse(new DeepDiveDecision(approve)));
        return await DriveAsync(runId, pending.Run, [], ct);
    }

  4. Step 4 — Add ResumeAsync, DriveAsync, and helpers to InvestigationService

    These four members go inside the same InvestigationService class from Step 3. Add them after RespondAsync, then close the class brace.

    1 · ResumeAsync. This loads the most recent checkpoint for a run and continues it. Two things make it tricky. First, the checkpoint index holds checkpoints from every run, not only this one. So you filter by run id. Second, the checkpoint ids are random values with no order. So you cannot tell which one is newest from the id. Instead, you sort by the file's last write time. If no checkpoint matches the run id, return null and the route replies 404. If one matches, drop any live handle for this run, build a fresh workflow, and resume from the newest checkpoint.

    Workflows/InvestigationService.cs — ResumeAsync 
        public async Task<InvestigationStatus?> ResumeAsync(string runId, CancellationToken ct)
    {
        var mine = (await _store.RetrieveIndexAsync(runId, null))
            .Where(checkpoint => checkpoint.SessionId == runId)
            .Select(checkpoint => (Info: checkpoint, WrittenAt: CheckpointWrittenAt(runId, checkpoint)))
            .OrderBy(entry => entry.WrittenAt)
            .ToList();

        if (mine.Count == 0)
            return null;

        _pending.TryRemove(runId, out _);
        var run = await InProcessExecution.ResumeStreamingAsync(_workflowFactory(), mine[^1].Info, _checkpointManager, ct);
        return await DriveAsync(runId, run, [new("resumed", $"from checkpoint {mine.Count} of run {runId}")], ct);
    }

    2 · CheckpointWrittenAt. A small helper. It finds the file behind a checkpoint and returns its last write time. ResumeAsync uses it to sort checkpoints from oldest to newest.

    Workflows/InvestigationService.cs — CheckpointWrittenAt 
        private DateTime CheckpointWrittenAt(string runId, CheckpointInfo checkpoint)
    {
        var file = _checkpointDir.GetFiles($"{runId}_{checkpoint.CheckpointId}*").FirstOrDefault();
        return file?.LastWriteTimeUtc ?? DateTime.MinValue;
    }

    3 · DriveAsync. This is the shared loop used by StartAsync, RespondAsync, and ResumeAsync. It reads workflow events one by one, turns each one into a small status object, and keeps the final report. If something throws, it logs the error and returns a failed status. The approval-pause event is not handled here. That part is added in F2.

    Workflows/InvestigationService.cs — DriveAsync 
        private async Task<InvestigationStatus> DriveAsync(
        string runId, StreamingRun run, List<WorkflowEventDto> events, CancellationToken ct)
    {
        string? report = null;
        try
        {
            await foreach (var evt in run.WatchStreamAsync(ct))
            {
                var dto = ToDto(evt);
                if (dto is not null) events.Add(dto);

                if (evt is WorkflowOutputEvent output)
                    report = output.Data?.ToString();
            }
        }
        catch (Exception ex)
        {
            _logger.LogError(ex, "Investigation run {RunId} failed.", runId);
            events.Add(new("error", ex.Message));
            return new InvestigationStatus(runId, "failed", null, null, events);
        }

        return new InvestigationStatus(runId, report is null ? "failed" : "completed", report, null, events);
    }

    4 · ToDto. This maps each workflow event to a small object for the API. The approval and port cases are added in F2. This is the last member, so the class brace closes after it.

    Workflows/InvestigationService.cs — ToDto (then close the class) 
        private static WorkflowEventDto? ToDto(WorkflowEvent evt) => evt switch
    {
        WorkflowStartedEvent => new("workflow_started", null),
        SuperStepCompletedEvent => new("superstep_completed", null),
        ExecutorInvokedEvent invoked => new("executor_invoked", invoked.ExecutorId),
        ExecutorCompletedEvent completed => new("executor_completed", completed.ExecutorId),
        ExecutorFailedEvent failed => new("executor_failed",
            $"{failed.ExecutorId}: {(failed.Data as Exception)?.GetBaseException().Message ?? failed.Data?.ToString()}"),
        InvestigationProgressEvent progress => new("progress", progress.Message),
        WorkflowOutputEvent => new("workflow_output", "report ready"),
        _ => null,
    };
}

🔄 Evolution arc

Why we showed a broken version first. The v1 ValidatorExecutor in Step 1 is only an example. It is not part of the build — only the final v2 ships. You read the simple, wrong version so you can see the exact problem. Every test in one process passes. Then a stop and resume gives a wrong or empty result, with no error. It is easier to remember the rule after you see working code fail a resume.

This lesson also shows three real-world traps for the first time: the store index covers all runs, the checkpoint ids have no order, and a Workflow can have only one owner. You will use all three fully in F2 — Deep investigation: HITL port + production checkpoints. There, the same pipeline adds a human-approval step and runs on real telemetry data.

How the two scopes work together

The named scope "investigation" is shared. Every executor in the run can read it. PlanExecutor writes "days". Each ProbeExecutor writes "probe:{name}". ValidatorExecutor reads "days" and writes "findings". DeepDiveExecutor reads "findings" when there is a cost spike. The private scope (no scopeName) is used only for "collected", the list that belongs to ValidatorExecutor alone. Keep each value in the smallest scope it needs. This stops other executors from depending on data they should not use.

public sealed class DeepDiveExecutor(ClickHouseClient clickHouse) : Executor<DeepDiveDecision>("deepdive")
{
    public override async ValueTask HandleAsync(
        DeepDiveDecision decision, IWorkflowContext context, CancellationToken cancellationToken = default)
    {
        var findings = await context.ReadStateAsync<Findings>("findings", scopeName: "investigation", cancellationToken)
            ?? new Findings(7, [], false, ["Findings state was missing."]);

        if (!decision.Approve)
        {
            findings.ValidationNotes.Add("A cost spike was detected but the deep dive was declined by the user.");
            await context.SendMessageAsync(findings, cancellationToken: cancellationToken);
            return;
        }
    }
}

Verify

✅ Gate — do not advance until green

1. Start a run and catch an early checkpoint. The /investigate call runs to the end before it returns, so you cannot stop it from the curl side. Instead, watch the checkpoints/ folder in a second terminal. The moment the first checkpoint file appears, stop the server with Ctrl+C. Stopping this early is the point: the newest checkpoint on disk is now a partial one, saved after the plan step but before synthesis. So the resume still has real work to do, and it will produce a report. If you let the run finish, the only checkpoint is the final one, and the resume produces nothing new. 

# Terminal 1 — start the server, then start a run:
dotnet run -- --environment Testing
curl -s -X POST "http://localhost:8124/workflow/investigate" \
  -H "Content-Type: application/json" -d '{"days":7}'

# Terminal 2 — watch for the first file, then stop Terminal 1 (Ctrl+C):
ls checkpoints/
# A file looks like: 96d437ca5603472f8e2b571bfc70679a_<guid>.json
# The runId is the part BEFORE the underscore.

2. Restart and resume. Start the server again. Call /resume with the runId you copied from the file name. 

dotnet run -- --environment Testing
curl -s -X POST "http://localhost:8124/workflow/<runId>/resume" | jq '{status, report}'

Expected: status is "completed" and report is not empty. The events array starts with a "resumed" entry, for example "from checkpoint 1 of run <runId>". There is no "plan" executor in the resumed events. The plan step was already saved in the checkpoint, so resume skips it and continues from the probes onward.

Negative test — unknown run id returns 404, not a crash: 

curl -s -o /dev/null -w "%{http_code}" \
  -X POST "http://localhost:8124/workflow/notavalidrunid/resume"
# Must print: 404

What to watch for: if you kept the v1 instance-field version, the resume returns status: "failed" or a report with zero findings. The validator never reaches three items. Switch to v2 (ReadOrInitStateAsync and QueueStateUpdateAsync) and run again. The direct run and the stop-and-resume run must give the same report.

⚠️ Pitfalls
  • Resume returns empty or partial report, no error thrown → state is in an instance field, not the context. The executor re-constructs with the field empty; the fan-in count never reaches the threshold; the validator silently returns without sending a message. Move accumulators to ReadOrInitStateAsync + QueueStateUpdateAsync.
  • "Already owned by another runner" exception → the same Workflow object was passed to two concurrent RunStreamingAsync calls. Use a Func<Workflow> factory and call it once per run/resume.
  • Resume finds no checkpoints even though the run completed → CheckpointManager was not passed to RunStreamingAsync (the overload without a manager silently skips checkpointing). Confirm the constructor call: CheckpointManager.CreateJson(_store, null).
  • Resume loads the WRONG run's state → the store index is global across all runs. If you query it without filtering to the target runId and sorting by file write time, you may pick a checkpoint from a different run. Always filter by checkpoint.SessionId == runId before selecting the latest.
  • An instance field passes every single-process test → this is the trap. A green CI run does not mean the code is safe on resume. The failure only happens when the process is stopped between supersteps. Every in-process test runs in one session, so it never hits this case.
  • Resume of a finished run gives no report → you stopped the server too late, so the only checkpoint on disk is the final one. Resume loads it, finds no remaining work, and returns no report. Stop at the first checkpoint file instead, so the resume still has the synthesis step left to run.
