Lesson 11 · D1 · Module D — Composition & orchestration

Weekly report: hand-built graph → builder sugar

★★ Haiku

What you'll learn

The weekly report needs three analysts to run at the same time, then one writer to combine their findings. The prebuilt builders AgentWorkflowBuilder.BuildConcurrent and BuildSequential do this in a few lines. But when they go wrong — the three analysts run one after another instead of in parallel, the wrong message comes back, or the trace shows no concurrency — you cannot fix them if they look like magic. So you build the report by hand first and see the exact graph the builders produce. Then you rewrite it with the builders, knowing they are just syntactic sugar over a fan-out, a fan-in barrier, and a sequential edge.

You build the report twice. In v1 you wire the fan-out, barrier, and summarizer node by hand using the raw WorkflowBuilder skills from B1–B3. Then in v2 you rewrite it with the prebuilt builders and see they emit the same graph you just wrote by hand. The hand-built v1 is shown only to reveal the graph the builders generate; you keep v2. Its job was to show you the graph underneath, so you can debug any orchestration shape later.

📘 Teach

Three new API surfaces in Module D:

  • AgentWorkflowBuilder.BuildConcurrent(agents) — fans all listed agents out in parallel as a single workflow superstep; the aggregated outputs flow to the next stage. Equivalent to a fan-out edge plus a fan-in barrier in the raw builder.
  • AgentWorkflowBuilder.BuildSequential(agents) — chains agents one after the next, each receiving the previous agent's output as its input. Equivalent to a series of direct edges.
  • workflow.AsAIAgent(name, description) — wraps any workflow as a single AIAgent. The caller sees one agent; the framework executes the full graph internally. This is concept #10 (workflow-as-agent) — it composes: you can nest workflow-agents inside larger workflows.

The data contract: each analyst receives the user prompt. Its output goes into the workflow transcript. The summarizer receives the aggregated transcript of all previous agents as its context — which is why the instruction "Do not call tools" is load-bearing for the summarizer: by the time it runs, the facts are already in the message history.

Build it

  1. Author the analyst instructions

    Each of the three analyst agents needs a focused prompt: one investigates cost, one security signals, one tooling health. They share a common contract — "no pleasantries, no questions back, your output feeds another agent" — so you enforce that in a shared constant and interpolate per-domain scope on top.

    The summarizer is different: it receives findings from all three analysts and must assemble a coherent markdown report without calling any tools. The Do not call tools guard is mandatory — without it the summarizer may try to gather its own data, doubling cost and producing an incoherent output.

    ℹ️ Cumulative state

    Instructions.SchemaDoc is a const string defined in Agents/Instructions.cs (introduced in A1). It embeds the ClickHouse table schema so every agent that uses it automatically gets up-to-date column knowledge. ModelTiers.Analyst(config) and ModelTiers.Reasoning(config) come from Agents/ModelTiers.cs introduced in A1 — it is already available; use it directly.

    namespace AiAgent.Agents;

public static class AnalystInstructions
{
    private const string AnalystCommon = $"""
        You are one specialist in a reporting pipeline. Investigate ONLY your domain
        using the SQL tools, then output your findings as a compact markdown section:
        headline numbers first, then 2-4 bullet observations. Mention anything unusual
        explicitly. No pleasantries, no questions back — your output feeds another agent.
        Run at most 4 queries.

        {Instructions.SchemaDoc}
        """;

    public const string Cost = $"""
        DOMAIN: cost & token economics for the requested time window.
        Investigate: spend per project FIRST (the fundamental access unit — scope to
        one project if the request names one), total spend, spend per model, most
        expensive sessions, cache-read vs input token ratio (cache economics), spend trend vs the
        previous window of the same length.

        {AnalystCommon}
        """;

    public const string Security = $"""
        DOMAIN: security signals for the requested time window.
        Investigate: credential_exposures (which files, which categories),
        blocked_tools (what was denied, FINAL + completed=0), file deletions in
        file_mutations, and unusual domains in websites_visited.

        {AnalystCommon}
        """;

    public const string Tooling = $"""
        DOMAIN: tooling health for the requested time window.
        Investigate: tool call volumes and failure rates (event tool_result,
        success != 'true'), slowest tools by avg duration_ms, compaction_events
        frequency (a long/expensive-session smell), and subagent usage if present.

        {AnalystCommon}
        """;

    public const string Summarizer = """
        You are the report writer at the end of a pipeline. You receive findings from
        three specialist analysts: cost, security, and tooling. Produce ONE coherent
        report in markdown:

        # Claude Code Report
        ## Highlights        (3-5 bullets, the things a team lead must know)
        ## Cost              (condensed from the cost analyst)
        ## Security          (condensed from the security analyst)
        ## Tooling           (condensed from the tooling analyst)
        ## Anomalies & Recommendations   (anything unusual + 1-3 concrete suggestions)

        Keep numbers exact as given by the analysts. Do not invent data. Do not call tools.
        """;
}

  2. v1 — hand-build the graph (conceptual sketch)

    Using only the raw WorkflowBuilder from B1, you can build this pipeline by hand. The shape is: three analyst executor-nodes fanned out from a single start message; a fan-in barrier waits for all three; the aggregated output feeds a summarizer executor-node. The tabs below contrast the two versions.

    ⚠️ DO NOT COMPILE — illustrative pseudocode only

    The v1 snippet below uses ReportRequest, AnalystFindings, AggregatedFindings, and WorkflowBuilder.StartNodeName — these types do not exist in MAF and will produce compile errors. This is a conceptual sketch to show the graph shape that BuildConcurrent / BuildSequential generate internally. Only the v2 tab (ReportWorkflow.cs) is real code. 

    // v1: ILLUSTRATIVE PSEUDOCODE — do NOT compile.
// These types (ReportRequest, AnalystFindings, AggregatedFindings,
// WorkflowBuilder.StartNodeName) do not exist in MAF.
// Purpose: show the graph shape that BuildConcurrent / BuildSequential
// produce internally — once you understand the shape, use the v2 form.

var builder = new WorkflowBuilder();

// Three analyst agent-nodes
builder.AddNode<ReportRequest, AnalystFindings>("CostAnalyst",
    async (msg, ctx, ct) =>
    {
        var result = await costAnalyst.RunAsync(msg.Prompt, ct);
        return new AnalystFindings("CostAnalyst", result.Text);
    });

builder.AddNode<ReportRequest, AnalystFindings>("SecurityAnalyst",
    async (msg, ctx, ct) =>
    {
        var result = await securityAnalyst.RunAsync(msg.Prompt, ct);
        return new AnalystFindings("SecurityAnalyst", result.Text);
    });

builder.AddNode<ReportRequest, AnalystFindings>("ToolingAnalyst",
    async (msg, ctx, ct) =>
    {
        var result = await toolingAnalyst.RunAsync(msg.Prompt, ct);
        return new AnalystFindings("ToolingAnalyst", result.Text);
    });

// Fan-out: one input message -> all three analyst nodes
builder.AddFanOutEdge<ReportRequest>(
    sourceNode: WorkflowBuilder.StartNodeName,
    targetNodes: ["CostAnalyst", "SecurityAnalyst", "ToolingAnalyst"],
    partitioner: (msg, idx) => msg);   // same prompt to each

// Fan-in barrier: all three findings -> summarizer
builder.AddFanInEdge<AnalystFindings, AggregatedFindings>(
    sourceNodes: ["CostAnalyst", "SecurityAnalyst", "ToolingAnalyst"],
    targetNode: "Summarizer",
    aggregator: findings => new AggregatedFindings(findings));

builder.AddNode<AggregatedFindings, string>("Summarizer",
    async (msg, ctx, ct) =>
    {
        var context = string.Join("\n\n", msg.Items.Select(f => f.Content));
        var result = await summarizer.RunAsync(context, ct);
        return result.Text;
    });

builder.SetOutputNode("Summarizer");
var workflow = builder.Build();
// To expose as one agent: workflow.AsAIAgent("telemetry-report", "...")

    Now create the four agents and assemble the graph. The three analysts get the SQL tools; the summarizer gets tools: null. BuildConcurrent wraps the three analysts as a fan-out that runs them in parallel. AsAIAgent packs that fan-out into one agent named "Analysts". BuildSequential then puts that one agent before the summarizer, so the summarizer reads the aggregated analyst output. The outer AsAIAgent exposes the whole graph as one agent named "telemetry-report", which the /report endpoint resolves from DI. 

            var costAnalyst    = CreateAnalyst(client, analystModel,   "CostAnalyst",     AnalystInstructions.Cost,     sqlTools);
        var securityAnalyst = CreateAnalyst(client, analystModel,  "SecurityAnalyst",  AnalystInstructions.Security, sqlTools);
        var toolingAnalyst  = CreateAnalyst(client, analystModel,  "ToolingAnalyst",   AnalystInstructions.Tooling,  sqlTools);
        var summarizer      = CreateAnalyst(client, reasoningModel, "Summarizer",       AnalystInstructions.Summarizer, tools: null);

        var analystsWorkflow = AgentWorkflowBuilder.BuildConcurrent(
            [costAnalyst, securityAnalyst, toolingAnalyst]);

        var analystsAgent = analystsWorkflow.AsAIAgent(
            name: "Analysts",
            description: "Runs cost, security and tooling analysts concurrently.");

        var reportWorkflow = AgentWorkflowBuilder.BuildSequential([analystsAgent, summarizer]);

        return reportWorkflow.AsAIAgent(
            name: "telemetry-report",
            description: "Produces a Claude Code telemetry report for the requested window.");
    }

    Last, the helper that builds each analyst. It wraps the agent with UseOpenTelemetry so each analyst emits its own invoke_agent span. These spans let the trace timeline show the three analysts overlapping, which is the proof that they ran in parallel. AgentFactory.OtelSourceName comes from Agents/AgentFactory.cs (introduced in C2) and is already available. 

        private static AIAgent CreateAnalyst(
        IAnthropicClient client, string model, string name, string instructions, List<AITool>? tools)
    {
        var agent = client.AsAIAgent(model: model, instructions: instructions, name: name, tools: tools);

        return agent.AsBuilder()
            .UseOpenTelemetry(AgentFactory.OtelSourceName)
            .Build();
    }
}
    ℹ️

    Why nest two AsAIAgent calls? The inner call wraps the concurrent fan-out as a single unit named "Analysts". The outer BuildSequential then treats that whole concurrent block as one stage before the summarizer. This two-level nesting — concurrent inside sequential — is the idiomatic MAF way to express "all of these in parallel, then this one."

  3. Wire a shared runner to avoid duplicated invocation logic

    Both the /report endpoint and the menu registry in D2 invoke the same workflow agent. Rather than repeat the "take the last message, collect author names" logic in two places, extract it into one static helper.

    Running a workflow agent returns the full transcript, not one string. The helper reads two things out of it. The deliverable is the last non-empty message — the summarizer's report; earlier messages are the analyst findings. The AgentsInvolved list collects the distinct author names. The /report endpoint returns AgentsInvolved in its JSON so the verify step can confirm all four agents ran.

    Agents/ReportRunner.cs 
    using Microsoft.Agents.AI;

namespace AiAgent.Agents;

public static class ReportRunner
{
    public static async Task<(string Report, List<string> AgentsInvolved)> RunAsync(
        AIAgent reportAgent, string window, CancellationToken ct)
    {
        var response = await reportAgent.RunAsync(
            $"Produce the report for {window}.", cancellationToken: ct);

        var lastMessage = response.Messages.LastOrDefault(m => !string.IsNullOrWhiteSpace(m.Text));
        var agentsInvolved = response.Messages
            .Select(m => m.AuthorName)
            .Where(author => !string.IsNullOrEmpty(author))
            .Distinct()
            .Select(author => author!)
            .ToList();

        return (lastMessage?.Text ?? response.Text, agentsInvolved);
    }
}

  4. Register the workflow agent and expose the endpoints

    Register the workflow agent as a keyed singleton — keyed because the DI container also holds the main DataAnalyst as an unkeyed AIAgent, and the two must not collide. The /report endpoint returns JSON; the /report/stream endpoint emits SSE with per-agent step events so the client can render progress as each analyst finishes.

    ℹ️ Already available

    [FromKeyedServices] is in the Microsoft.Extensions.DependencyInjection namespace, which a minimal-API host already includes — no extra using needed. SseEvent is the static helper introduced in A2 and is already in Program.cs. Each chunk below names where it goes.

    First, the DI registration. It goes in the DI block, before var app = builder.Build();. The key "report" keeps this agent separate from the unkeyed DataAnalyst. The endpoints below resolve it with [FromKeyedServices("report")], so the key string must match in both places.

    Program.cs (excerpts) 
    builder.Services.AddKeyedSingleton<AIAgent>("report", (sp, _) => ReportWorkflow.Create(
    sp.GetRequiredService<IConfiguration>(),
    sp.GetRequiredService<SchemaTools>(),
    sp.GetRequiredService<AnalysisTools>()));

    Next, the /report endpoint. It goes after var app = builder.Build();. It calls ReportRunner and returns the report plus the agentsInvolved list as JSON. 

    app.MapPost("/report", async (ReportRequest? request,
    [FromKeyedServices("report")] AIAgent reportAgent, CancellationToken ct) =>
{
    var window = string.IsNullOrWhiteSpace(request?.Window) ? "the last 7 days" : request.Window;
    var (report, agentsInvolved) = await ReportRunner.RunAsync(reportAgent, window, ct);
    return Results.Ok(new { report, agentsInvolved });
});

    Then the /report/stream endpoint. It streams the run instead of waiting for the end. Each time the author name changes, it emits an agent_step event. The client reads these events to show which analyst is running. The verify step uses the order of these events to prove the analysts ran in parallel. 

    app.MapPost("/report/stream", async (ReportRequest? request, HttpContext context,
    [FromKeyedServices("report")] AIAgent reportAgent, CancellationToken ct) =>
{
    var window  = string.IsNullOrWhiteSpace(request?.Window) ? "the last 7 days" : request!.Window;

    context.Response.Headers.ContentType = "text/event-stream";
    context.Response.Headers.CacheControl = "no-cache";

    try
    {
        string? currentAgent = null;
        await foreach (var update in reportAgent.RunStreamingAsync(
            $"Produce the report for {window}.", cancellationToken: ct))
        {
            if (!string.IsNullOrEmpty(update.AuthorName) && update.AuthorName != currentAgent)
            {
                currentAgent = update.AuthorName;
                await SseEvent.WriteAsync(context.Response, "agent_step", new { agent = currentAgent }, ct);
            }
            if (!string.IsNullOrEmpty(update.Text))
                await SseEvent.WriteAsync(context.Response, "token",
                    new { agent = currentAgent, text = update.Text }, ct);
        }
        await SseEvent.WriteAsync(context.Response, "done", new { }, ct);
    }
    catch (Exception ex)
    {
        await SseEvent.WriteAsync(context.Response, "error", new { message = ex.Message }, ct);
    }
});

    Last, declare the request record at file scope, after app.Run();, with the other request records: internal sealed record ReportRequest(string? Window);

Why the reveal matters

The v1 graph and the v2 builder call produce the same runtime execution: three concurrent superstep nodes followed by one sequential node. The difference is purely in how much bookkeeping you own. The raw builder lets you customize partitioners, edge predicates, and custom executors — as you will in B1–B3 and again in F2's investigation pipeline. The high-level builders buy you terseness at the cost of control. Now that you have seen both, you can choose the right level for each situation.

# BEFORE the agent_step event for Summarizer.
# The three analyst steps may appear in any order relative to each other (they ran in parallel).
# The Summarizer agent_step MUST be the last one before "done".

Check 3 — v1 and v2 produce equivalent structure:

If you built v1 locally before replacing it: both should return a markdown document with ## Cost, ## Security, ## Tooling, and ## Highlights sections. The exact wording will differ (LLM output), but the section headings prove the same pipeline shape ran.

Negative test — fan-out degraded to sequential:

If the three agent_step events for the analysts appear in strict sequence (one done event each, no interleaving timestamps), the concurrent fan-out is not working — the agents are being run one after another. Verify that BuildConcurrent was applied to all three analysts before wrapping them with AsAIAgent, not BuildSequential.

⚠️ Pitfalls
  • Analysts respond conversationally instead of reporting → the prompt contract "your output feeds another agent" is missing. Without it, the model asks clarifying questions or adds pleasantries, which pollutes the summarizer's context and produces a confused report. The AnalystCommon constant enforces this.
  • Summarizer calls SQL tools and invents data → the summarizer has tools: null in CreateAnalyst. If tools are accidentally passed, the summarizer will sometimes try to gather its own numbers — at double the cost and with inconsistent grounding. Also: without "Do not call tools" in its instructions, even a tool-less summarizer may claim it cannot answer because it "has no access to data."
  • Keyed registration not found — DI throws at startup → the endpoint uses [FromKeyedServices("report")]; if the registration used a different key string (or was registered without a key), the app crashes on first request, not at startup. Verify the key string matches exactly in both AddKeyedSingleton and the endpoint attribute.
  • Wrong message taken from the transcript → RunAsync on a workflow agent returns the full conversation transcript. Taking response.Text gives only the last update, which may be incomplete. ReportRunner uses response.Messages.LastOrDefault(m => !string.IsNullOrWhiteSpace(m.Text)) — the last non-empty message — which is reliably the Summarizer's output.
  • OTel spans show no concurrency → each analyst needs its own UseOpenTelemetry call (done in CreateAnalyst). Without it, analysts share the default span context and the trace timeline collapses into a single sequential-looking line even if the graph ran concurrently.
