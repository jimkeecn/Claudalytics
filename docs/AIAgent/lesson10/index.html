Lesson 10 · C3 · Module C — The product

Tool-level human approval

★★ Haiku

What you'll learn

One tool in this agent is dangerous. It can scan the whole otel_logs table with no time filter. That query reads millions of rows and can run for minutes. It costs real money on a request the user may never have meant to run. If the agent fires it on its own, you only find out after the bill. C3 puts that one tool behind a human approval gate. When the model picks the dangerous tool, the run pauses and waits. No SQL touches the database until a person approves it.

The mechanism is a wrapper. You register the tool inside ApprovalRequiredAIFunction instead of as a plain function. When the model selects the wrapped tool, the framework does not run it. It emits a ToolApprovalRequestContent and pauses the run. Your server stores that pending approval under a generated id and returns kind: "approval" to the caller. A second endpoint, POST /chat/approve, resolves the decision. Approve replays the tool call into the same session. Deny injects a refusal and the agent answers without running anything. Each approval is used exactly once. A second use returns 404. The gate lives at the single tool, not at the workflow level. The workflow-level gate is F2's RequestPort.

📘 Teach

The three parts of tool-level HITL

MAF builds tool approval from three pieces that work together.

  • ApprovalRequiredAIFunction — the wrapper you pass instead of a raw AIFunction. When the model selects the wrapped tool, the framework emits a ToolApprovalRequestContent and pauses the run. It does not run the function.
  • ToolApprovalRequestContent — the pause signal. It holds the original ToolCall, which is the function call the model wanted to make. It also has a CreateResponse(approved, reason) method. You use that method to build the reply that resumes the run.
  • agent.RunAsync(reply, session) — how you send the decision back. You call RunAsync with one ChatMessage(ChatRole.User, [pending.Request.CreateResponse(approved, reason)]) on the same session. If approved, the framework runs the tool and continues. If denied, it feeds the refusal reason and the agent answers without running the tool.

You need no new library package. Everything here is in the packages C2 already added. The MAF chat-client layer enforces the whole contract. It intercepts the tool call before it reaches your code.

Why an unbounded scan needs a gate

In C1 you added SqlValidator. It requires a Timestamp filter on every otel_logs query, because otel_logs is the big table. That is the right default. A full scan of a large log table is expensive and usually not needed. But sometimes a user really does need an all-time total. An example is "which project has spent the most since the beginning?". The answer is a second tool named RunUnboundedSql. It skips the time-filter rule. To stay safe, it sits behind a human decision. The model can propose it. A human must approve it.

Build it

  1. Add the unbounded SQL tool to SchemaTools

    This is the tool the gate protects. The agent reads its description and calls it only when a question needs a full scan. Add it inside the existing public sealed class SchemaTools(ClickHouseClient clickHouse), next to RunSql. No new usings are needed.

    RunUnboundedSql is the same as RunSql with one change. It calls SqlValidator.Validate(query, requireTimeFilter: false), which turns off the time-filter rule. Every other guard still runs: read-only verbs, single statement, and the auto-added limit.

    Tools/SchemaTools.cs 
    [Description("Executes a read-only SELECT WITHOUT the otel_logs time-filter requirement. "
           + "Use ONLY when a full-table scan is genuinely needed. "
           + "Every call requires explicit human approval before it runs.")]
public async Task<string> RunUnboundedSql(
    [Description("The SELECT (or WITH ... SELECT) query to execute, "
               + "may scan otel_logs without a Timestamp filter.")] string query)
{
    try
    {
        var sql = SqlValidator.Validate(query, requireTimeFilter: false);
        return await clickHouse.QueryAsync(sql);
    }
    catch (Exception ex)
    {
        return $"QUERY FAILED: {ex.Message}";
    }
}

    You do not change SqlValidator here. Its Validate method already takes the requireTimeFilter flag from C1. You only call it with false. The read-only regex guards are the same ones both tools use.

    For reference, the Validate method is shown below as it stands after C1. The class is public static partial class SqlValidator with [GeneratedRegex] partial methods (SelectOrWith, DeniedKeywords, HasLimit, TargetsOtelLogs). Keep it partial and keep those methods as they are. Nothing in this snippet is new; it is here so you can see what the false path skips.

    Tools/SqlValidator.cs — Validate method (unchanged from C1) 
    public static string Validate(string query, bool requireTimeFilter = true)
{
    var sql = query.Trim().TrimEnd(';').Trim();

    if (sql.Contains(';'))
        throw new ArgumentException("Only a single SQL statement is allowed.");

    if (!SelectOrWith().IsMatch(sql))
        throw new ArgumentException("Only SELECT (or WITH ... SELECT) queries are allowed.");

    var denied = DeniedKeywords().Match(sql);
    if (denied.Success)
        throw new ArgumentException($"Keyword '{denied.Value}' is not allowed. This tool is read-only; FORMAT is appended automatically.");

    if (requireTimeFilter && TargetsOtelLogs().IsMatch(sql)
        && !sql.Contains("Timestamp", StringComparison.OrdinalIgnoreCase))
        throw new ArgumentException(
            "Queries against otel_logs must filter on Timestamp (it is a large table). " +
            "Add e.g. WHERE Timestamp >= now() - INTERVAL 1 DAY.");

    if (!HasLimit().IsMatch(sql))
        sql += $" LIMIT {DefaultLimit}";

    return sql;
}

  3. Store pending approvals in a shared dictionary

    The pause and the decision happen in two separate HTTP requests. Between them, the server has to remember the paused approval. When a ToolApprovalRequestContent appears in the agent's response, you save it here. The /chat/approve endpoint in Step 5 reads it back by id. Register a singleton ConcurrentDictionary<string, PendingApproval> in DI. using System.Collections.Concurrent; is already present from A2.

    Add the AddSingleton call in the DI block of Program.cs, after the existing ConcurrentDictionary<string, AgentSession> registration. The PendingApproval record is file-scoped. Place it after app.Run();, next to the other record declarations (ChatRequest, ApproveRequest, and so on).

    Program.cs — DI block (before app.Build()) 
    builder.Services.AddSingleton<ConcurrentDictionary<string, PendingApproval>>();
    Program.cs — file scope after app.Run() 
    internal sealed record PendingApproval(
    string SessionId,
    AgentSession Session,
    ToolApprovalRequestContent Request);

    The record carries the AgentSession on purpose. The approval decision must continue the same conversation. If you drop the session here, the agent resumes with no history and no context, and the answer is wrong. The session is the MAF multi-turn memory unit introduced in A2.

  4. Detect the pause signal in the chat response builder

    This is the read side of the pause. After each agent.RunAsync call, you scan the response for a ToolApprovalRequestContent. If one is there, the run is paused, so you store the approval and tell the caller to ask a human. If none is there, the response is a normal answer. The caller is the front end, which switches on kind: "approval" shows an approve or deny prompt, "answer" shows the reply as before.

    ToChatResponse and StoreApproval are file-scope static helper methods. Place them after app.Run();, next to GetOrCreateSessionAsync (already present from A2). Both the /chat endpoint and the /chat/approve endpoint in Step 5 call them.

    The first method, ToChatResponse, flattens the response into its content items. It collects any tool calls for display. It then looks for the first ToolApprovalRequestContent. If it finds one, it calls StoreApproval to save the pending approval and gets back an id. The returned object sets kind to "approval" when an approval request was found, and "answer" otherwise.

    Program.cs — file scope after app.Run() 
    static object ToChatResponse(string sessionId, AgentSession session, AgentResponse response,
    ConcurrentDictionary<string, PendingApproval> approvals)
{
    var contents = response.Messages.SelectMany(message => message.Contents).ToList();

    var toolCalls = contents.OfType<FunctionCallContent>()
        .Select(call => new { name = call.Name, arguments = (object?)call.Arguments })
        .ToList();

    var approvalRequest = contents.OfType<ToolApprovalRequestContent>()
        .Select(approval =>
        {
            var call = approval.ToolCall as FunctionCallContent;
            return new
            {
                approvalId = StoreApproval(approvals, sessionId, session, approval),
                toolName = call?.Name,
                arguments = call?.Arguments,
            };
        })
        .FirstOrDefault();

    return new
    {
        sessionId,
        kind = approvalRequest is null ? "answer" : "approval",
        answer = response.Text,
        menu = (object?)null,
        toolCalls,
        approvalRequest,
    };
}

    The second method, StoreApproval, is the write side. It makes a new id, saves the PendingApproval under that id in the shared dictionary, and returns the id. That id is what the front end later sends to /chat/approve.

    Program.cs — file scope after app.Run() 
    static string StoreApproval(
    ConcurrentDictionary<string, PendingApproval> approvals,
    string sessionId, AgentSession session, ToolApprovalRequestContent request)
{
    var approvalId = Guid.NewGuid().ToString("N");
    approvals[approvalId] = new PendingApproval(sessionId, session, request);
    return approvalId;
}

  5. Return the approval shape from /chat

    The /chat endpoint from A2 returns only { sessionId, answer }, so when a run pauses for approval the caller never sees an approvalId and cannot show an approve prompt. Inject the approvals dictionary and return ToChatResponse instead, so a paused run comes back as kind: "approval" with the stored id.

    Program.cs — replace the /chat endpoint 
    app.MapPost("/chat", async (ChatRequest request, AIAgent agent,
    ConcurrentDictionary<string, AgentSession> sessions,
    ConcurrentDictionary<string, PendingApproval> approvals,
    CancellationToken ct) =>
{
    if (string.IsNullOrWhiteSpace(request.Message))
        return Results.BadRequest(new { error = "message is required" });

    var (sessionId, session) = await GetOrCreateSessionAsync(
        request.SessionId, agent, sessions, ct);

    var response = await agent.RunAsync(request.Message, session, cancellationToken: ct);

    return Results.Ok(ToChatResponse(sessionId, session, response, approvals));
});

  6. Add the POST /chat/approve endpoint

    This endpoint is the write side of the decision. It reads the pending approval that Step 4 stored. It removes the entry with TryRemove, so the id can be used only once. It then builds a reply with CreateResponse and calls RunAsync on the same session to resume the paused run. The session comes from pending.Session, so the agent keeps the full conversation.

    Add the app.MapPost call in the route block of Program.cs, after the existing /chat endpoint. The ApproveRequest record is file-scoped. Place it after app.Run();, next to ChatRequest and the other record declarations.

    Program.cs — route block 
    app.MapPost("/chat/approve", async (ApproveRequest request, AIAgent agent,
    ConcurrentDictionary<string, PendingApproval> approvals, CancellationToken ct) =>
{
    if (string.IsNullOrWhiteSpace(request.ApprovalId)
        || !approvals.TryRemove(request.ApprovalId, out var pending))
        return Results.NotFound(new { error = "unknown or already-handled approvalId" });

    var reply = new ChatMessage(ChatRole.User,
        [pending.Request.CreateResponse(request.Approved, request.Reason ?? "")]);

    var response = await agent.RunAsync(reply, pending.Session, cancellationToken: ct);
    return Results.Ok(ToChatResponse(pending.SessionId, pending.Session, response, approvals));
});
    Program.cs — file scope after app.Run() 
    internal sealed record ApproveRequest(string ApprovalId, bool Approved, string? Reason);

    TryRemove is what makes an approval one-time. The dictionary is the approval registry. The moment the id is removed, it is gone. A second call with the same id finds nothing and returns the NotFound branch.

    app.MapPost("/chat/stream", async (HttpContext context, AIAgent agent,
    ConcurrentDictionary<string, AgentSession> sessions,
    ConcurrentDictionary<string, PendingApproval> approvals, CancellationToken ct) =>
    Program.cs — /chat/stream await foreach (replace existing body) 
    await foreach (var update in agent.RunStreamingAsync(request.Message, session, cancellationToken: ct))
{
    foreach (var content in update.Contents)
    {
        switch (content)
        {
            case FunctionCallContent call:
                await SseEvent.WriteAsync(context.Response, "tool_call",
                    new { name = call.Name, arguments = call.Arguments }, ct);
                break;
            case ToolApprovalRequestContent approval:
                var approvalId = StoreApproval(approvals, sessionId, session, approval);
                var approvalCall = approval.ToolCall as FunctionCallContent;
                await SseEvent.WriteAsync(context.Response, "approval_request",
                    new { approvalId, toolName = approvalCall?.Name, arguments = approvalCall?.Arguments }, ct);
                break;
        }
    }

    if (!string.IsNullOrEmpty(update.Text))
        await SseEvent.WriteAsync(context.Response, "token", new { text = update.Text }, ct);
}

How the two-endpoint flow works end-to-end

The whole interaction is two HTTP calls.

  1. First call — POST /chat with a question that needs an unbounded scan. The model picks RunUnboundedSql. The framework sees the ApprovalRequiredAIFunction wrapper and pauses. It emits a ToolApprovalRequestContent. Your server stores it and returns { kind: "approval", approvalRequest: { approvalId: "...", toolName: "RunUnboundedSql", arguments: {...} } }. The run is suspended. No SQL has run yet.
  2. Second call — POST /chat/approve with the approvalId and approved: true/false. The endpoint removes the pending entry, so the id is now used up. It calls CreateResponse and resumes RunAsync on the same session. If approved, the tool runs and the agent answers. If denied, the framework feeds a refusal and the agent answers without running anything.
🔧 Note

The approval registry lives in process memory. After a server restart, pending approvals are gone, and the client gets a 404. For production you would save the approval queue to a backing store such as a database or Redis. The in-memory approach is fine for this lesson. Durability across restarts is the subject of F2's production checkpoints.

Verify

✅ Gate — do not advance until green

Step 1 — trigger the approval request.

curl -s -X POST http://localhost:5200/chat \
  -H "Content-Type: application/json" \
  -d '{"message": "Across the entire otel_logs history with no time filter at all, what is the timestamp of the very first event ever recorded?"}' \
  | jq '{kind, approvalRequest}'

Expected output — the run pauses, no SQL has run yet:

{
  "kind": "approval",
  "approvalRequest": {
    "approvalId": "<some-id>",
    "toolName": "RunUnboundedSql",
    "arguments": { "query": "SELECT ..." }
  }
}

Step 2 — approve and verify execution.

curl -s -X POST http://localhost:5200/chat/approve \
  -H "Content-Type: application/json" \
  -d '{"approvalId": "<some-id>", "approved": true}' \
  | jq '{kind, answer}'

Expected: kind: "answer" with a substantive reply giving the timestamp of the earliest event in otel_logs.

Step 3 — deny path.

Send a fresh /chat question that triggers the approval, then deny it: 

curl -s -X POST http://localhost:5200/chat/approve \
  -H "Content-Type: application/json" \
  -d '{"approvalId": "<new-id>", "approved": false, "reason": "too expensive"}' \
  | jq '{kind, answer}'

Expected: kind: "answer", and the answer text gracefully acknowledges the refusal (e.g., "I wasn't able to run the full scan — the request was denied"). The agent does not crash or return an empty reply.

Negative test — second use of a consumed id returns 404. 

curl -s -X POST http://localhost:5200/chat/approve \
  -H "Content-Type: application/json" \
  -d '{"approvalId": "<the-id-you-already-used>", "approved": true}' \
  | jq .error

Expected: "unknown or already-handled approvalId" with HTTP 404. This confirms approvals are one-shot.

Negative test — bogus id is also 404.

curl -s -X POST http://localhost:5200/chat/approve \
  -H "Content-Type: application/json" \
  -d '{"approvalId": "doesnotexist", "approved": true}' \
  | jq .error

Expected: same 404 error body.

⚠️ Pitfalls
  • Approval stored without its session → the agent resumes with no conversation history, so the answer has no grounding or is wrong. Always store the AgentSession in the pending approval record.
  • kind: "answer" but the answer is empty or "I cannot", even though you approved → the approval was replayed on the wrong session, a new one. Confirm you take the session from pending.Session, not from GetOrCreateSessionAsync at decision time.
  • Second use of an approval id does not return 404 → you saved the approval with a plain dictionary set (approvals[id] = ...) inside the approve endpoint, instead of removing it with TryRemove. The approval stays and can be reused.
  • Normal tool calls stop working after the wrapper → you wrapped a tool that should not be gated. Only RunUnboundedSql should be wrapped. Every other tool stays a plain AIFunctionFactory.Create call.
  • The agent never selects RunUnboundedSql → the tool name and description do not set it apart from RunSql. The model will pick the simpler tool. Make the description say "WITHOUT the time-filter requirement" and "full-table scan", so the model knows when to use it.
