Lesson 01 · A1 · Module A — Hello agent

Your first agent + a function tool

★ Haiku

What you'll learn

Ask a raw LLM "what tables are in my telemetry?" and it will make up column names with full confidence, because it has never seen your ClickHouse schema. The fix is an agent: an LLM wired into a tool-call loop, where you hand it one real C# method that returns the true schema and let it call that method before it answers.

In the Microsoft Agent Framework you give the agent a name, a system instruction, a model, and a list of callable functions. MAF then handles the back-and-forth between the model and your code until the model stops asking for tool results. This lesson uses three API surfaces to do that — ChatClientAgentOptions, AIFunctionFactory.Create, and client.AsAIAgent. It also sets up the Testing environment launch step that every later lesson uses as a gate check.

📘 Teach

Mental model: an agent is an LLM in a tool-call loop with configurable memory. Three MAF API surfaces do the wiring:

  • ChatClientAgentOptions — holds the name, description, ChatOptions.Instructions (the system prompt), ChatOptions.ModelId, and the Tools list. Every option lives in one object. The agent's identity and its tools are declared together.
  • AIFunctionFactory.Create(method) — turns an ordinary C# instance method into a tool the model can call. The [Description("…")] attributes on the method and its parameters become the tool schema the LLM receives. You do not hand-write any schema.
  • IAnthropicClient.AsAIAgent(options) — builds the AIAgent from the provider client and the options. In A3 you will chain .AsBuilder().UseOpenTelemetry(…).Build() here. For now the plain call is enough.

agent.RunAsync(prompt) runs one full tool-call loop and returns an AgentResponse. The .Text property holds the final model reply. .Messages holds the full transcript, including the tool calls the model made on the way.

Build it

  1. Understand model tiering from the start

    If you hard-code "claude-sonnet-4-6" in your agent, every test run bills you at Sonnet rates and you must hunt through code to switch models. D3 treats hard-coded model ids as an anti-pattern for exactly this reason. So the project reads model names from configuration through one static helper from day one.

    Agents/ModelTiers.cs is a leaf file with no dependencies. Each method reads one tier name from IConfiguration and falls back to a default if the config key is missing. IConfiguration is available through implicit usings (Microsoft.NET.Sdk.Web), so no extra using directive is needed. AgentFactory (step 4) calls ModelTiers.Analyst(config) to pick the agent's model.

    Agents/ModelTiers.cs 
    namespace AiAgent.Agents;

public static class ModelTiers
{
    public static string Light(IConfiguration config) => config["Models:Light"] ?? "claude-haiku-4-5";

    public static string Analyst(IConfiguration config) => config["Models:Analyst"] ?? "claude-sonnet-4-6";

    public static string Reasoning(IConfiguration config) => config["Models:Reasoning"] ?? "claude-opus-4-8";
}

    The appsettings.Testing.json shown in the Setup callout above pins all three tiers to Haiku. So when you launch with --environment Testing, every gate runs on the cheapest model.

  2. Create the system prompt constants

    The agent needs two pieces of text: a system prompt that tells it what its job is, and a schema document it can return when asked. Both live in one leaf file so later lessons have a single place to extend.

    Agents/Instructions.cs has no dependencies on other files in this lesson. It provides Instructions.System, which AgentFactory (step 4) reads as the system prompt, and Instructions.SchemaDoc, which SchemaTools.GetSchema (step 3) returns to the model. Write a skeleton now. The full schema text is filled in later in C1, but the constant must exist and be non-empty for A1 to compile.

    Agents/Instructions.cs (A1 skeleton) 
    namespace AiAgent.Agents;

public static class Instructions
{
    public const string SchemaDoc = """
        # ClickHouse schema placeholder
        Fill in with actual schema in C1 (lesson08).
        """;

    public const string System = $"""
        You are the Claudalytics analyst. Answer questions about Claude Code
        telemetry stored in ClickHouse.

        {SchemaDoc}
        """;
}

  3. Write the function tool

    This is the method that fixes the made-up-column-names problem from the intro. When the model needs to know the real schema, it calls this tool and gets the true answer instead of guessing.

    Tools/SchemaTools.cs holds the single function tool the agent will call in A1. It depends only on Instructions.SchemaDoc (step 2), which is already present. AgentFactory (step 4) registers this method as a tool. ClickHouse queries are added later in B1; here you only need the schema reference. A tool is a plain C# instance method with a [Description] attribute. The model reads that description as the tool schema, so make it precise. State what the tool returns and when to use it.

    Tools/SchemaTools.cs 
    using System.ComponentModel;
using AiAgent.Agents;

namespace AiAgent.Tools;

public sealed class SchemaTools
{
    [Description("Returns the full ClickHouse schema reference: tables, columns, attribute extraction idioms and example queries.")]
    public string GetSchema() => Instructions.SchemaDoc;
}

  4. Wire the Anthropic client and create the agent

    This step is where the three leaf files come together into an actual agent. The factory injects SchemaTools (step 3), reads the model tier from ModelTiers (step 1), and passes Instructions.System (step 2) as the system prompt. Program.cs (step 5) calls this factory once at startup to build the singleton agent.

    The factory is trimmed to what A1 needs. It grows in later lessons: compaction in E2, context provider in E1, OTel middleware in A3, and agent-as-tool in F1. Edit this file in those lessons; do not regenerate it.

    Agents/AgentFactory.cs 
    using AiAgent.Tools;
using Anthropic;
using Microsoft.Agents.AI;
using Microsoft.Extensions.AI;

namespace AiAgent.Agents;

public static class AgentFactory
{
    public static AIAgent Create(
        IConfiguration config,
        SchemaTools tools,
        ILoggerFactory loggerFactory)
    {
        var apiKey = config["ANTHROPIC_API_KEY"]
            ?? throw new InvalidOperationException("ANTHROPIC_API_KEY is not set.");

        IAnthropicClient client = new AnthropicClient { ApiKey = apiKey };

        var options = new ChatClientAgentOptions
        {
            Name = "claudalytics-analyst",
            Description = "Answers natural-language questions over Claudalytics telemetry in ClickHouse.",
            ChatOptions = new ChatOptions
            {
                ModelId = ModelTiers.Analyst(config),
                Instructions = Instructions.System,
                Tools =
                [
                    AIFunctionFactory.Create(tools.GetSchema),
                ],
            },
        };

        return client.AsAIAgent(options, loggerFactory: loggerFactory);
    }
}

    All three leaf files are now in place — the project builds cleanly after pasting this step.

  5. Register the agent and expose a /chat endpoint

    The factory and tool from the previous steps are useless until something runs them. Program.cs registers the AIAgent as a singleton and maps a POST endpoint that callers hit to ask questions. For A1 the endpoint stays minimal: no session store yet (that is A2), and no streaming (that is A3).

    First, the usings and the DI registrations. These go at the top of Program.cs and just before var app = builder.Build();. The AddSingleton<AIAgent> call asks DI for SchemaTools and passes it to AgentFactory.Create (step 4), so the agent is built once and reused for every request. The Microsoft.Extensions.AI using is needed for FunctionCallContent, which the endpoint reads in the next chunk.

    Program.cs (usings + DI — before builder.Build()) 
    using AiAgent.Agents;
using AiAgent.Tools;
using Microsoft.Agents.AI;
using Microsoft.Extensions.AI;

builder.Services.AddSingleton<SchemaTools>();
builder.Services.AddSingleton<AIAgent>(sp => AgentFactory.Create(
    sp.GetRequiredService<IConfiguration>(),
    sp.GetRequiredService<SchemaTools>(),
    sp.GetRequiredService<ILoggerFactory>()));

var app = builder.Build();

    Next, the endpoint. It goes after var app = builder.Build();. It calls agent.RunAsync to run one tool-call loop, then returns two fields. answer is the model's final text. toolCalls is the list of tools the model actually called, pulled out of the transcript by filtering response.Messages for FunctionCallContent. The next step adds the health endpoints alongside this one.

    Program.cs (/chat — after builder.Build()) 
    app.MapPost("/chat", async (ChatRequest request, AIAgent agent, CancellationToken ct) =>
{
    if (string.IsNullOrWhiteSpace(request.Message))
        return Results.BadRequest(new { error = "message is required" });

    var response = await agent.RunAsync(request.Message, cancellationToken: ct);
    return Results.Ok(new
    {
        answer = response.Text,
        toolCalls = response.Messages
            .SelectMany(m => m.Contents)
            .OfType<FunctionCallContent>()
            .Select(c => new { name = c.Name }),
    });
});

app.Run();

    Last, the request type. ChatRequest is a file-scope record, so it goes at the very bottom of the file, after app.Run();.

    Program.cs (record — after app.Run()) 
    internal sealed record ChatRequest(string Message);

    The /chat endpoint is now live. The toolCalls field is the A1 verification signal. A confident answer with an empty toolCalls list means the tool was not registered, or its description was too vague for the model to choose it. You will check this in the Verify gate.

  6. Add a smoke-test health endpoint

    Before you trust the /chat answers, you want a cheap way to confirm the model is reachable and the API key is valid. /healthz/llm sends one tiny prompt and returns the reply, so a failure here points at wiring, not at your prompt. The Verify gate below calls this endpoint first.

    These two endpoints go in Program.cs after var app = builder.Build();, next to /chat from step 5. /healthz is a plain liveness check; /healthz/llm is the LLM smoke test.

    Program.cs (healthz — after builder.Build()) 
    app.MapGet("/healthz", () => Results.Ok(new { status = "ok" }));

app.MapGet("/healthz/llm", async (AIAgent agent, CancellationToken ct) =>
{
    var response = await agent.RunAsync("Reply with the single word: ok", cancellationToken: ct);
    return Results.Ok(new { status = "ok", model_reply = response.Text });
});

Why tool descriptions matter

The model cannot read your code. It sees only the tool name and the description you wrote. When the description is thin, the model guesses, and it usually guesses wrong. The fix is always the same. Make the description say exactly when to use the tool and what it returns, not just what it is called.

Compare what the model sees for GetSchema with a precise vs a vague description:

  • Precise: "Returns the full ClickHouse schema reference: tables, columns, attribute extraction idioms and example queries." — the model knows to call this whenever it needs to write or validate a query.
  • Vague: "Gets schema info." — the model cannot tell whether this is relevant for query-writing, so it skips the tool and answers from its own (nonexistent) knowledge of your data, producing hallucinated column names.

A single tool with a precise description is more reliable than multiple tools with overlapping or thin descriptions. Add tools only when they are distinct in purpose — and make each description say both when to use it and what it returns.

Verify

✅ Gate — do not advance until green

Step 1 — environment check. Launch with the ritual: 

dotnet run -- --environment Testing

Confirm the console prints Hosting environment: Testing. If it says anything else, stop and fix the launch command.

Step 2 — smoke test the LLM path:

curl http://localhost:8124/healthz/llm

Expected: {"status":"ok","model_reply":"ok"}

Step 3 — ask a question that requires GetSchema: 

curl -s -X POST http://localhost:8124/chat \
  -H "Content-Type: application/json" \
  -d '{"message": "what tables are available in the schema?"}'

The response toolCalls array must be non-empty and contain get_schema. The answer must describe the schema contents, not generic placeholders.

Negative test — the hallucination check.

If you get a confident answer but toolCalls is empty, the model answered from its own "knowledge" (it has none about your schema). This means the tool is not registered or its description is too vague. Check that AIFunctionFactory.Create(tools.GetSchema) appears in the Tools array in your options, and that the method carries a [Description] attribute.

⚠️ Pitfalls
  • Console shows Hosting environment: Production → Missing -- separator. Run dotnet run -- --environment Testing, not dotnet run --environment Testing. Without the separator, dotnet treats --environment as its own flag and silently discards it.
  • Non-empty answer, empty toolCalls → Tool not registered. The method must appear in ChatOptions.Tools via AIFunctionFactory.Create. Check the array in AgentFactory.cs; a missing entry produces no compile error and no runtime warning — just a hallucinating model.
  • Model skips the tool and answers from its own knowledge → Vague [Description] attribute. The model cannot tell when the tool is relevant, so it guesses without calling it. Rewrite the description to say exactly what the tool returns and when to use it.
  • ANTHROPIC_API_KEY is not set at startup → The key is missing from appsettings.Local.json (the gitignored file). Never commit the key; the Local file is loaded last and overrides everything.
  • Tool method throws instead of returning an error string → An unhandled exception from a tool ends the RunAsync call with an exception, not a model-readable message. Always catch and return "QUERY FAILED: {ex.Message}" so the model can reason about the failure.
