第 07 课 · B4 · 模块 B — 图

能在进程死亡后存活的状态：检查点与恢复

★★★ 无需 LLM

你将学到什么

一次调查可能跑几分钟，发出很多 ClickHouse 查询（探针 probe），以后在 F2 还会停下来等人审批。如果进程崩溃或重启，你不想从零重来：重跑探针、 重付 LLM 费用、丢掉已经给过的审批。B4 让一次运行能在重启后从中断处继续。

执行器（executor）看起来是普通对象，所以容易把扇入结果放进字段。但进程重启后 字段会变空，结果就错了或为空。修复办法：状态不放自己的字段，放进工作流上下文（context）。 之后 FileSystemJsonCheckpointStore 会在每个超步（superstep）自动保存并恢复它。

📘 讲解

主要心智模型：上下文（context）是一次运行里唯一能持久保存的存储， 其他都是临时的。

  • ReadStateAsync<T>(key, scopeName?) — 读一个值。省略 scopeName 用私有作用域，传名字用共享作用域。
  • ReadOrInitStateAsync<T>(key, factory) — 读取，不存在就用默认值初始化（累加器首次为空时必需）。
  • QueueStateUpdateAsync(key, value, scopeName?) — 排队写入，超步边界原子应用并纳入检查点。
  • FileSystemJsonCheckpointStore(DirectoryInfo) — 把每个检查点存为 {runId}_{checkpointId}.json 文件。
  • CheckpointManager.CreateJson(store, null) — 包装存储，传给 RunStreamingAsync 即启用检查点。
  • ResumeStreamingAsync(workflow, checkpointInfo, manager) — 重建图并从指定检查点恢复（一个 Workflow 只能被一个 runner 持有）。

为什么分两阶段：先排队再应用

运行时不立即写状态，而是收集后在超步结束时一起应用。这避免了扇入（fan-in）时 多个探针并发写互相覆盖。所以每个执行器在开头用 ReadStateAsync 读取， 读到的总是上次已保存的值，不会是别的执行器写到一半的值。

  1. 步骤 1 — 理解为什么 v1 在恢复时会崩

    仔细看这个 v1。单进程测试全过。但若进程在扇入超步与合成超步之间被杀， _collected 列表只在内存里，恢复后变空，计数再也到不了 3， 验证器从此沉默。

[SendsMessage(typeof(DeepDiveRequest))]

public sealed class ValidatorExecutor() : Executor<ProbeResult>("validator")
{
    private const int ExpectedProbes = 3;

    // Instance field: invisible to the checkpoint serialiser.
    // Works in a single process run; LOST on kill+resume.
    private readonly List<ProbeResult> _collected = [];

    public override async ValueTask HandleAsync(
        ProbeResult result, IWorkflowContext context, CancellationToken cancellationToken = default)
    {
        _collected.Add(result);  // ← vanishes on restart

        if (_collected.Count < ExpectedProbes)
            return;

        var days = await context.ReadStateAsync<int>("days", scopeName: "investigation", cancellationToken);
        var costSpike = DetectCostSpike(_collected.FirstOrDefault(p => p.Name == "cost-trend")?.Rows);
        var findings = new Findings(days, _collected, costSpike, []);

        await context.QueueStateUpdateAsync("findings", findings, scopeName: "investigation", cancellationToken);
        await context.SendMessageAsync(findings, cancellationToken: cancellationToken);
    }
}

    ValidatorExecutor v2（4 / 4）：DetectCostSpike 辅助方法 
        private static bool DetectCostSpike(string? costTrendRows)
    {
        if (costTrendRows is null) return false;

        var costs = costTrendRows.Split('\n').Skip(1)
            .Select(line => line.Split('\t'))
            .Where(cells => cells.Length >= 2
                && double.TryParse(cells[1], System.Globalization.NumberStyles.Any,
                    System.Globalization.CultureInfo.InvariantCulture, out _))
            .Select(cells => double.Parse(cells[1], System.Globalization.CultureInfo.InvariantCulture))
            .ToList();

        if (costs.Count == 0) return false;
        var last = costs[^1];
        if (costs.Count == 1) return last > 5;

        var priorAverage = costs[..^1].Average();
        return last > priorAverage * 1.5;
    }
}

    Workflows/InvestigationService.cs — 构造函数 
        public InvestigationService(IConfiguration config, Tools.ClickHouseClient clickHouse, ILogger<InvestigationService> logger)
    {
        _logger = logger;
        var dir = new DirectoryInfo(config["CHECKPOINT_DIR"] ?? "checkpoints");
        dir.Create();
        _checkpointDir = dir;
        _store = new FileSystemJsonCheckpointStore(dir);
        _checkpointManager = CheckpointManager.CreateJson(_store, null);
        _workflowFactory = () => InvestigationWorkflow.Build(config, clickHouse);

    3 · 启动与进程内响应。StartAsync 开新运行并经 CheckpointManager 写快照，再交给 DriveAsync。RespondAsync 在运行还活着时回应审批； 没有句柄（如重启后）返回 null，让路由改用 /resume。 类先不闭合，步骤 4 补齐剩余成员和右花括号。

    Workflows/InvestigationService.cs — StartAsync + RespondAsync 
        public async Task<InvestigationStatus> StartAsync(int days, CancellationToken ct)
    {
        var runId = Guid.NewGuid().ToString("N");
        var run = await InProcessExecution.RunStreamingAsync(
            _workflowFactory(), new InvestigationRequest(days), _checkpointManager, runId, ct);
        return await DriveAsync(runId, run, [], ct);
    }

    public async Task<InvestigationStatus?> RespondAsync(string runId, bool approve, CancellationToken ct)
    {
        if (!_pending.TryRemove(runId, out var pending))
            return null;

        await pending.Run.SendResponseAsync(pending.Request.CreateResponse(new DeepDiveDecision(approve)));
        return await DriveAsync(runId, pending.Run, [], ct);
    }

  4. 步骤 4 — 向 InvestigationService 添加 ResumeAsync、DriveAsync 及辅助方法

    这四个成员加到步骤 3 的同一个类里，放在 RespondAsync 之后，然后闭合类。

    1 · ResumeAsync。加载该运行最新检查点并继续。两个坑： 索引含所有运行，要按 runId 过滤；检查点 id 是无序随机值，要按文件写入时间排序。 无匹配返回 null，路由回 404。

    Workflows/InvestigationService.cs — ResumeAsync 
        public async Task<InvestigationStatus?> ResumeAsync(string runId, CancellationToken ct)
    {
        var mine = (await _store.RetrieveIndexAsync(runId, null))
            .Where(checkpoint => checkpoint.SessionId == runId)
            .Select(checkpoint => (Info: checkpoint, WrittenAt: CheckpointWrittenAt(runId, checkpoint)))
            .OrderBy(entry => entry.WrittenAt)
            .ToList();

        if (mine.Count == 0)
            return null;

        _pending.TryRemove(runId, out _);
        var run = await InProcessExecution.ResumeStreamingAsync(_workflowFactory(), mine[^1].Info, _checkpointManager, ct);
        return await DriveAsync(runId, run, [new("resumed", $"from checkpoint {mine.Count} of run {runId}")], ct);
    }

    2 · CheckpointWrittenAt。小工具，找到检查点对应的文件 并返回它的最后写入时间，供 ResumeAsync 排序。

    Workflows/InvestigationService.cs — CheckpointWrittenAt 
        private DateTime CheckpointWrittenAt(string runId, CheckpointInfo checkpoint)
    {
        var file = _checkpointDir.GetFiles($"{runId}_{checkpoint.CheckpointId}*").FirstOrDefault();
        return file?.LastWriteTimeUtc ?? DateTime.MinValue;
    }

    3 · DriveAsync。Start、Respond、Resume 共用的循环。 逐个读事件、转成小状态对象、记录最终报告；出错则记日志并返回 failed。 审批暂停分支在 F2 才加。

    Workflows/InvestigationService.cs — DriveAsync 
        private async Task<InvestigationStatus> DriveAsync(
        string runId, StreamingRun run, List<WorkflowEventDto> events, CancellationToken ct)
    {
        string? report = null;
        try
        {
            await foreach (var evt in run.WatchStreamAsync(ct))
            {
                var dto = ToDto(evt);
                if (dto is not null) events.Add(dto);

                if (evt is WorkflowOutputEvent output)
                    report = output.Data?.ToString();
            }
        }
        catch (Exception ex)
        {
            _logger.LogError(ex, "Investigation run {RunId} failed.", runId);
            events.Add(new("error", ex.Message));
            return new InvestigationStatus(runId, "failed", null, null, events);
        }

        return new InvestigationStatus(runId, report is null ? "failed" : "completed", report, null, events);
    }

    4 · ToDto。把每个工作流事件映射成 API 用的小对象。 审批和端口分支在 F2 加。这是最后一个成员，之后闭合类。

    Workflows/InvestigationService.cs — ToDto（之后闭合类） 
        private static WorkflowEventDto? ToDto(WorkflowEvent evt) => evt switch
    {
        WorkflowStartedEvent => new("workflow_started", null),
        SuperStepCompletedEvent => new("superstep_completed", null),
        ExecutorInvokedEvent invoked => new("executor_invoked", invoked.ExecutorId),
        ExecutorCompletedEvent completed => new("executor_completed", completed.ExecutorId),
        ExecutorFailedEvent failed => new("executor_failed",
            $"{failed.ExecutorId}: {(failed.Data as Exception)?.GetBaseException().Message ?? failed.Data?.ToString()}"),
        InvestigationProgressEvent progress => new("progress", progress.Message),
        WorkflowOutputEvent => new("workflow_output", "report ready"),
        _ => null,
    };
}

🔄 演进脉络

为什么先给坏版本。步骤 1 的 v1 只是示例，不会进入最终构建——只有 v2 会发布。 先看错的版本，才能看清确切问题：单进程测试全绿，停了再恢复却给出错误或空结果， 而且没有报错。看着能跑的代码在恢复时失败，更容易记住规则。

本课还首次预演三个生产陷阱：存储索引覆盖所有运行、检查点 id 无序、一个 Workflow 只能有一个持有者。你会在 F2 — 深度调查：HITL 端口 + 生产检查点中完整用到它们，届时同一条流水线会加入人工审批，并对接真实遥测数据。

两个作用域如何协同工作

共享作用域 "investigation" 对每个执行器都可见： PlanExecutor 写 "days"，每个 ProbeExecutor 写 "probe:{name}"， ValidatorExecutor 读 "days" 写 "findings"，激增时 DeepDiveExecutor 读 "findings"。私有作用域（无 scopeName）只放 "collected"，归 ValidatorExecutor 独有。 每个值放最窄的作用域，避免执行器间意外耦合。

public sealed class DeepDiveExecutor(ClickHouseClient clickHouse) : Executor<DeepDiveDecision>("deepdive")
{
    public override async ValueTask HandleAsync(
        DeepDiveDecision decision, IWorkflowContext context, CancellationToken cancellationToken = default)
    {
        var findings = await context.ReadStateAsync<Findings>("findings", scopeName: "investigation", cancellationToken)
            ?? new Findings(7, [], false, ["Findings state was missing."]);

        if (!decision.Approve)
        {
            findings.ValidationNotes.Add("A cost spike was detected but the deep dive was declined by the user.");
            await context.SendMessageAsync(findings, cancellationToken: cancellationToken);
            return;
        }
    }
}

验证

✅ 关卡 — 未变绿前不要前进

1. 启动运行并抓住早期检查点。/investigate 会跑完才返回，所以无法从 curl 端中断。改在第二个终端盯 checkpoints/ 文件夹，第一个文件一出现就 Ctrl+C 停服务。 要停得早：此时磁盘上最新的检查点是 plan 之后、synthesis 之前的部分快照， 恢复才还有活干、才会产出报告。若让它跑完，只剩最终检查点，恢复就什么都不产出。 

# 终端 1 — 启动服务，再启动运行：
dotnet run -- --environment Testing
curl -s -X POST "http://localhost:8124/workflow/investigate" \
  -H "Content-Type: application/json" -d '{"days":7}'

# 终端 2 — 盯第一个文件出现，然后停掉终端 1（Ctrl+C）：
ls checkpoints/
# 文件形如：96d437ca5603472f8e2b571bfc70679a_<guid>.json
# runId 是下划线前面那段。

2. 重启并恢复。再次启动服务，用从文件名复制的 runId 调 /resume。 

dotnet run -- --environment Testing
curl -s -X POST "http://localhost:8124/workflow/<runId>/resume" | jq '{status, report}'

预期：status 为 "completed"，report 非空。events 以 "resumed" 开头，例如 "from checkpoint 1 of run <runId>"。恢复后的 events 里没有 "plan"——plan 已存进检查点，恢复跳过它，从探针继续。

反向测试 — 未知 runId 返回 404，而不是崩溃： 

curl -s -o /dev/null -w "%{http_code}" \
  -X POST "http://localhost:8124/workflow/notavalidrunid/resume"
# Must print: 404

需要留意：若保留 v1 实例字段版本，恢复会返回 status: "failed" 或零发现的报告，验证器到不了三项。 切到 v2（ReadOrInitStateAsync 和 QueueStateUpdateAsync）再跑，直接运行和杀死+恢复必须给出相同报告。

⚠️ 常见坑
  • 恢复返回空或部分报告，且没有报错 → 状态放在了实例字段而非上下文。改用 ReadOrInitStateAsync + QueueStateUpdateAsync。
  • "Already owned by another runner" 异常 → 同一个 Workflow 被传给两个并发的 RunStreamingAsync。用 Func<Workflow> 工厂，每次运行/恢复只调一次。
  • 运行已完成，恢复却找不到任何检查点 → 没把 CheckpointManager 传给 RunStreamingAsync（无 manager 的重载会静默跳过检查点）。
  • 恢复加载了错误运行的状态 → 存储索引在所有运行间全局。选最新检查点前，先用 checkpoint.SessionId == runId 过滤。
  • 实例字段能通过每个单进程测试 → 这正是陷阱。CI 绿不代表恢复安全；失败只在进程于两个超步间被杀时才显现。
  • 已完成的运行去恢复，结果没有报告 → 停得太晚，磁盘上只剩最终检查点。恢复加载它，没有剩余工作可做，就不产出报告。 改在第一个检查点文件出现时就停。
