第 01 课 · A1 · 模块 A — Hello 智能体（agent）

你的第一个智能体（agent） + 一个函数工具（function tool）

★ Haiku

你将学到什么

直接问一个裸 LLM“我的 telemetry 里有哪些表”，它会自信地编出根本不存在的列名，因为它从没见过你的 ClickHouse schema。解决办法是智能体（agent）：一个接入了工具调用（tool call）循环的 LLM，你给它一个返回真实 schema 的 C# 方法，让它在回答前先调用这个方法。

在 MAF 中你给智能体一个名字、一条系统指令、一个模型和一组可调用函数，MAF 负责在模型和代码之间来回传递，直到模型不再请求工具结果。本课用三个 API 面来实现 —— ChatClientAgentOptions、AIFunctionFactory.Create 和 client.AsAIAgent，并搭好后续每课当作关卡（gate）检查的 Testing 环境启动步骤。

📘 讲解

心智模型：智能体（agent）就是一个处于工具调用（tool call）循环中、并带有可配置记忆的 LLM。三个 MAF API 面负责这套接线：

  • ChatClientAgentOptions —— 名称、 描述、ChatOptions.Instructions（系统 提示词（system prompt））、ChatOptions.ModelId，以及 Tools 列表。所有选项都集中在一个对象里；智能体（agent）的身份与能力被一并声明。
  • AIFunctionFactory.Create(method) —— 把任意一个普通的 C# 实例方法变成模型可以调用的工具（tool）。方法及其参数上的 [Description("…")] 特性会成为 LLM 收到的工具 schema。无需手写 schema。
  • IAnthropicClient.AsAIAgent(options) —— 根据提供方客户端 + 选项创建出 AIAgent。在 A3 中你会在这里链式调用 .AsBuilder().UseOpenTelemetry(…).Build()；目前这种直接调用就足够了。

agent.RunAsync(prompt) 会运行一个完整的工具调用（tool call）循环， 并返回一个 AgentResponse。.Text 属性保存模型最终的回复； .Messages 保存完整的对话记录，包括中间的工具调用。

每一个关卡都用 dotnet run -- --environment Testing 来启动（其中的 -- 至关重要）。完整解释和反向测试见 L0。

动手实现

  1. 从一开始就理解模型分层（model tiering）

    硬编码模型 id 会让每次测试都按 Sonnet 计费，还得翻代码改模型，这正是 D3 把它当作反模式的原因。所以项目从第一天起就用一个静态辅助类从配置读取模型名。

    Agents/ModelTiers.cs 是叶子文件，无依赖。每个方法从 IConfiguration 读取一个分层名，缺失时用默认值兜底。AgentFactory（步骤 4）调用 ModelTiers.Analyst(config) 来选定模型。

    Agents/ModelTiers.cs 
    namespace AiAgent.Agents;

public static class ModelTiers
{
    public static string Light(IConfiguration config) => config["Models:Light"] ?? "claude-haiku-4-5";

    public static string Analyst(IConfiguration config) => config["Models:Analyst"] ?? "claude-sonnet-4-6";

    public static string Reasoning(IConfiguration config) => config["Models:Reasoning"] ?? "claude-opus-4-8";
}

    appsettings.Testing.json 的结构已在上面的“准备”提示框中给出；它把全部三个分层都锁定到 Haiku，让每个关卡都保持低成本。

  2. 创建系统提示词（system prompt）常量

    智能体需要两段文本：告诉它职责的系统提示词，以及被问到时可以返回的 schema 文档。两者放在同一个叶子文件里，方便后续课程扩展。

    Agents/Instructions.cs 不依赖本课其他文件。Instructions.System 由 AgentFactory（步骤 4）当作系统提示词读取，Instructions.SchemaDoc 由 SchemaTools.GetSchema（步骤 3）返回给模型。现在先写骨架；完整 schema 在 C1 补全，但 A1 要能编译，这个常量必须非空。

    Agents/Instructions.cs (A1 skeleton) 
    namespace AiAgent.Agents;

public static class Instructions
{
    public const string SchemaDoc = """
        # ClickHouse schema placeholder
        Fill in with actual schema in C1 (lesson08).
        """;

    public const string System = $"""
        You are the Claudalytics analyst. Answer questions about Claude Code
        telemetry stored in ClickHouse.

        {SchemaDoc}
        """;
}

  3. 编写函数工具（function tool）

    这个方法就是用来解决开头“模型编造列名”问题的。模型需要真实 schema 时就调用它，从而拿到真答案而不是靠猜。

    Tools/SchemaTools.cs 持有 A1 中智能体唯一会调用的工具，只依赖 Instructions.SchemaDoc（步骤 2），由 AgentFactory（步骤 4）注册为工具。ClickHouse 查询在 B1 才加入。工具就是带 [Description] 特性的普通 C# 实例方法，描述本身就是模型读取的工具 schema，所以要写清楚它返回什么、何时用它。

    Tools/SchemaTools.cs 
    using System.ComponentModel;
using AiAgent.Agents;

namespace AiAgent.Tools;

public sealed class SchemaTools
{
    [Description("Returns the full ClickHouse schema reference: tables, columns, attribute extraction idioms and example queries.")]
    public string GetSchema() => Instructions.SchemaDoc;
}

  4. 接入 Anthropic 客户端并创建智能体（agent）

    这一步把前面三个叶子文件组合成真正的智能体：注入 SchemaTools（步骤 3），从 ModelTiers（步骤 1）读取模型分层，并把 Instructions.System（步骤 2）作为系统提示词传入。Program.cs（步骤 5）在启动时调用这个工厂一次，构建出单例智能体。

    工厂被精简到只满足 A1，后续逐步扩展：compaction 在 E2、context provider 在 E1、OTel middleware 在 A3、agent-as-tool 在 F1。那时直接编辑此文件，不要重新生成。

    Agents/AgentFactory.cs 
    using AiAgent.Tools;
using Anthropic;
using Microsoft.Agents.AI;
using Microsoft.Extensions.AI;

namespace AiAgent.Agents;

public static class AgentFactory
{
    public static AIAgent Create(
        IConfiguration config,
        SchemaTools tools,
        ILoggerFactory loggerFactory)
    {
        var apiKey = config["ANTHROPIC_API_KEY"]
            ?? throw new InvalidOperationException("ANTHROPIC_API_KEY is not set.");

        IAnthropicClient client = new AnthropicClient { ApiKey = apiKey };

        var options = new ChatClientAgentOptions
        {
            Name = "claudalytics-analyst",
            Description = "Answers natural-language questions over Claudalytics telemetry in ClickHouse.",
            ChatOptions = new ChatOptions
            {
                ModelId = ModelTiers.Analyst(config),
                Instructions = Instructions.System,
                Tools =
                [
                    AIFunctionFactory.Create(tools.GetSchema),
                ],
            },
        };

        return client.AsAIAgent(options, loggerFactory: loggerFactory);
    }
}

    现在三个叶子文件都已就位 —— 粘贴完这一步后项目就能干净地构建。

  5. 注册智能体（agent）并暴露一个 /chat 端点（endpoint）

    前几步的工厂和工具不运行起来就没用。Program.cs 把 AIAgent 注册为单例，并映射一个供调用者提问的 POST 端点。A1 端点保持最小：暂无会话存储（那是 A2），也无流式（那是 A3）。

    先是 using 和 DI 注册，放在文件顶部和 var app = builder.Build(); 之前。AddSingleton<AIAgent> 从 DI 取出 SchemaTools 传给 AgentFactory.Create（步骤 4），智能体只构建一次并复用。Microsoft.Extensions.AI 这个 using 用于下一块要读的 FunctionCallContent。

    Program.cs (usings + DI — before builder.Build()) 
    using AiAgent.Agents;
using AiAgent.Tools;
using Microsoft.Agents.AI;
using Microsoft.Extensions.AI;

builder.Services.AddSingleton<SchemaTools>();
builder.Services.AddSingleton<AIAgent>(sp => AgentFactory.Create(
    sp.GetRequiredService<IConfiguration>(),
    sp.GetRequiredService<SchemaTools>(),
    sp.GetRequiredService<ILoggerFactory>()));

var app = builder.Build();

    接着是端点，放在 var app = builder.Build(); 之后。它调用 agent.RunAsync 跑一次工具调用循环，返回两个字段：answer 是模型最终文本，toolCalls 是模型实际调用的工具列表（从 response.Messages 中筛出 FunctionCallContent）。

    Program.cs (/chat — after builder.Build()) 
    app.MapPost("/chat", async (ChatRequest request, AIAgent agent, CancellationToken ct) =>
{
    if (string.IsNullOrWhiteSpace(request.Message))
        return Results.BadRequest(new { error = "message is required" });

    var response = await agent.RunAsync(request.Message, cancellationToken: ct);
    return Results.Ok(new
    {
        answer = response.Text,
        toolCalls = response.Messages
            .SelectMany(m => m.Contents)
            .OfType<FunctionCallContent>()
            .Select(c => new { name = c.Name }),
    });
});

app.Run();

    最后是请求类型。ChatRequest 是文件作用域 record，放在文件末尾 app.Run(); 之后。

    Program.cs (record — after app.Run()) 
    internal sealed record ChatRequest(string Message);

    现在 /chat 已上线。toolCalls 字段就是 A1 的验证信号：答案自信但 toolCalls 为空，说明工具没注册，或描述太含糊让模型没选它。下面的验证关卡会检查这一点。

  6. 添加一个冒烟测试健康端点

    信任 /chat 答案之前，先要有个便宜的方式确认模型可达、API 密钥有效。/healthz/llm 发一个极小的 prompt 并返回回复，这里失败就指向接线问题而非 prompt。下面的验证关卡会先调用它。

    两个端点放在 var app = builder.Build(); 之后，和步骤 5 的 /chat 一起。/healthz 是普通存活检查，/healthz/llm 是 LLM 冒烟测试。

    Program.cs (healthz — after builder.Build()) 
    app.MapGet("/healthz", () => Results.Ok(new { status = "ok" }));

app.MapGet("/healthz/llm", async (AIAgent agent, CancellationToken ct) =>
{
    var response = await agent.RunAsync("Reply with the single word: ok", cancellationToken: ct);
    return Results.Ok(new { status = "ok", model_reply = response.Text });
});

为什么工具（tool）描述很重要

模型没有代码可供检查。它看到的只有工具（tool）名称和你写的描述。描述单薄时模型就会靠猜 —— 而且通常猜错。修复办法始终一样：让描述精确说明何时该用这个工具、它返回什么，而不只是它叫什么。

对比一下模型在精确描述与含糊描述下对 GetSchema 看到的内容：

  • 精确： “Returns the full ClickHouse schema reference: tables, columns, attribute extraction idioms and example queries.” —— 模型知道在它需要编写或校验查询时就该调用这个工具（tool）。
  • 含糊： “Gets schema info.” —— 模型分辨不出这是否与编写查询有关，于是跳过该工具（tool），转而用它自己（其实并不存在）的、关于你数据的“知识”来回答，结果就编造出根本不存在的列名。

一个带有精确描述的工具（tool），比多个描述彼此重叠或单薄的工具更可靠。只有在用途确实各不相同时才添加工具 —— 并让每个描述都同时说清楚何时用它以及它返回什么。

验证

✅ 关卡（gate） — 未变绿前不要前进

第 1 步 — 环境检查。用这套仪式启动：

dotnet run -- --environment Testing

确认控制台打印出 Hosting environment: Testing。如果显示的是别的内容，停下来修正启动命令。

第 2 步 — 对 LLM 路径做冒烟测试：

curl http://localhost:8124/healthz/llm

预期：{"status":"ok","model_reply":"ok"}

第 3 步 — 提出一个需要用到 GetSchema 的问题： 

curl -s -X POST http://localhost:8124/chat \
  -H "Content-Type: application/json" \
  -d '{"message": "what tables are available in the schema?"}'

响应中的 toolCalls 数组必须 非空并包含 get_schema。 answer 必须描述 schema 的实际内容，而不是泛泛的占位符。

反向测试 —— 幻觉检查。

如果你得到一个自信的答案但 toolCalls 为空，说明模型是凭它自己的“知识”回答的（而它对你的 schema 一无所知）。这意味着工具（tool）没有被注册，或者它的描述太含糊。检查 AIFunctionFactory.Create(tools.GetSchema) 是否出现在你选项里的 Tools 数组中，以及该方法是否带有 [Description] 特性。

⚠️ 常见坑
  • 控制台显示 Hosting environment: Production → 缺少 -- 分隔符。要运行 dotnet run -- --environment Testing，而不是 dotnet run --environment Testing。没有分隔符时，dotnet 会把 --environment 当成它自己的标志，并悄悄丢弃掉。
  • 答案非空，但 toolCalls 为空 → 工具（tool）没有注册。该方法必须通过 AIFunctionFactory.Create 出现在 ChatOptions.Tools 中。检查 AgentFactory.cs 里的那个数组；缺一项不会产生编译错误，也没有运行时警告 —— 只会得到一个在产生幻觉的模型。
  • 模型跳过工具，凭自己的知识作答 → [Description] 特性太含糊。模型分辨不出该工具（tool）何时相关，于是不调用它就开始猜。把描述重写成精确说明工具返回什么、何时使用。
  • 启动时报 ANTHROPIC_API_KEY is not set → 密钥不在 appsettings.Local.json（那个被 git 忽略的文件）里。永远不要提交密钥；Local 文件最后被加载，会覆盖其他一切。
  • 工具（tool）方法抛出异常，而不是返回一个错误字符串 → 工具抛出的未处理异常会让 RunAsync 调用以异常告终，而不是返回一条模型可读的消息。务必捕获异常并返回 "QUERY FAILED: {ex.Message}"，这样模型才能对失败进行推理。
