第 06 课 · B3 · 模块 B — 图

智能体（agent）不过是一个节点（node）

★★ Haiku

你将学到什么

现在 Claudalytics Copilot 调查只会丢出原始 probe 行。有人问“这意味着 什么？”，流水线答不上来，因为没有任何东西把数字转成文字。本课把一个 LLM agent 作为一个 node 放进图里，它读取带类型的 probe 数据并写出一份短报告。 于是这次运行最终给出人能读的 prose。

心智模型很简单——agent 不过是一个 node。你继承 Executor<T>，接收带类型输入，调用 agent.RunAsync，再产出结果。 B2 的图拓扑与事件流不变，只有最后一个 node 变聪明。

为此你会加入三个消息记录（Findings、 DeepDiveRequest、DeepDiveDecision）、一个做 fan-in 的 ValidatorExecutor 和一个持有 agent 的 SynthesisExecutor，并创建 InvestigationWorkflow.cs 作为图的 Build 方法的正式归宿，退役 B1 的脚手架文件 ProbeWorkflow.cs 和 CollectorExecutor。

📘 讲解

MAF 的智能光谱：每个工作流（workflow）节点（node）都处于 “纯确定性代码”（免费、瞬时）与“完整 LLM 智能体（agent）”（灵活、昂贵）之间。 你来决定每一步配多少智能。SQL 探针（probe）一点都不需要； 而综合步骤恰好需要足够的智能，把表格化的数字转写成连贯的文字。

本课引入的 API 接口：

  • Executor<TInput> —— 基类不变； 通过构造函数注入智能体（DI 的用法和任何服务一模一样）。
  • [YieldsOutput(typeof(T))] —— 终端节点（node） 声明；框架在运行时会拒绝未声明的产出类型，因此该特性是必需的。
  • context.YieldOutputAsync(value, ct) —— 把 最终值推送到工作流输出流并结束本次运行。
  • agent.RunAsync(prompt, ct) —— 单轮 LLM 调用， 返回 .Text。这里要用一个专门的 写作智能体（writer agent），而不是主分析师；它绝不能 反问追加问题（见下方的提示词契约）。

工作流（workflow）内智能体（agent）的提示词契约：模型的 第一次回复就是工作流的输出。没有任何渠道能让追加的问题得到回答。系统 指令必须包含： “你的回复就是最终成品。不要提问，也不要索取更多数据。”

本课之后的流水线形态

PlanExecutor
    │  (3× ProbeJob)
    ▼  fan-out
ProbeExecutor × 3
    │  (3× ProbeResult)
    ▼  fan-in barrier
ValidatorExecutor        ← NEW: deterministic; builds Findings; routes spike branch
    │  (Findings)             (DeepDiveRequest goes to deepDive directly — no human gate in B3)
    ▼
SynthesisExecutor        ← NEW: holds AIAgent → markdown report
    │  [YieldsOutput]
    ▼  workflow output: string

动手实现

  1. 在 InvestigationModels.cs 中定义新的消息记录

    图需要带类型的消息在 node 之间传递。Findings 由 validator 构建，由 synthesis node 读取。DeepDiveRequest 和 DeepDiveDecision 属于 cost-spike 分支。把这三个记录追加到 Workflows/InvestigationModels.cs（B1 已建立，含 InvestigationRequest、ProbeJob、 ProbeResult）。无需新增 using。

    Workflows/InvestigationModels.cs — 追加在 ProbeResult 之后 
    /// <summary>Aggregated, validated probe results.</summary>
public sealed record Findings(int Days, List<ProbeResult> Results, bool CostSpike, List<string> ValidationNotes);

/// <summary>Deep-dive branch request, sent by the validator on a cost spike.</summary>
public sealed record DeepDiveRequest(string Reason);

/// <summary>Deep-dive branch decision, returned by the approval port in F2.</summary>
public sealed record DeepDiveDecision(bool Approve);

    在这里引入后两个记录，是因为 validator 的 [SendsMessage] 特性和 DeepDiveExecutor 桩（第 3 步）会引用它们。把请求交给人并等待决定的 human-in-the-loop approval PORT 在 F2 中加入。

  2. 为写作智能体（writer agent）加入系统指令

    synthesis node 需要一个 agent 可调用。这个 agent 是 writer，不是主 分析师。它只接收结构化数据并返回 markdown 文字。在 Agents/Instructions.cs 的 Instructions 类里、System 常量之后加入一个 Writer 常量。usings 和 namespace 在 A1 中已就绪。

    Agents/Instructions.cs — Instructions 类内 
    public const string Writer = """
    You are a technical writer for an observability report.
    You receive structured probe data (TSV) and validation notes.
    Write a short markdown investigation report: headline numbers,
    then findings, then 1-3 recommendations.
    Use ONLY the numbers present in the data — do not invent figures.
    If data is thin, say so honestly.
    Your response is the final product. Do not ask questions or request more data.
    """;

    最后一句是提示词契约。模型的第一次回复就是工作流的输出，没有渠道能让 追加问题得到回答，所以 agent 绝不能反问。

  3. 把 ValidatorExecutor、 DeepDiveExecutor 桩和 SynthesisExecutor 加入 InvestigationExecutors.cs

    把这三个执行器（executor）全部追加到 Workflows/InvestigationExecutors.cs。该文件顶部的 using 已经包含 来自 B1 的 using Microsoft.Agents.AI; 和 using Microsoft.Agents.AI.Workflows;。 顺序对讲解很重要：先 Validator（扇入（fan-in）逻辑），再 DeepDive 桩（尖峰分支的占位）， 最后 Synthesis（LLM 节点（node））。

    ValidatorExecutor —— 确定性 fan-in

    validator 位于 fan-in barrier 之后。它收集全部三条 ProbeResult，检查每条，构建出 synthesis node 接着读取的 Findings 记录。B3 里还没有 cost-spike 检查，所以 CostSpike 恒为 false，Days 是占位 的 0；B4（L07）会通过 context state 接入真实值并加入尖峰检测。字段上的 ⚠ 标记一个 bug：它在 checkpoint/resume 时会丢， B4 会讲。

    Workflows/InvestigationExecutors.cs — 追加 
    [SendsMessage(typeof(Findings))]
[SendsMessage(typeof(DeepDiveRequest))]
public sealed class ValidatorExecutor() : Executor<ProbeResult>("validator")
{
    private const int ExpectedProbes = 3;
    private readonly List<ProbeResult> _accumulated = []; // ⚠ B4 shows why this field breaks on resume

    public override async ValueTask HandleAsync(
        ProbeResult result, IWorkflowContext context, CancellationToken cancellationToken = default)
    {
        _accumulated.Add(result);
        if (_accumulated.Count < ExpectedProbes) return;

        var notes = _accumulated
            .Where(probe => !probe.HasData)
            .Select(probe => $"Probe '{probe.Name}' returned no usable numbers — finding rejected, not interpreted.")
            .ToList();

        var findings = new Findings(
            Days: 0,
            Results: [.._accumulated],
            CostSpike: false,
            ValidationNotes: notes);

        await context.AddEventAsync(
            new InvestigationProgressEvent("Validation complete — forwarding findings."), cancellationToken);

        await context.SendMessageAsync(findings, cancellationToken: cancellationToken);
    }
}

    即便 B3 从不发送它，[SendsMessage(typeof(DeepDiveRequest))] 也要声明。builder 在 Build() 时校验所有 edge，现在声明该类型， 第 4 步加入的深挖 edge 才会被无错接受。

    DeepDiveExecutor —— 尖峰分支的桩

    第 4 步把它接入图，让 builder 能校验已声明的 [SendsMessage(typeof(DeepDiveRequest))] edge。B3 里它是桩： 从共享 state 读取 findings（缺失时兜底为空记录），原样转发给 synthesis node。完整主体在 F2 中加入。

    Workflows/InvestigationExecutors.cs — 追加 
    [SendsMessage(typeof(Findings))]
public sealed class DeepDiveExecutor() : Executor<DeepDiveDecision>("deepdive")
{
    public override async ValueTask HandleAsync(
        DeepDiveDecision decision, IWorkflowContext context, CancellationToken cancellationToken = default)
    {
        var findings = await context.ReadStateAsync<Findings>(
            "findings", scopeName: "investigation", cancellationToken)
            ?? new Findings(0, [], false, ["Findings state was missing."]);

        await context.AddEventAsync(
            new InvestigationProgressEvent("Deep-dive stub — forwarding findings."), cancellationToken);

        await context.SendMessageAsync(findings, cancellationToken: cancellationToken);
    }
}

    SynthesisExecutor —— agent node

    synthesis executor 是图中唯一的 LLM node，读取 validator 发来的 Findings。结构和其他 executor 一样：继承 Executor<T>，实现 HandleAsync。区别在主体 调用 writer.RunAsync。前半部分把带类型的 Findings 转成 agent 能读的纯文本。

    Workflows/InvestigationExecutors.cs — 追加 
    [YieldsOutput(typeof(string))]
public sealed class SynthesisExecutor(AIAgent writer) : Executor<Findings>("synthesis")
{
    public override async ValueTask HandleAsync(
        Findings findings, IWorkflowContext context, CancellationToken cancellationToken = default)
    {
        await context.AddEventAsync(
            new InvestigationProgressEvent("Synthesizing the report."), cancellationToken);

        var probesText = string.Join("\n\n",
            findings.Results.Select(probe => $"## {probe.Name}\n{probe.Rows}"));
        var notesText = findings.ValidationNotes.Count == 0
            ? "(none)"
            : string.Join("\n", findings.ValidationNotes);

    后半部分用一个 prompt 调用 writer agent，prompt 带上 probe 文本、notes 和天数。agent 返回 markdown，YieldOutputAsync 把它作为工作流 的最终输出推出去。在此块之后收尾方法和类。

    Workflows/InvestigationExecutors.cs — 同一方法 
            var response = await writer.RunAsync($"""
            Write a short markdown investigation report over the last {findings.Days} days of
            Claude Code telemetry. Cost spike detected: {findings.CostSpike}.

            Probe data (TSV):
            {probesText}

            Validator notes (mention them honestly):
            {notesText}

            Shape: headline numbers, findings, then 1-3 recommendations. Use only the
            numbers in the data above.
            """, cancellationToken: cancellationToken);

        await context.YieldOutputAsync(response.Text, cancellationToken);
    }
}

    [YieldsOutput(typeof(string))] 是必需的。没有它，框架会抛出 运行时错误，点名该 executor 和未声明的类型。

  4. 在 InvestigationWorkflow.Build() 中内联构造写作智能体（writer agent）

    synthesis node 需要把 writer agent 传进去。不要把它注册 到 DI：注册成 AddSingleton<AIAgent> 会和同类型的主分析师 冲突，DI 会注入最后注册的那个。正确做法是在 InvestigationWorkflow.Build() 内部内联构造，这正是本项目的做法。 无需新增 NuGet 包，依赖都在 A1 中加过。 放在解析 apiKey 并创建 client 之后。

    Workflows/InvestigationWorkflow.cs — Build() 内 
    var writer = client.AsAIAgent(
    model: ModelTiers.Analyst(config),
    instructions: Instructions.Writer,
    name: "InvestigationWriter");

    client.AsAIAgent(model:, instructions:, name:) 是 三参数重载。传入 instructions: 即可设置系统提示词（system prompt），无需 ChatClientAgentOptions 包装对象—— 你正是用的这种形式。

  5. 创建 Workflows/InvestigationWorkflow.cs，包含 完整的 B3 图

    这是 InvestigationWorkflow.Build 方法的正式归宿，创建为新文件， 替换掉 B1 的脚手架 ProbeWorkflow.cs。前半部分写文件头、writer agent，以及每个 node 各一个实例（就是前几步写的那些）。

    Workflows/InvestigationWorkflow.cs 新文件 
    using AiAgent.Agents;
using AiAgent.Tools;
using Anthropic;
using Microsoft.Agents.AI;
using Microsoft.Agents.AI.Workflows;

namespace AiAgent.Workflows;

/// <summary>The investigation graph (B3 form). No human-approval port yet; that is added in F2.</summary>
public static class InvestigationWorkflow
{
    public static Workflow Build(IConfiguration config, ClickHouseClient clickHouse)
    {
        var apiKey = config["ANTHROPIC_API_KEY"]
            ?? throw new InvalidOperationException("ANTHROPIC_API_KEY is not set.");

        IAnthropicClient client = new AnthropicClient { ApiKey = apiKey };
        var writer = client.AsAIAgent(
            model: ModelTiers.Analyst(config),
            instructions: Instructions.Writer,
            name: "InvestigationWriter");

        var plan = new PlanExecutor();
        ProbeExecutor[] probes =
        [
            new("probe-0", clickHouse),
            new("probe-1", clickHouse),
            new("probe-2", clickHouse),
        ];
        var validator = new ValidatorExecutor();
        var deepDive = new DeepDiveExecutor();
        var synthesis = new SynthesisExecutor(writer);

        var builder = new WorkflowBuilder(plan);

    后半部分接线。fan-out edge 把每个 ProbeJob 从 plan 路由到一个 probe；fan-in barrier 等三个 probe 都到齐才放行 validator；正常路径把 Findings 从 validator 送到 synthesis node。最后两条是 spike 分支：validator 把 DeepDiveRequest 发给桩，桩再把 findings 转 给 synthesis。B3 从不触发，但两条 edge 现在都要声明，builder 才会在 Build() 时接受 validator 的 [SendsMessage(typeof(DeepDiveRequest))]。这条分支还没有 human gate，审批 port 在 F2 中加入。

    Workflows/InvestigationWorkflow.cs — 同一方法 
            builder.AddFanOutEdge<ProbeJob>(plan, probes.Select(p => (ExecutorBinding)p),
            (job, targetCount) => [(job?.Slot ?? 0) % targetCount]);

        builder.AddFanInBarrierEdge(probes.Select(p => (ExecutorBinding)p), validator);

        builder.AddEdge<Findings>(validator, synthesis, _ => true);

        builder.AddEdge<DeepDiveRequest>(validator, deepDive, _ => true);
        builder.AddEdge(deepDive, synthesis);

        return builder.WithOutputFrom(synthesis).Build();
    }
}

  6. 在 Program.cs 中重新指向服务工厂

    在 B2 中注册的 InvestigationService 使用的工厂仍然构建旧的 ProbeWorkflow。把它改为构建新图——这是一行改动：

    Program.cs 
    // Before (B2 — ProbeWorkflow):
builder.Services.AddSingleton(sp =>
    new InvestigationService(() => ProbeWorkflow.Build(sp.GetRequiredService<ClickHouseClient>()), sp.GetRequiredService<ILogger<InvestigationService>>()));

// After (B3 — InvestigationWorkflow):

🔄 演进线索

本课完成线索 1：B1 collector → B3 synthesis node。朴素 collector 拼接原始 TSV 并返回，足以证明 fan-in 可行。但只要有人问“这意味着 什么？”流水线就答不上来。synthesis node 就是修复方案。下方 v1 vs v2 展示改了 什么。

v1 vs v2

v1 收集器只是用来暴露问题——你不会把它发布上线。 终态如下：

// v1 — naive concatenating collector — do not ship
[YieldsOutput(typeof(string))]
public sealed class CollectorExecutor() : Executor<ProbeResult>("collector")
{
    private readonly List<string> _accumulated = [];  // ⚠ breaks on checkpoint/resume (B4)

    public override async ValueTask HandleAsync(
        ProbeResult result, IWorkflowContext context, CancellationToken cancellationToken = default)
    {
        _accumulated.Add($"## {result.Name}\n{result.Rows}");
        if (_accumulated.Count < 3) return;

        // Concatenate and emit — no intelligence.
        await context.YieldOutputAsync(string.Join("\n\n", _accumulated), cancellationToken);
    }
}

它为什么崩溃：输出是原始 TSV——没有 解读、没有建议，人无法使用。实例字段 _accumulated 在检查点（checkpoint）/恢复（resume）时也会出问题（这是 B4 的主题）。

v2 综合节点（node）从 ValidatorExecutor 接收一个 组装好的 Findings 记录——一条消息、一次 LLM 调用、一次 产出。没有实例字段；累加是在验证器里通过 context.ReadOrInitStateAsync 以检查点（checkpoint）安全的方式完成的 （在 B4 中加入）。

Workflows/InvestigationExecutors.cs 
[YieldsOutput(typeof(string))]
public sealed class SynthesisExecutor(AIAgent writer) : Executor<Findings>("synthesis")
{
    public override async ValueTask HandleAsync(
        Findings findings, IWorkflowContext context, CancellationToken cancellationToken = default)
    {
        var probesText = string.Join("\n\n",
            findings.Results.Select(probe => $"## {probe.Name}\n{probe.Rows}"));

        var response = await writer.RunAsync($"""
            Write a short markdown investigation report over the last {findings.Days} days ...
            Probe data (TSV): {probesText}
            Use only the numbers in the data above.
            """, cancellationToken: cancellationToken);

        await context.YieldOutputAsync(response.Text, cancellationToken);
    }
}

验证

✅ 关卡 — 未变绿前不要前进

dotnet run -- --environment Testing
curl -s -X POST http://localhost:8124/investigate \
  -H "Content-Type: application/json" \
  -d '{"days": 7}'

以下三点必须全部成立：

  1. 响应体是散文式 markdown——有标题、 句子、数字。而不是一坨原始 TSV。
  2. 报告里的数字与探针数据完全一致。如果 cost-trend 显示成本最高的一天是 0.12， 报告就必须说 0.12——不能是 凭空捏造的数字。
  3. 来自 B2 驱动器的事件时间线显示出同样的图 形态：探针（probe）执行器（executor）处于一个超步（superstep），验证器其次， 综合节点（node）最后。加入一个智能体（agent）节点并不会改变拓扑。

反向测试：把探针（probe）数据从 综合提示词中移除（传入一个空的 probesText）并 重新运行。模型会产出一份听起来煞有介事、但数字是编造的报告——它 照样能成功完成。这就是幻觉基线。如果你接地（grounded）和 不接地（ungrounded）的两份报告看起来一模一样，说明提示词没有把模型 约束到数据上——把指令收紧一些。前进之前记得把探针数据放回去。

⚠️ 常见坑
  • 工作流（workflow）输出是一个问题，而不是一份报告 → 写作智能体（writer agent）的指令缺了提示词契约那句话。补上： “你的回复就是最终成品。不要提问，也不要索取 更多数据。”
  • 点名 SynthesisExecutor 和 string 的运行时错误 → 类上缺了 [YieldsOutput(typeof(string))] 特性。
  • 报告里的数字和探针（probe）对不上 → 综合节点（node）运行时 findings.Results 是空的。 验证器没有填充 Findings 记录—— 在 ValidatorExecutor 里加一个调试事件，记录 结果数量。
  • 注入到 SynthesisExecutor 的智能体（agent）不对 → 你在 Program.cs 中把写作智能体（writer agent）注册成了 AddSingleton<AIAgent>。DI 会解析出最后注册的那个 AIAgent，于是 SynthesisExecutor 拿到的是 注册顺序竞赛中胜出的那一个。修复办法：在 InvestigationWorkflow.Build() 中内联构造写作智能体（如 第 4 步所示），并直接传给 new SynthesisExecutor(writer)——完全不走 DI 查找。
  • 构建错误：未声明的边（edge）类型 DeepDiveRequest → ValidatorExecutor 缺了 [SendsMessage(typeof(DeepDiveRequest))]，或者 InvestigationWorkflow.Build() 里的 AddEdge<DeepDiveRequest>(validator, deepDive) 调用不见了。即便 B3 中尖峰分支从不触发，这两者也都必须存在。
