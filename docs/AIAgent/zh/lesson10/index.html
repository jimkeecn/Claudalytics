工具级人工审批

★★ Haiku

你将学到什么

这个智能体里有一个危险工具：它能不带时间过滤地全表扫描 otel_logs，读数百万行、跑几分钟，在用户也许没打算 执行的请求上烧掉真金白银。C3 把这一个工具放到人工审批关卡（gate）之后。模型选中它时运行先暂停，没人批准前不碰数据库。

机制是一个包装器：把工具注册进 ApprovalRequiredAIFunction，而不是普通函数。模型选中后 框架不执行，而是发出 ToolApprovalRequestContent 并暂停。 服务器用生成的 id 存下待审批项，返回 kind: "approval"。 第二个端点 POST /chat/approve 落实决定：批准就把工具调用 重放进同一会话（session），拒绝就注入一条拒绝消息。每个审批只能用一次， 再用返回 404。关卡在单个工具上，不在工作流级别（那是 F2 的 RequestPort）。

📘 讲解

工具级 HITL 的三个组成部分

MAF 用三个协作部件实现工具审批。

  • ApprovalRequiredAIFunction —— 包装器，代替原始 AIFunction。模型选中被包装的工具时， 框架发出 ToolApprovalRequestContent 并暂停，不执行函数。
  • ToolApprovalRequestContent —— 暂停信号。携带原始 ToolCall（模型想发起的函数调用）， 并带一个 CreateResponse(approved, reason) 方法， 用来构造恢复（resume）运行的回复。
  • agent.RunAsync(reply, session) —— 把决定回灌。在同一会话上用一条 ChatMessage(ChatRole.User, [pending.Request.CreateResponse(approved, reason)]) 调用 RunAsync。批准则执行工具并继续；拒绝则灌入原因、 不执行工具直接作答。

无需新库包，都在 C2 已加的包里。 整个契约由 MAF 的 chat-client 层强制，它在工具调用到达你的代码前就拦截。

为什么无界限扫描需要一道关卡（gate）

C1 里的 SqlValidator 要求每条 otel_logs 查询都带 Timestamp 过滤，因为它是大表。这是正确默认：全表扫描既贵又 通常没必要。但偶尔用户确实需要全时间段聚合（例如“从一开始到现在哪个项目 花得最多？”）。办法是再加一个工具 RunUnboundedSql，它跳过 时间过滤规则，但被一道人工关卡挡住。模型可以提议，人工必须批准。

动手实现

  1. 把无界限 SQL 工具加进 SchemaTools

    这就是关卡保护的工具。智能体读它的描述，仅在问题需要全表扫描时才调用。 加在已有的 public sealed class SchemaTools(ClickHouseClient clickHouse) 内部，与 RunSql 并列，无需新增 using。

    RunUnboundedSql 与 RunSql 只差一处：它调用 SqlValidator.Validate(query, requireTimeFilter: false)，关掉时间过滤规则。其余防护照常：只读动词、单条语句、自动加 LIMIT。

    Tools/SchemaTools.cs 
    [Description("Executes a read-only SELECT WITHOUT the otel_logs time-filter requirement. "
           + "Use ONLY when a full-table scan is genuinely needed. "
           + "Every call requires explicit human approval before it runs.")]
public async Task<string> RunUnboundedSql(
    [Description("The SELECT (or WITH ... SELECT) query to execute, "
               + "may scan otel_logs without a Timestamp filter.")] string query)
{
    try
    {
        var sql = SqlValidator.Validate(query, requireTimeFilter: false);
        return await clickHouse.QueryAsync(sql);
    }
    catch (Exception ex)
    {
        return $"QUERY FAILED: {ex.Message}";
    }
}

    这里不改 SqlValidator。它的 Validate 从 C1 起就接受 requireTimeFilter 标志，你只是传 false。只读正则防护两个工具共用。

    下面是 C1 之后的 Validate 供参考。类保持 public static partial class SqlValidator， [GeneratedRegex] partial 方法保持不动。此处没有新增内容， 只是让你看清 false 路径跳过了什么。

    Tools/SqlValidator.cs — Validate 方法（C1 起不变） 
    public static string Validate(string query, bool requireTimeFilter = true)
{
    var sql = query.Trim().TrimEnd(';').Trim();

    if (sql.Contains(';'))
        throw new ArgumentException("Only a single SQL statement is allowed.");

    if (!SelectOrWith().IsMatch(sql))
        throw new ArgumentException("Only SELECT (or WITH ... SELECT) queries are allowed.");

    var denied = DeniedKeywords().Match(sql);
    if (denied.Success)
        throw new ArgumentException($"Keyword '{denied.Value}' is not allowed. This tool is read-only; FORMAT is appended automatically.");

    if (requireTimeFilter && TargetsOtelLogs().IsMatch(sql)
        && !sql.Contains("Timestamp", StringComparison.OrdinalIgnoreCase))
        throw new ArgumentException(
            "Queries against otel_logs must filter on Timestamp (it is a large table). " +
            "Add e.g. WHERE Timestamp >= now() - INTERVAL 1 DAY.");

    if (!HasLimit().IsMatch(sql))
        sql += $" LIMIT {DefaultLimit}";

    return sql;
}

  2. 用 ApprovalRequiredAIFunction 包装该工具

    这一步设下关卡。包装器让框架暂停而不执行。把 RunUnboundedSql 注册进 new ApprovalRequiredAIFunction(...)，其他工具仍用普通 AIFunctionFactory.Create。智能体按名字看到它，只有框架知道它被关卡管控。

    替换 AgentFactory.Create 里的 Tools = [...] 块。 using Microsoft.Agents.AI; 从 A1 起就在， ApprovalRequiredAIFunction 也在同一命名空间，无需新增 NuGet 包。

  3. 把待审批项存进一个共享字典

    暂停和决定发生在两次 HTTP 请求里，服务器要在两者之间记住这个暂停的审批。 响应里出现 ToolApprovalRequestContent 时就存在这里， 步骤 5 的 /chat/approve 按 id 读回。在 DI 中注册单例 ConcurrentDictionary<string, PendingApproval>， using System.Collections.Concurrent; 从 A2 起就在。

    把 AddSingleton 加在 DI 块里、已有的 ConcurrentDictionary<string, AgentSession> 注册之后。 PendingApproval 是文件作用域 record，放在 app.Run(); 之后，与 ChatRequest、 ApproveRequest 等并列。

    Program.cs — DI 块（在 app.Build() 之前） 
    builder.Services.AddSingleton<ConcurrentDictionary<string, PendingApproval>>();
    Program.cs — app.Run() 之后的文件作用域 
    internal sealed record PendingApproval(
    string SessionId,
    AgentSession Session,
    ToolApprovalRequestContent Request);

    record 特意带上 AgentSession。审批决定必须继续同一对话。 这里丢掉会话，智能体就会没有历史、没有上下文地恢复，答案出错。 会话是 A2 引入的 MAF 多轮记忆单元。

  4. 在 chat 响应构造器中检测暂停信号

    这是暂停的读取端。每次 agent.RunAsync 后扫描响应里有没有 ToolApprovalRequestContent。有就说明运行暂停，存下审批并让 调用方去问人；没有就是普通答案。调用方（前端）按 kind 分支： "approval" 显示批准/拒绝提示，"answer" 照常显示回复。

    ToChatResponse 和 StoreApproval 是文件作用域的 static 辅助方法，放在 app.Run(); 之后、 GetOrCreateSessionAsync（A2 起就在）旁边。/chat 和步骤 5 的 /chat/approve 都会调用它们。

    第一个方法 ToChatResponse 把响应摊平成内容项，收集工具调用供展示， 再找第一个 ToolApprovalRequestContent。找到就调 StoreApproval 存下并拿到 id。返回对象据此把 kind 设为 "approval" 或 "answer"。

    Program.cs — app.Run() 之后的文件作用域 
    static object ToChatResponse(string sessionId, AgentSession session, AgentResponse response,
    ConcurrentDictionary<string, PendingApproval> approvals)
{
    var contents = response.Messages.SelectMany(message => message.Contents).ToList();

    var toolCalls = contents.OfType<FunctionCallContent>()
        .Select(call => new { name = call.Name, arguments = (object?)call.Arguments })
        .ToList();

    var approvalRequest = contents.OfType<ToolApprovalRequestContent>()
        .Select(approval =>
        {
            var call = approval.ToolCall as FunctionCallContent;
            return new
            {
                approvalId = StoreApproval(approvals, sessionId, session, approval),
                toolName = call?.Name,
                arguments = call?.Arguments,
            };
        })
        .FirstOrDefault();

    return new
    {
        sessionId,
        kind = approvalRequest is null ? "answer" : "approval",
        answer = response.Text,
        menu = (object?)null,
        toolCalls,
        approvalRequest,
    };
}

    第二个方法 StoreApproval 是写入端。生成新 id，把 PendingApproval 存进共享字典，返回 id。前端之后把这个 id 发给 /chat/approve。

    Program.cs — app.Run() 之后的文件作用域 
    static string StoreApproval(
    ConcurrentDictionary<string, PendingApproval> approvals,
    string sessionId, AgentSession session, ToolApprovalRequestContent request)
{
    var approvalId = Guid.NewGuid().ToString("N");
    approvals[approvalId] = new PendingApproval(sessionId, session, request);
    return approvalId;
}

  5. 让 /chat 返回审批结构

    A2 的 /chat 只返回 { sessionId, answer }。 运行因审批而暂停时，调用方拿不到 approvalId， 无法弹出审批提示。注入 approvals 字典并改为返回 ToChatResponse，暂停的运行就会以 kind: "approval" 带上已存的 id 返回。

    Program.cs — replace the /chat endpoint 
    app.MapPost("/chat", async (ChatRequest request, AIAgent agent,
    ConcurrentDictionary<string, AgentSession> sessions,
    ConcurrentDictionary<string, PendingApproval> approvals,
    CancellationToken ct) =>
{
    if (string.IsNullOrWhiteSpace(request.Message))
        return Results.BadRequest(new { error = "message is required" });

    var (sessionId, session) = await GetOrCreateSessionAsync(
        request.SessionId, agent, sessions, ct);

    var response = await agent.RunAsync(request.Message, session, cancellationToken: ct);

    return Results.Ok(ToChatResponse(sessionId, session, response, approvals));
});

  6. 添加 POST /chat/approve 端点（endpoint）

    这是决定的写入端。它读回步骤 4 存的待审批项，用 TryRemove 移除条目（id 因此只能用一次），再用 CreateResponse 构造回复， 在同一会话上调 RunAsync 恢复运行。会话取自 pending.Session，所以对话历史保留。

    把 app.MapPost 加在路由块里、已有 /chat 之后。 ApproveRequest record 是文件作用域，放在 app.Run(); 之后、ChatRequest 等旁边。

    Program.cs — 路由块 
    app.MapPost("/chat/approve", async (ApproveRequest request, AIAgent agent,
    ConcurrentDictionary<string, PendingApproval> approvals, CancellationToken ct) =>
{
    if (string.IsNullOrWhiteSpace(request.ApprovalId)
        || !approvals.TryRemove(request.ApprovalId, out var pending))
        return Results.NotFound(new { error = "unknown or already-handled approvalId" });

    var reply = new ChatMessage(ChatRole.User,
        [pending.Request.CreateResponse(request.Approved, request.Reason ?? "")]);

    var response = await agent.RunAsync(reply, pending.Session, cancellationToken: ct);
    return Results.Ok(ToChatResponse(pending.SessionId, pending.Session, response, approvals));
});
    Program.cs — app.Run() 之后的文件作用域 
    internal sealed record ApproveRequest(string ApprovalId, bool Approved, string? Reason);

    TryRemove 让审批一次性。字典是审批登记表，id 一被移除就没了。 用同一个 id 再调会找不到，落进 NotFound 分支。

  7. 在流式端点中处理暂停信号（可选）

    流式端点边到边发 token，所以要自己处理暂停。更新里出现 ToolApprovalRequestContent 时不停下来，而是存下审批并发出 approval_request SSE 事件，浏览器据此弹出批准/拒绝提示。 本步可选，只在你接通了 A3 / C2 的流式端点时才做。

    把这两个新 case 加进 /chat/stream 的 await foreach 里那个已有 switch（A3 引入）。 同时把 ConcurrentDictionary<string, PendingApproval> approvals 加进处理器参数列表以注入单例。处理器签名如下，随后是完整循环体。

    Program.cs — /chat/stream 处理器签名（加上 approvals 参数） 
    app.MapPost("/chat/stream", async (HttpContext context, AIAgent agent,
    ConcurrentDictionary<string, AgentSession> sessions,
    ConcurrentDictionary<string, PendingApproval> approvals, CancellationToken ct) =>
    Program.cs — /chat/stream 的 await foreach（替换已有的 循环体） 
    await foreach (var update in agent.RunStreamingAsync(request.Message, session, cancellationToken: ct))
{
    foreach (var content in update.Contents)
    {
        switch (content)
        {
            case FunctionCallContent call:
                await SseEvent.WriteAsync(context.Response, "tool_call",
                    new { name = call.Name, arguments = call.Arguments }, ct);
                break;
            case ToolApprovalRequestContent approval:
                var approvalId = StoreApproval(approvals, sessionId, session, approval);
                var approvalCall = approval.ToolCall as FunctionCallContent;
                await SseEvent.WriteAsync(context.Response, "approval_request",
                    new { approvalId, toolName = approvalCall?.Name, arguments = approvalCall?.Arguments }, ct);
                break;
        }
    }

    if (!string.IsNullOrEmpty(update.Text))
        await SseEvent.WriteAsync(context.Response, "token", new { text = update.Text }, ct);
}

这套双端点（endpoint）流程端到端是怎么跑的

整个交互就两次 HTTP 调用。

  1. 第一次 —— POST /chat，问题需要无界限扫描。 模型选中 RunUnboundedSql，框架见到 ApprovalRequiredAIFunction 包装器就暂停，发出 ToolApprovalRequestContent。服务器存下它，返回 { kind: "approval", approvalRequest: { approvalId: "...", toolName: "RunUnboundedSql", arguments: {...} } }。运行挂起，还没跑任何 SQL。
  2. 第二次 —— POST /chat/approve，带 approvalId 和 approved: true/false。 端点移除条目（id 用掉），调 CreateResponse，在同一会话上恢复 RunAsync。批准则执行工具并作答；拒绝则灌入拒绝消息、不执行就作答。
🔧 说明

审批登记表在进程内存里。服务器重启后待审批项消失，客户端拿到 404。 生产环境要把审批队列存到后端（数据库、Redis）。本课用内存即可； 跨重启的持久性是 F2 的生产检查点（checkpoint）主题。

验证

✅ 关卡 — 未变绿前不要前进

第 1 步 —— 触发审批请求。

curl -s -X POST http://localhost:5200/chat \
  -H "Content-Type: application/json" \
  -d '{"message": "Across the entire otel_logs history with no time filter at all, what is the timestamp of the very first event ever recorded?"}' \
  | jq '{kind, approvalRequest}'

预期输出 —— 运行暂停，尚未执行任何 SQL：

{
  "kind": "approval",
  "approvalRequest": {
    "approvalId": "<some-id>",
    "toolName": "RunUnboundedSql",
    "arguments": { "query": "SELECT ..." }
  }
}

第 2 步 —— 批准并验证已执行。

curl -s -X POST http://localhost:5200/chat/approve \
  -H "Content-Type: application/json" \
  -d '{"approvalId": "<some-id>", "approved": true}' \
  | jq '{kind, answer}'

预期：kind: "answer"，并附带一段实质性的回复， 给出 otel_logs 中最早事件的时间戳。

第 3 步 —— 拒绝路径。

发起一个新的 /chat 问题来触发 审批，然后拒绝它：

curl -s -X POST http://localhost:5200/chat/approve \
  -H "Content-Type: application/json" \
  -d '{"approvalId": "<new-id>", "approved": false, "reason": "too expensive"}' \
  | jq '{kind, answer}'

预期：kind: "answer"，且回复文本 优雅地确认了这次拒绝（例如“我没能运行 这次全表扫描 —— 该请求被拒绝了”）。智能体不会崩溃 或返回一个空回复。

反向测试 —— 第二次使用已消费的 id 返回 404。 

curl -s -X POST http://localhost:5200/chat/approve \
  -H "Content-Type: application/json" \
  -d '{"approvalId": "<the-id-you-already-used>", "approved": true}' \
  | jq .error

预期： "unknown or already-handled approvalId"，HTTP 状态 404。这确认了审批是一次性的。

反向测试 —— 伪造的 id 同样返回 404。

curl -s -X POST http://localhost:5200/chat/approve \
  -H "Content-Type: application/json" \
  -d '{"approvalId": "doesnotexist", "approved": true}' \
  | jq .error

预期：相同的 404 错误体。

⚠️ 常见坑
  • 审批存了却没带上它的会话（session） → 智能体恢复时 没有对话历史，答案没根据或出错。永远把 AgentSession 存进待审批 record。
  • kind: "answer" 但答案为空或“我无法”，即使已批准 → 审批被重放到了错误的会话（新会话）。确认会话取自 pending.Session，而不是落实时从 GetOrCreateSessionAsync 取。
  • 第二次使用某个审批 id 没有返回 404 → 你在 approve 端点用普通字典赋值（approvals[id] = ...） 存审批，而不是用 TryRemove 移除。审批存活，可被重用。
  • 加了包装器后正常工具调用失效 → 你把不该关卡的工具也包了。只有 RunUnboundedSql 该包装， 其他工具都用普通 AIFunctionFactory.Create。
  • 智能体从不选 RunUnboundedSql → 工具名和描述没把它和 RunSql 区分开，模型偏爱更简单的工具。 让描述写明“WITHOUT the time-filter requirement”和“full-table scan”。
