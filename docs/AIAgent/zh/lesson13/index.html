第 13 课 · D3 · 模块 D — 组合与编排（orchestration）

智能体（agent）即工具（tool） + 模型分级（model tiering）

★★ Haiku + 1 次真实层级检查

你将学到什么

本课解决本应用里的两个真实问题。其一：D1 的每周报告工作流（workflow）只能从自己的 /report 端点运行，用户在对话中无法临时索要。你把整个报告工作流包装成 DataAnalyst 上一个可调用的工具（tool），让 LLM 自己决定何时运行它（智能体即工具，AsAIFunction）。其二：没有便宜的方式跑关卡（gate）。每处模型 id 已经从 ModelTiers（在 A1 引入）读取，但没有 Testing 覆盖时，每个关卡都打到生产层级——Analyst 是 Sonnet、Reasoning 是 Opus——测试循环烧真金白银。你加一个 appsettings.Testing.json 把三个层级全部塌缩到 Haiku，于是一个 --environment Testing 开关就让每个智能体都变便宜，无需改代码。

第一个手法处理谁调用谁；第二个处理哪个模型来执行这次调用。学完本课，项目里每个智能体都从同一个辅助方法读取模型，每周报告工作流也能在对话中途被调用，不再需要专门的派发步骤。

📘 讲解

智能体（agent）即工具（tool）（AsAIFunction）：任何 AIAgent 都暴露了一个 .AsAIFunction(AIFunctionFactoryOptions) 方法，它把整个智能体——它的工具、它的会话（session）、它的指令——包装成单个 AIFunction。把它注册到另一个智能体的 ChatOptions.Tools 里，外层 LLM 就会像调用任何其他函数那样调用它：传入一段自然语言提示，并把内层智能体的最终文本作为结果接收回来。这就是LLM 选择的派发：模型根据工具描述自行决定何时调用子智能体，这与 D2 中由代码选择的路由器（router）形成对比——后者通过对一个带类型的路由（routing）决策做模式匹配来派发。

模型分级（model tiering）（ModelTiers）：一个三行的静态辅助方法，把某个任务的推理需求映射到从 IConfiguration 读取的模型字符串。层级有： Light（分类、上下文压缩（compaction）摘要）、 Analyst（基于 schema 的 SQL 工作）、 Reasoning（跨领域综合）。默认值作为兜底烤进代码里； appsettings.json 按层级覆盖，而 appsettings.Testing.json 把三个层级全部覆盖成 Haiku，于是每个关卡（gate）都跑得很便宜。没有这层间接，每处调用点上硬编码的模型 id 对 Testing 覆盖是不可见的——Testing 环境设置的是 Models:Light、 Models:Analyst 和 Models:Reasoning，而不是一个个的字符串字面量。

动手构建

  1. 确认 ModelTiers 可用，并接好 Testing 覆盖

    Agents/ModelTiers.cs 在 A1 就已引入——它已经存在。这里不需要新建文件。这个三层辅助方法把推理需求映射到一个从 IConfiguration 读取的模型字符串，并把生产环境默认值作为兜底烤进代码里。

    ℹ️ 已存在 — A1/lesson01

    下面仅供参考重列。不要创建或覆盖此文件——它是在 A1 创建的。

    Agents/ModelTiers.cs (introduced in A1/lesson01) 
    using Microsoft.Extensions.Configuration;

namespace AiAgent.Agents;

/// <summary>
/// Model tiering: one place that maps a job's reasoning demand to a model.
/// Light = classification/summarization, Analyst = SQL-over-schema work,
/// Reasoning = cross-domain synthesis and recommendations.
/// Defaults live here; appsettings "Models" section overrides per tier.
/// </summary>
public static class ModelTiers
{
    public static string Light(IConfiguration config)
        => config["Models:Light"] ?? "claude-haiku-4-5";

    public static string Analyst(IConfiguration config)
        => config["Models:Analyst"] ?? "claude-sonnet-4-6";

    public static string Reasoning(IConfiguration config)
        => config["Models:Reasoning"] ?? "claude-opus-4-8";
}

    真正属于本课的工作：在 appsettings.Testing.json 里接好 Testing 覆盖，让所有层级在关卡期间塌缩到 Haiku。AgentFactory.cs、 Router.cs 和 ReportWorkflow.cs 里每处模型 id 已经从 ModelTiers.* 读取（你在 A1、D1、D2 就接好了），所以覆盖会自动触达它们。

    这里设置的键由三个 ModelTiers 方法读回。带 --environment Testing 运行时，.NET 配置加载器把本文件叠加到 appsettings.json 之上，于是 config["Models:Analyst"] 返回 Haiku，所有从 ModelTiers.Analyst(config) 读取的调用点都拿到 Haiku，无需改代码。 这是部分摘录——完整文件还包含一个在 E2 加入的 Logging 段： "Microsoft.Agents.AI": "Debug"。

  2. 把报告智能体作为一个具名工具注册到 DataAnalyst 上

    在 AgentFactory.cs 里，报告工作流（在 D1 构建）以一个 AIAgent 参数传入。在它上面调用 .AsAIFunction() 并给一段精确描述——这段描述是外层模型决定何时运行报告的唯一依据。把它和现有 SQL 工具一起注册进 ChatOptions.Tools，报告就成了 LLM 工具循环里可挑选的一个工具。

    本工厂里两个模型 id 已经从 ModelTiers.* 读取：DataAnalyst 用 ModelTiers.Analyst(config)，同工厂里的压缩摘要器用 ModelTiers.Light(config)，所以 Testing 覆盖会触达它们，这里无需改动。

  3. 注入报告智能体并更新 DI 注册

    AgentFactory.Create 新增的 reportAgent 参数在构建时由 DI 提供。Program.cs 里报告 AIAgent 已注册为键 "report" 的带键单例（来自 D1），DataAnalyst 注册用 GetRequiredKeyedService<AIAgent>("report") 读回并传入工厂。路由器、洞察智能体和报告工作流的注册已经用 ModelTiers.* 读取模型 id，自动流经配置并拾取 Testing 覆盖。

    两处注册都放在 var app = builder.Build() 之前。带键 "report" 单例必须在 DataAnalyst 单例之前注册，因为 DataAnalyst 工厂在构建时就解析这个键，键必须已存在。

  4. 给子智能体工具加上一段护栏描述

    你传给 AsAIFunction 的描述，是外层模型决定何时调用这个工具的唯一信号。两条规则：精确说明它做什么，并加上一条明确的成本警告，免得模型在随口一问的问题上也去伸手调它。你用的是：

    "Expensive — only when the user asks for the weekly report."

    没有这句话，LLM 会对任何沾上成本或工具的问题都去调用这个多智能体工作流（workflow）——在一个本该 Haiku 层级就能澄清的问题上，烧掉 Analyst 层级的额度。

模型分级与 Testing 覆盖

本项目里每个模型 id 都已经从 ModelTiers 读取——在 A1 引入，并自 D1、 D2 起一直使用。 AgentFactory.cs 里 DataAnalyst 用 ModelTiers.Analyst(config)、压缩摘要器用 ModelTiers.Light(config)；Router.cs 用 ModelTiers.Light(config)；ReportWorkflow.cs 里分析师用 ModelTiers.Analyst(config)、汇总器用 ModelTiers.Reasoning(config)。

因为选择集中在一个辅助方法里，一次配置改动就触达所有智能体。 appsettings.Testing.json 把三个层级都设为 Haiku，于是 dotnet run -- --environment Testing 让每个智能体都跑得便宜，无需改代码。调用点上的字面量模型字符串对这个覆盖是不可见的：Testing 文件设置的是 Models:Light、Models:Analyst、 Models:Reasoning，而不是一个个字面量。这正是把选择集中到 ModelTiers 的原因。

为什么用 AsAIFunction，而不是 D2 的路由器派发

D2 用代码派发：路由器（router）返回一个带类型的 RouteDecision，再由一个 switch 语句挑选处理器。本课的 AsAIFunction 用模型派发：外层智能体读取工具描述，在它自己的工具调用（tool call）循环中决定是否以及何时调用子智能体。这两种机制是互补的：

  • 代码选择（路由器（router））：确定、可审计，适合在构建时目录已知的能力菜单。
  • LLM 选择（AsAIFunction）：灵活的对话中组合——模型可以在一轮内把子智能体与其他工具串联起来、给它传入一段算出来的提示，或基于代码级路由器看不到的上下文跳过它。

两者并存：路由器（router）派发到 DataAnalyst 会话（session），而在那个会话内部，DataAnalyst 又能通过 run_weekly_report 调用报告工作流（workflow）——两层，两种不同的派发机制。

验证

✅ 关卡（gate） — 未变绿前不要前进

检查 1 — 智能体（agent）即工具（tool）在 chat 流上触发（Haiku）

从 Testing 环境开始（dotnet run -- --environment Testing）。用一段引导性提示 POST 到 /chat/stream： 

curl -s -N -X POST http://localhost:8124/chat/stream \
  -H "Content-Type: application/json" \
  -d '{"message": "please run the weekly report for the last 7 days"}'

你必须在流中看到一个 name: "run_weekly_report" 的 tool_call SSE 事件，随后是一个包含报告叙述的 token 事件，然后是 done。

检查 2 — 分级（model tiering）（那一次真实层级检查）

不带 Testing 覆盖只跑一轮：

dotnet run

向 /chat（路由器（router）那一轮）POST 一条消息，再向 /report（摘要器那一轮）POST 一条。然后查询你的 OTel traces 表——两种 span 类型都必须存在，且它们的 model_id 属性必须不同： 

-- In ClickHouse (or your OTel viewer)
SELECT
    SpanAttributes['gen_ai.request.model'] AS model_id,
    count() AS spans
FROM otel_traces
WHERE ServiceName = 'claudalytics-agent'
  AND Timestamp > now() - INTERVAL 5 MINUTE
GROUP BY model_id;

你应该至少看到两个不同的模型 id——Light 层级的路由器（router）和 Analyst/Reasoning 层级的摘要器。 检查完后立即切回 Testing。

反向测试

回到 Testing，POST 一个不提及每周报告的数据问题："which project spent the most last week?" 流中绝不能包含一个名为 run_weekly_report 的 tool_call 事件。如果真实层级检查里出现了相同的模型 id，说明配置没有流通——确认这次检查没有传 --environment Testing，appsettings.json 里是真实（非 Haiku）的 Models 值，并且每一处智能体调用点都用 ModelTiers.* 而不是字符串字面量。

⚠️ 常见坑
  • 子智能体在随口问的问题上被调用 → 描述太含糊。在 AsAIFunction 描述里加上 "Expensive — only when the user explicitly asks for the weekly report"。
  • 分层检查里模型 id 相同 → 某个调用点留着字面量模型字符串，而不是 ModelTiers.* 调用。在所有 .cs 文件里搜索 "claude-； ModelTiers.cs 之外的每一处命中都要改掉。
  • Testing 覆盖没有效果 → 检查 -- 分隔符和环境名；完整细节见 L0。
  • 报告智能体的带键服务没被解析出来 → DataAnalyst 工厂收到的 reportAgent 是 null。在构建 DataAnalyst 时确保用的是 GetRequiredKeyedService<AIAgent>("report")——而不是 GetRequiredService<AIAgent>。
  • 内层智能体复用了外层会话（session） → 通过 AsAIFunction 调用时，子智能体每次调用都跑一个全新的临时会话（不传任何 session 参数）。这是对的。不要把外层智能体的 AgentSession 传进子智能体的工具选项里。
