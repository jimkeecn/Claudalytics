第 03 课 · A3 · 模块 A — Hello agent

流式返回答案（SSE）

★★ Haiku

你将学到什么

Claudalytics Copilot 用户问“我有哪些项目”时，agent 要跑 ClickHouse 查询再写一段答案。现在用户得看着加载圈等整轮结束，才一次性看到全部文字。 流式（Streaming） 用 RunStreamingAsync 运行 agent，在每个 token 产出时立即通过 Server-Sent Events（SSE） 连接发给客户端。

本课新增 /chat/stream endpoint，把四种流式更新映射到四种 SSE 事件：session、token、tool_call、 done。approval 处理（approval_request）放到后面的 C3/第10课，A3 的流不带 approval。

📘 讲解

流式（streaming）运行与更新流

MAF 的 AIAgent 暴露了两个运行方法。你已经在 A1 中认识了阻塞式的那个：

  • RunAsync(message, session) —— 等待整轮完成， 返回一个 AgentResponse。
  • RunStreamingAsync(message, session) —— 返回一个 IAsyncEnumerable<StreamingChatMessageUpdate>。 序列中的每一项都是一次部分更新，在模型产出它的那一刻立即发出。

一个 StreamingChatMessageUpdate 携带两样你关心的东西：

  • update.Text —— 当模型在本次更新中产出了文本 token 时， 它是一个非空字符串。这就是你要立即转发的部分单词或短语。
  • update.Contents —— 一个有类型的内容项列表。 这里要关注的是 FunctionCallContent（模型选择调用的 工具，tool）。还有第二种内容类型 ToolApprovalRequestContent，会在后面的 C3/第10课 中引入，用于那些 在执行前需要人工签批的工具；A3 不处理它。

SSE 格式很小：每个事件两行，后面跟一个空行。

event: token
data: {"text":"Hello, "}

event: token
data: {"text":"world!"}

event: done
data: {}

客户端读到每个 event:/data: 对就立即反应。 关键是每次写入后都要 flush：ASP.NET 响应体默认带缓冲， 没有显式 FlushAsync 的话，“流”就只是一个很慢的单次响应。

四种 SSE 事件类型

你在 /chat/stream 上恰好用四个事件名。知道各自由什么 触发，更新循环里的判断就很好读。

事件 何时触发 关键负载字段
session 在流开始之前，仅一次——携带客户端在后续请求中应回传的会话（session） id。 sessionId
token 在每次 update.Text 非空的更新时触发。 text
tool_call 对 update.Contents 中的每个 FunctionCallContent 触发。 name、arguments
done 在 await foreach 正常结束之后，仅一次。 （空对象）

当运行抛出异常时，会在 catch 块中发出一个 error 事件来 代替 done。

动手实现

  1. 添加 SseEvent 辅助方法

    每次 SSE 写入都做两件事：序列化为 JSON，再 flush 响应体。第 3 步的 流式循环会多次调用它，所以抽成一个方法。把它作为文件级 static class 放在 Program.cs 底部，app.Run(); 之后。

    🔧 说明

    必需的 using（不在隐式 usings 中）：在 Program.cs 顶部加上 using System.Text.Json;。 JsonSerializer 就在这个命名空间里，并且不在默认 ASP.NET 隐式 usings 集合中。

    Program.cs 
    internal static class SseEvent
{
    private static readonly JsonSerializerOptions JsonOptions =
        new(JsonSerializerDefaults.Web);

    public static async Task WriteAsync(
        HttpResponse response, string eventName, object data, CancellationToken ct)
    {
        await response.WriteAsync(
            $"event: {eventName}\ndata: {JsonSerializer.Serialize(data, JsonOptions)}\n\n", ct);
        await response.Body.FlushAsync(ct);
    }
}

    data: 后的双换行（\n\n）是 SSE 记录分隔符， 告诉 EventSource 事件已完整；省略它客户端会卡到连接关闭。 没有 FlushAsync，token 会在内存里排队，运行结束时一次性发出， 就不是流了。

  2. 在流打开之前接好 session

    /chat/stream endpoint 读请求体，用 A2 的 GetOrCreateSessionAsync 解析或创建 session，设好 SSE 响应头， 先发一个 session 事件。客户端存下 sessionId， 下一条消息回传它，agent 就能保持多轮记忆。

    🔧 说明

    第 2 步和第 3 步是同一个 MapPost 处理器， 拆成了两个代码片段。 第 2 步打开这个 lambda，第 3 步把它收尾。收尾的 }); 出现在第 3 步的末尾。把两个片段在 Program.cs 中连续粘贴——放在其它 app.Map… 调用之间（在 var app = builder.Build(); 之后、 app.Run(); 之前）——以构成一个完整的 app.MapPost("/chat/stream", …); 调用。

    必需的 usings（如果尚未存在，请加到 Program.cs 顶部）：

    • using Microsoft.Extensions.AI; —— 流式循环内部 检查的有类型内容项 FunctionCallContent 需要它。 这个命名空间不在默认隐式 usings 集合中。

    假定已有的符号（从 A1/A2 沿用过来）： ChatRequest、AgentSession、 GetOrCreateSessionAsync。这三个必须已经从 A1 和 A2 课中存在于 Program.cs 里。 （PendingApproval 和 StoreApproval 会在后面的 C3/第10课 中引入——这里 并不需要它们。）

    Program.cs 
    app.MapPost("/chat/stream", async (HttpContext context, AIAgent agent,
    ConcurrentDictionary<string, AgentSession> sessions, CancellationToken ct) =>
{
    var request = await context.Request.ReadFromJsonAsync<ChatRequest>(ct);
    if (request is null || string.IsNullOrWhiteSpace(request.Message))
    {
        context.Response.StatusCode = StatusCodes.Status400BadRequest;
        return;
    }

    var (sessionId, session) =
        await GetOrCreateSessionAsync(request.SessionId, agent, sessions, ct);

    context.Response.Headers.ContentType = "text/event-stream";
    context.Response.Headers.CacheControl = "no-cache";
    await SseEvent.WriteAsync(context.Response, "session", new { sessionId }, ct);

    设置 Content-Type: text/event-stream 和 Cache-Control: no-cache 是 SSE 规范要求的。少了 content-type 头， 代理和负载均衡器可能缓冲整个响应。

  3. 驱动流式循环

    调用 RunStreamingAsync，用 await foreach 读每个更新。 循环里先看 update.Contents，再看 update.Text， 各发对应 SSE 事件。正常结束后发 done，抛异常则发 error。 客户端靠 done 知道本轮结束。

    🔧 说明

    这个片段接续并收尾第 2 步打开的 app.MapPost lambda。 最后那个 }); 同时关闭 lambda 体和 MapPost 调用——不要再加第二个。

    Program.cs 
        try
    {
        await foreach (var update in
            agent.RunStreamingAsync(request.Message, session, cancellationToken: ct))
        {
            foreach (var content in update.Contents)
            {
                if (content is FunctionCallContent call)
                {
                    await SseEvent.WriteAsync(context.Response, "tool_call",
                        new { name = call.Name, arguments = call.Arguments }, ct);
                }
            }

            if (!string.IsNullOrEmpty(update.Text))
                await SseEvent.WriteAsync(context.Response, "token",
                    new { text = update.Text }, ct);
        }

        await SseEvent.WriteAsync(context.Response, "done", new { }, ct);
    }
    catch (Exception ex)
    {
        await SseEvent.WriteAsync(context.Response, "error",
            new { message = ex.Message }, ct);
    }
});

    为什么先看 Contents 再看 Text？单次更新可能两者都有： 模型在同一块里既发 tool call 又发文本。contents 循环处理结构化的 tool call， 文本检查随后运行。同一次更新两个事件都发是正确的。

  4. 为什么 session 事件要放在 try 块之前

    session 事件写在 try 块之前。即便运行立即失败， 客户端也需要 session id。若它在 try 里、agent 在第一个 token 就抛异常， 客户端只会收到没有 id 的 error，无法在同一 session 里重试。 先发 session 保证 id 一定送达。

更新流如何映射到 agent 的 tool 循环

事件的时序能解释终端里看到的东西。一个带 tool call 的完整 agent 轮次， 大致按这个顺序产生更新：

  1. 零个或多个 token 事件——模型在决定调用工具之前“出声 思考”的文本（有些模型会发这个，有些不会）。
  2. 一个 tool_call 事件——模型确定要调用某个函数。
  3. 静默——MAF 在本地执行工具；执行期间没有更新流出。
  4. 更多 token 事件——模型看到工具结果之后的答案。
  5. done。

如果智能体调用了多个工具（例如先查 schema 再做一次 SQL 查询），那么 tool_call / 静默 的模式会在最终答案 token 到达之前重复 出现。done 事件总是最后一个，并且恰好只发出一次。

验证

✅ 关卡（gate） — 未变绿前不要前进

从 Testing 环境开始（A1 起就有的强制仪式）： 

dotnet run -- --environment Testing

控制台必须打印 Hosting environment: Testing。

用 curl 发送一个流式请求——观察 token 逐步到达： 

curl -s -N -X POST http://localhost:8124/chat/stream \
  -H "Content-Type: application/json" \
  -d '{"message": "What projects do I have?"}'

-N 标志会禁用 curl 自身的输出缓冲，这样你就能在每个 SSE 事件到达时看到它。预期的输出形态（具体文本会有所不同）： 

event: session
data: {"sessionId":"a3f1..."}

event: tool_call
data: {"name":"list_projects","arguments":{}}

event: token
data: {"text":"You have "}

event: token
data: {"text":"three projects: "}

event: token
data: {"text":"claudalytics, ..."}

event: done
data: {}

变绿检查：

  • session 事件最先到达，在任何 token 之前。
  • 至少出现一个 tool_call 事件（智能体（agent）调用了 list_projects 或等价的工具）。
  • 到达多个 token 事件，每个都带一小段文本片段—— 而不是一整个大块。
  • 流以 done 结束，而不仅仅是连接被关闭。

反向测试——检测缓冲：

如果你只看到一个包含整个答案的 token 事件，紧接着就是 done，那说明响应被缓冲了。检查两件事：

  1. SseEvent 里每个 WriteAsync 之后是否 调用了 FlushAsync？如果它缺失，token 会在 ASP.NET 的 缓冲里排队，等连接关闭时一股脑全部释放。
  2. 你的 curl 和应用之间是否有反向代理（nginx、YARP、IIS 后的 Kestrel）？除非配置了 proxy_buffering off 或等价设置， 否则代理通常会缓冲 SSE。

用第 1 步拿到的会话 id 做后续追问：

curl -s -N -X POST http://localhost:8124/chat/stream \
  -H "Content-Type: application/json" \
  -d '{"message": "Which of those is most expensive?", "sessionId": "a3f1..."}'

答案应当引用第一轮里的那些项目。来自 A2 的同一套多轮记忆在这里也能 生效，因为 RunStreamingAsync 接受与 RunAsync 相同的 AgentSession 参数。

⚠️ 常见坑
  • 一整个大块 token，然后才 done → 在 SseEvent.WriteAsync 里缺了 FlushAsync。 ASP.NET 会缓冲响应体；如果每次写入之后没有显式刷新，所有事件都会 被攒在内存里，等运行结束时一起发出。在 WriteAsync 之后加上 await response.Body.FlushAsync(ct)。
  • 客户端在最后一个 token 之后挂住，永远不关闭 → done 事件从未发出。当 done 写入位于 try 里，但排在某个抛出异常的语句之后从而被跳过时， 就会发生这种情况。done 写入必须是 try 块 里的最后一条语句，并且 catch 必须改为发出 error。实现了 EventSource 的浏览器在缺少 done 时会无限重连。
  • 没有 tool_call 事件，但答案却提到了工具（tool）结果 → 工具是在更上层某处通过 RunAsync（非流式路径）调用 的，或者端点（endpoint）悄悄路由（routing）到了一个非流式处理器。确认请求打到的是 /chat/stream 而不是 /chat。
  • 客户端没有收到会话（session） id → session 事件位于 try 块内、且在流式调用已经开始之后，因此一个 早期错误会把它丢弃。把 session 写入移到 try 块之前——它必须是设置响应头之后的第一个写入。
  • 代理 / 负载均衡器缓冲了流 → 在第一次写入之前， 给响应设置 Content-Type: text/event-stream 和 Cache-Control: no-cache。大多数代理会遵守这些头来 禁用缓冲。在 nginx 中，给 SSE 路由加上 proxy_buffering off;。
