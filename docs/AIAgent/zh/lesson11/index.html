周报：手搓图 → 构建器语法糖

★★ Haiku

你将学到什么

周报需要三个分析师（analyst）同时跑，再由一个写手汇总。预制构建器 BuildConcurrent 和 BuildSequential 几行就能做到，但一旦它们出错（并发退化成顺序、取错消息、追踪看不出并发）， 把它们当魔法就没法调试。所以你先手工搭一遍，看清它们生成的那张图。

你会构建两遍：v1 用来自 B1–B3 的原始 WorkflowBuilder 手工连线；v2 用预制构建器重写， 发现两者生成同一张图。手搓的 v1 只是用来揭示构建器生成的图——你保留 v2。 它的作用是 让你看清底层的图，以便日后调试任何编排（orchestration）形态。

📘 讲解

模块 D 中三个新的 API 面：

  • AgentWorkflowBuilder.BuildConcurrent(agents) — 把列出的所有智能体（agent）作为单个工作流超步（superstep）并行扇出（fan-out）； 聚合后的输出流向下一阶段。 等价于原始构建器里的一条扇出边（edge）加一道扇入屏障（fan-in barrier）。
  • AgentWorkflowBuilder.BuildSequential(agents) — 把智能体一个接一个串联起来，每个都把上一个智能体的输出当作自己的输入。 等价于一连串直连的边（edge）。
  • workflow.AsAIAgent(name, description) — 把任意工作流包装成单个 AIAgent。调用方只看到一个智能体； 框架在内部执行完整的图。这就是概念 #10（工作流即智能体）——它可组合： 你可以把工作流智能体嵌套进更大的工作流（workflow）里。

数据契约：每个分析师都收到用户的提示词。它的输出进入工作流的对话记录（transcript）。 汇总器把之前所有智能体的聚合对话记录作为自己的上下文（context）——这正是为什么 “Do not call tools”（不要调用工具（tool））这条指令对汇总器是关键所在： 等它运行时，事实数据早已存在于消息历史中。

动手构建

  1. 编写分析师指令

    三个分析师智能体（agent）各自需要一段聚焦的提示词：一个调查成本，一个调查安全信号， 一个调查工具（tool）健康度。它们共享一个共同契约——“不要客套，不要反问， 你的输出会喂给另一个智能体”——所以你把它放进一个共享常量里强制执行， 再在其上插入各领域的具体范围。

    汇总器则不同：它收到来自全部三位分析师的发现，必须在不调用任何工具（tool）的情况下， 拼出一份连贯的 markdown 报告。 Do not call tools 这道防护是强制性的——少了它， 汇总器可能会试图自己去采集数据，使成本翻倍并产出杂乱无章的结果。

    ℹ️ 累积状态

    Instructions.SchemaDoc 是一个定义在 Agents/Instructions.cs（在 A1 中引入）里的 const string。它内嵌了 ClickHouse 表的 schema， 这样每个用到它的智能体（agent）都会自动获得最新的列信息。 ModelTiers.Analyst(config) 和 ModelTiers.Reasoning(config) 来自 Agents/ModelTiers.cs，同样在 A1 中引入——它已经就绪，直接用即可。

  2. v1 — 手工搭建图（概念草图）

    只用来自 B1 的原始 WorkflowBuilder，你就能手工搭出这条流水线。 它的形态是：从单条起始消息扇出（fan-out）到三个分析师执行器（executor）节点（node）； 一道扇入屏障（fan-in barrier）等待这三者全部完成；聚合后的输出喂给一个汇总器执行器节点。 下面的标签页对比了这两个版本。

    ⚠️ 请勿编译 — 仅为示意伪代码

    下面的 v1 片段用到了 ReportRequest、AnalystFindings、 AggregatedFindings 和 WorkflowBuilder.StartNodeName ——这些类型在 MAF 中 并不存在，会产生编译错误。这只是一段概念草图， 用来展示 BuildConcurrent / BuildSequential 在内部生成的图形态。 只有 v2 标签页（ReportWorkflow.cs）才是真实代码。 

    // v1: ILLUSTRATIVE PSEUDOCODE — do NOT compile.
// These types (ReportRequest, AnalystFindings, AggregatedFindings,
// WorkflowBuilder.StartNodeName) do not exist in MAF.
// Purpose: show the graph shape that BuildConcurrent / BuildSequential
// produce internally — once you understand the shape, use the v2 form.

var builder = new WorkflowBuilder();

// Three analyst agent-nodes
builder.AddNode<ReportRequest, AnalystFindings>("CostAnalyst",
    async (msg, ctx, ct) =>
    {
        var result = await costAnalyst.RunAsync(msg.Prompt, ct);
        return new AnalystFindings("CostAnalyst", result.Text);
    });

builder.AddNode<ReportRequest, AnalystFindings>("SecurityAnalyst",
    async (msg, ctx, ct) =>
    {
        var result = await securityAnalyst.RunAsync(msg.Prompt, ct);
        return new AnalystFindings("SecurityAnalyst", result.Text);
    });

builder.AddNode<ReportRequest, AnalystFindings>("ToolingAnalyst",
    async (msg, ctx, ct) =>
    {
        var result = await toolingAnalyst.RunAsync(msg.Prompt, ct);
        return new AnalystFindings("ToolingAnalyst", result.Text);
    });

// Fan-out: one input message -> all three analyst nodes
builder.AddFanOutEdge<ReportRequest>(
    sourceNode: WorkflowBuilder.StartNodeName,
    targetNodes: ["CostAnalyst", "SecurityAnalyst", "ToolingAnalyst"],
    partitioner: (msg, idx) => msg);   // same prompt to each

// Fan-in barrier: all three findings -> summarizer
builder.AddFanInEdge<AnalystFindings, AggregatedFindings>(
    sourceNodes: ["CostAnalyst", "SecurityAnalyst", "ToolingAnalyst"],
    targetNode: "Summarizer",
    aggregator: findings => new AggregatedFindings(findings));

builder.AddNode<AggregatedFindings, string>("Summarizer",
    async (msg, ctx, ct) =>
    {
        var context = string.Join("\n\n", msg.Items.Select(f => f.Content));
        var result = await summarizer.RunAsync(context, ct);
        return result.Text;
    });

builder.SetOutputNode("Summarizer");
var workflow = builder.Build();
// To expose as one agent: workflow.AsAIAgent("telemetry-report", "...")

using Microsoft.Extensions.AI;

namespace AiAgent.Agents;

public static class ReportWorkflow
{
    public static AIAgent Create(IConfiguration config, SchemaTools tools, AnalysisTools analysis)
    {
        var apiKey = config["ANTHROPIC_API_KEY"]
            ?? throw new InvalidOperationException("ANTHROPIC_API_KEY is not set.");

        IAnthropicClient client = new AnthropicClient { ApiKey = apiKey };

    然后选模型层级（tier）和工具列表。三个分析师要用 SQL 采集数据， 所以跑在便宜的 Analyst 层并拿到 SQL 工具； 汇总器只写文字，跑在 Reasoning 层且不给工具。 sqlTools 列表在下一段传给每个分析师。 

            var analystModel = ModelTiers.Analyst(config);
        var reasoningModel = ModelTiers.Reasoning(config);

        List<AITool> sqlTools =
        [
            AIFunctionFactory.Create(tools.GetSchema),
            AIFunctionFactory.Create(tools.RunSql),
            AIFunctionFactory.Create(tools.ListProjects),
            AIFunctionFactory.Create(analysis.CostBreakdown),
            AIFunctionFactory.Create(analysis.SessionDeepDive),

    接着建四个智能体并组装图。BuildConcurrent 把三个分析师包成并行扇出，AsAIAgent 再把它打包成一个名为 "Analysts" 的智能体。 BuildSequential 把它放到汇总器之前， 汇总器读到聚合后的分析师输出；外层 AsAIAgent 把整张图暴露为 "telemetry-report"，由 /report 端点解析。 

            var costAnalyst    = CreateAnalyst(client, analystModel,   "CostAnalyst",     AnalystInstructions.Cost,     sqlTools);
        var securityAnalyst = CreateAnalyst(client, analystModel,  "SecurityAnalyst",  AnalystInstructions.Security, sqlTools);
        var toolingAnalyst  = CreateAnalyst(client, analystModel,  "ToolingAnalyst",   AnalystInstructions.Tooling,  sqlTools);
        var summarizer      = CreateAnalyst(client, reasoningModel, "Summarizer",       AnalystInstructions.Summarizer, tools: null);

        var analystsWorkflow = AgentWorkflowBuilder.BuildConcurrent(
            [costAnalyst, securityAnalyst, toolingAnalyst]);

        var analystsAgent = analystsWorkflow.AsAIAgent(
            name: "Analysts",
            description: "Runs cost, security and tooling analysts concurrently.");

        var reportWorkflow = AgentWorkflowBuilder.BuildSequential([analystsAgent, summarizer]);

        return reportWorkflow.AsAIAgent(
            name: "telemetry-report",
            description: "Produces a Claude Code telemetry report for the requested window.");
    }

    最后是建每个分析师的辅助方法。它用 UseOpenTelemetry 让每个分析师发出各自的 invoke_agent span， 追踪时间线上三者重叠就是并发的证据。 AgentFactory.OtelSourceName 来自 Agents/AgentFactory.cs（在 C2 中引入），已经就绪。 

        private static AIAgent CreateAnalyst(
        IAnthropicClient client, string model, string name, string instructions, List<AITool>? tools)
    {
        var agent = client.AsAIAgent(model: model, instructions: instructions, name: name, tools: tools);

        return agent.AsBuilder()
            .UseOpenTelemetry(AgentFactory.OtelSourceName)
            .Build();
    }
}
    ℹ️

    为什么要嵌套两次 AsAIAgent 调用？ 内层调用把并发扇出包装成一个名为 "Analysts" 的整体单元。 外层的 BuildSequential 随后把这整块并发块当作汇总器之前的 一个阶段来处理。这种两级嵌套——顺序里套并发—— 正是用 MAF 惯用方式表达“这些全部并行，然后这一个”的写法。

  3. 接一个共享 runner，避免重复的调用逻辑

    /report 端点（endpoint）和 D2 的菜单注册表都会调用同一个工作流智能体（agent），所以把“取最后一条消息、收集作者名”抽成一个静态辅助方法。

    工作流智能体返回的是完整对话记录（transcript），不是一个字符串。辅助方法从中读两样东西： 成品是最后一条非空消息（汇总器的报告），前面的是分析师发现； AgentsInvolved 收集去重后的作者名。/report 端点把 AgentsInvolved 放进 JSON，供验证步骤确认四个智能体都跑过。

    Agents/ReportRunner.cs 
    using Microsoft.Agents.AI;

namespace AiAgent.Agents;

public static class ReportRunner
{
    public static async Task<(string Report, List<string> AgentsInvolved)> RunAsync(
        AIAgent reportAgent, string window, CancellationToken ct)
    {
        var response = await reportAgent.RunAsync(
            $"Produce the report for {window}.", cancellationToken: ct);

        var lastMessage = response.Messages.LastOrDefault(m => !string.IsNullOrWhiteSpace(m.Text));
        var agentsInvolved = response.Messages
            .Select(m => m.AuthorName)
            .Where(author => !string.IsNullOrEmpty(author))
            .Distinct()
            .Select(author => author!)
            .ToList();

        return (lastMessage?.Text ?? response.Text, agentsInvolved);
    }
}

  4. 注册工作流（workflow）智能体（agent）并暴露端点（endpoint）

    把工作流（workflow）智能体（agent）注册为带键单例（keyed singleton）——之所以带键，是因为 DI 容器里还持有主 DataAnalyst（一个无键的 AIAgent），两者绝不能冲突。 /report 端点（endpoint）返回 JSON； /report/stream 端点发出带有逐智能体步骤事件的 SSE， 这样客户端就能在每位分析师完成时渲染进度。

    ℹ️ 已就绪

    [FromKeyedServices] 位于 Microsoft.Extensions.DependencyInjection 命名空间，最小 API 宿主已包含——无需额外 using。 SseEvent 是 A2 中引入的静态辅助方法，已在 Program.cs 里。每段下面都注明放置位置。

    先是 DI 注册，放在 DI 区块里、var app = builder.Build(); 之前。键 "report" 让它与无键的 DataAnalyst 区分开；端点用 [FromKeyedServices("report")] 解析，两处键字符串必须一致。

    Program.cs (excerpts) 
    builder.Services.AddKeyedSingleton<AIAgent>("report", (sp, _) => ReportWorkflow.Create(
    sp.GetRequiredService<IConfiguration>(),
    sp.GetRequiredService<SchemaTools>(),
    sp.GetRequiredService<AnalysisTools>()));

    然后是 /report 端点，放在 var app = builder.Build(); 之后。它调用 ReportRunner，把报告和 agentsInvolved 列表作为 JSON 返回。 

    app.MapPost("/report", async (ReportRequest? request,
    [FromKeyedServices("report")] AIAgent reportAgent, CancellationToken ct) =>
{
    var window = string.IsNullOrWhiteSpace(request?.Window) ? "the last 7 days" : request.Window;
    var (report, agentsInvolved) = await ReportRunner.RunAsync(reportAgent, window, ct);
    return Results.Ok(new { report, agentsInvolved });
});

    再是 /report/stream 端点。它流式跑，作者名每变一次就发一个 agent_step 事件，客户端据此显示当前分析师； 验证步骤用这些事件的先后顺序证明分析师是并行跑的。 

    app.MapPost("/report/stream", async (ReportRequest? request, HttpContext context,
    [FromKeyedServices("report")] AIAgent reportAgent, CancellationToken ct) =>
{
    var window  = string.IsNullOrWhiteSpace(request?.Window) ? "the last 7 days" : request!.Window;

    context.Response.Headers.ContentType = "text/event-stream";
    context.Response.Headers.CacheControl = "no-cache";

    try
    {
        string? currentAgent = null;
        await foreach (var update in reportAgent.RunStreamingAsync(
            $"Produce the report for {window}.", cancellationToken: ct))
        {
            if (!string.IsNullOrEmpty(update.AuthorName) && update.AuthorName != currentAgent)
            {
                currentAgent = update.AuthorName;
                await SseEvent.WriteAsync(context.Response, "agent_step", new { agent = currentAgent }, ct);
            }
            if (!string.IsNullOrEmpty(update.Text))
                await SseEvent.WriteAsync(context.Response, "token",
                    new { agent = currentAgent, text = update.Text }, ct);
        }
        await SseEvent.WriteAsync(context.Response, "done", new { }, ct);
    }
    catch (Exception ex)
    {
        await SseEvent.WriteAsync(context.Response, "error", new { message = ex.Message }, ct);
    }
});

    最后在文件作用域、app.Run(); 之后，与其它请求 record 一起声明： internal sealed record ReportRequest(string? Window);

为什么这个揭示很重要

v1 的图和 v2 的构建器调用产生的是同样的运行时执行： 三个并发的超步（superstep）节点（node），后面跟一个顺序节点。 区别纯粹在于你要亲自承担多少记账工作。原始构建器让你能自定义分区器（partitioner）、 边（edge）谓词（edge predicate）和自定义执行器（executor）——你在 B1–B3 中就会这么做，在 F2 的调查流水线里还会再来一遍。 高层构建器以放弃控制力为代价，换来了简洁。 既然你两者都见过了，就能为每种情况选对合适的抽象层级。

7 段脉络中的第 3 段。上面手搓的 v1 图只是用来揭示构建器生成的图—— 它唯一的用途就是揭开语法糖的神秘面纱；你保留 v2。这里创建的 v2 ReportWorkflow 会在 D2（路由器（router） + 菜单注册表）中 成为一个一等公民式的菜单项，在 D3 中被包装为 DataAnalyst 上的“智能体（agent）即工具（tool）”， 并一路延续到毕业项目，在那里通过 A2A 对外暴露。

检查 2 — 分析师步骤在流式（streaming）输出中交错出现（说明并发是真的）： 

curl -s -N -X POST http://localhost:8124/report/stream \
  -H "Content-Type: application/json" \
  -d '{"window":"last 7 days"}'
# You MUST see agent_step events for CostAnalyst, SecurityAnalyst, and ToolingAnalyst
# BEFORE the agent_step event for Summarizer.
# The three analyst steps may appear in any order relative to each other (they ran in parallel).
# The Summarizer agent_step MUST be the last one before "done".

检查 3 — v1 和 v2 产生等价的结构：

如果你在替换之前在本地搭过 v1：两者都应返回一份带有 ## Cost、## Security、## Tooling 和 ## Highlights 各小节的 markdown 文档。 具体措辞会有差异（LLM 输出），但这些小节标题足以证明跑的是同一种流水线形态。

反向测试 — 扇出（fan-out）退化成了顺序：

如果三个分析师的 agent_step 事件严格按顺序出现 （每个各有一个 done 事件，时间戳没有交错）， 那么并发扇出就没起作用——这些智能体（agent）是一个接一个被运行的。 请确认 BuildConcurrent 在用 AsAIAgent 包装之前 被应用到了全部三个分析师上，而不是用了 BuildSequential。

⚠️ 常见坑
  • 分析师以对话口吻回应，而不是在做报告 → 提示词契约“你的输出会喂给另一个智能体（agent）”缺失了。 少了它，模型会反问澄清性问题或加入客套话， 这会污染汇总器的上下文（context），产出一份混乱的报告。 AnalystCommon 常量负责强制执行这一点。
  • 汇总器调用了 SQL 工具并捏造数据 → 汇总器在 CreateAnalyst 中传入的是 tools: null。如果不小心给它传了工具（tool）， 汇总器有时会试图自己去采集数据——成本翻倍，而且依据不一致。 此外：如果指令里没有 “Do not call tools”，即便是没有工具的汇总器， 也可能声称自己无法作答，因为它“没有数据访问权限”。
  • 找不到带键注册——DI 在启动时抛错 → 端点用的是 [FromKeyedServices("report")]； 如果注册时用了不同的键字符串（或注册时没带键）， 应用会在首次请求时崩溃，而非在启动时崩溃。 请确认 AddKeyedSingleton 和端点特性两处的键字符串完全一致。
  • 从对话记录里取错了消息 → 对工作流（workflow）智能体（agent）调用 RunAsync 返回的是完整的对话记录。 取 response.Text 只会得到最后一次更新，可能并不完整。 ReportRunner 用的是 response.Messages.LastOrDefault(m => !string.IsNullOrWhiteSpace(m.Text)) ——最后一条非空消息——它可靠地就是汇总器的输出。
  • OTel span 显示不出并发 → 每个分析师都需要自己的 UseOpenTelemetry 调用（在 CreateAnalyst 里完成）。 少了它，分析师们会共享默认的 span 上下文， 即使图是并发跑的，追踪时间线也会塌缩成一条看起来像顺序执行的线。
