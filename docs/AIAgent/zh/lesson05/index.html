第 05 课 · B2 · 模块 B — 图

观察图的运行：工作流（workflow）事件

★★ 无需 LLM

你将学到什么

一次 Claudalytics Copilot investigation 在图里要跑很多步：规划探针、运行、校验、写报告。没有 event，你看不到哪个 probe 在跑、为什么某个失败，也无法把进度推给 UI。运行结束之前，整个过程就是一个黑盒。

每次 workflow 运行都会发出一条带类型的实时 event 流，你从手头已有的同一个 StreamingRun 上读取它。本课你将搭建一个 driver 读取这条流，在产出结果的同时生成事件时间线，并学会从 executor 内部发出自己的 event。学完 B2，你就有了一扇随图运行的调试窗口。

📘 讲解

内置的事件流

当你调用 InProcessExecution.RunStreamingAsync(…) 时，会拿回一个 StreamingRun。在它上面调用 run.WatchStreamAsync(ct)，即可得到一个 IAsyncEnumerable<WorkflowEvent>。框架会自动发出下面这些具体子类型：

  • WorkflowStartedEvent — 运行已经开始。
  • SuperStepStartedEvent / SuperStepCompletedEvent — 一次前沿（frontier）推进：一批同时触发的并发节点（node）。
  • ExecutorInvokedEvent — 一个命名的执行器（executor）即将运行；携带 ExecutorId。
  • ExecutorCompletedEvent — 该执行器正常结束。
  • ExecutorFailedEvent — 执行器抛出了异常；异常对象就在 evt.Data 里。调用 .GetBaseException().Message 把根因暴露出来——默认的 .ToString() 会是一大堵堆栈墙。
  • WorkflowOutputEvent — 某个 [YieldsOutput] 执行器产出了最终结果；从 evt.Data 读取它。
  • RequestInfoEvent — 运行被暂停，正等待人工回应（在 F2 中完整讲解）。

从执行器（executor）内部发出自定义事件

任何执行器都可以调用 await context.AddEventAsync(new MyEvent(…), ct)。该事件会出现在事件流里，位于其外层的 ExecutorInvokedEvent 与 ExecutorCompletedEvent 之间。你的自定义类必须继承 WorkflowEvent，并把它的负载（payload）传给基类构造函数。

事件如何映射到你在 B1 里构建的图

回顾 B1 中的流水线：一个规划器（planner）节点（node）扇出（fan-out）三个探针（probe）任务，三个探针执行器（executor）并行运行，一个扇入屏障（fan-in barrier）把结果汇给收集器（collector），随后产出输出。事件流让这套结构在 运行时变得可见：

  • 三个探针执行器的 ExecutorInvokedEvent 共享 同一对 SuperStepStartedEvent / SuperStepCompletedEvent 括号——这证明扇出的并行是真实存在的。
  • 收集器的 ExecutorInvokedEvent 只会在三个探针的 ExecutorCompletedEvent 全部出现之后才登场——这正是扇入屏障在落实它"等待全部完成"的契约。
  • 如果你弄坏某个探针的 SQL，一个 ExecutorFailedEvent 会指名道姓地点出是哪个执行器，并携带异常——无需猜哪个节点失败了。

动手构建

  1. 定义自定义进度事件

    继承 WorkflowEvent，带上一个字符串负载。把消息传给基类构造函数（框架会存储它），同时也把它暴露成一个带类型的属性，这样消费方的代码就不必去强转 Data。

    🔧 放置位置

    文件：Workflows/InvestigationModels.cs — 这个文件在 B1 里就已经存在，顶部以 using Microsoft.Agents.AI.Workflows; 开头，下面是 namespace AiAgent.Workflows;。 把下面这个类追加到同一个 namespace AiAgent.Workflows 块内部，放在已有的 record 声明之后。无需新增 NuGet—— Microsoft.Agents.AI.Workflows 在 B1 里就已经加好了。

    Workflows/InvestigationModels.cs 
    /// <summary>Custom workflow event — executors narrate their progress with these.</summary>
public sealed class InvestigationProgressEvent(string message) : WorkflowEvent(message)
{
    public string Message { get; } = message;
}

    正是这次对基类构造函数的调用，把事件路由进了 WatchStreamAsync。没有它，对象虽然存在，事件流却永远看不到它。

  2. 从 executor 发出自定义事件

    在任意 executor 的 HandleAsync 里，用你的事件实例调用 context.AddEventAsync。planner 宣布要跑几个 probe，每个 probe 开始时也宣布一声。这两条 event 落进 DriveAsync 稍后读取的同一条流，所以进度会出现在时间线里。

    第一行加在 PlanExecutor.HandleAsync，在 clamp days 之后的第一行：

    Workflows/InvestigationExecutors.cs — in PlanExecutor.HandleAsync 
    await context.AddEventAsync(
    new InvestigationProgressEvent($"Planning {days}-day investigation: 3 probes."),
    cancellationToken);

    第二行加在 ProbeExecutor.HandleAsync，在 ClickHouse 调用之前：

    Workflows/InvestigationExecutors.cs — in ProbeExecutor.HandleAsync 
    await context.AddEventAsync(
    new InvestigationProgressEvent($"Probe '{job.Name}' running."),
    cancellationToken);

    B3 里加入的 validator 与 synthesis 节点也用同样方式发进度：从它们的 HandleAsync 内部把新的 InvestigationProgressEvent 传给 context.AddEventAsync。

  3. 添加 WorkflowEventDto record

    原始的 WorkflowEvent 体系是一个内部类型。在把它返回给 HTTP 调用方、或缓冲进时间线之前，先把它映射成一个简单的 record。这个 record 处于命名空间作用域——在类之外——这样同命名空间里的任何文件都能用到它。

    🔧 放置位置

    文件：Workflows/InvestigationService.cs。B2 创建这个文件——它目前还不存在。先从下面这个最小骨架开始，然后在后续步骤里逐步加入类型与方法： 

    using Microsoft.Agents.AI.Workflows;

namespace AiAgent.Workflows;

// <-- add WorkflowEventDto HERE (namespace scope, before the class)

public sealed class InvestigationService(
    Func<Workflow> workflowFactory, ILogger<InvestigationService> logger)
{
    private readonly Func<Workflow> _workflowFactory = workflowFactory;
    private readonly ILogger<InvestigationService> _logger = logger;
    // <-- add InvestigationStatus HERE (still namespace scope, can go above or below the class)
    // <-- add ToDto, DriveAsync, StartAsync INSIDE this class
}

    无需新增 NuGet—— Microsoft.Agents.AI.Workflows 在 B1 里就已经加好了。检查点（checkpoint）支持在 B4 里加入；暂时不要导入 Microsoft.Agents.AI.Workflows.Checkpointing。

    Workflows/InvestigationService.cs — 位于命名空间作用域，类之前 
    /// <summary>One simplified workflow event, as returned to HTTP clients.</summary>
public sealed record WorkflowEventDto(string Type, string? Detail);

  4. 添加 ToDto — 把原始事件映射成 DTO

    把 ToDto 作为 private static 方法加到 InvestigationService 内部。下一步的 DriveAsync 会读它：流里每个原始 event 都先经过 ToDto 再进时间线。用 switch 表达式逐一处理，未处理的类型返回 null 被跳过。

    Workflows/InvestigationService.cs — 位于 InvestigationService 内部 
    /// <summary>The raw-event-stream lesson, flattened for JSON/SSE consumers.</summary>
private static WorkflowEventDto? ToDto(WorkflowEvent evt) => evt switch
{
    WorkflowStartedEvent                   => new("workflow_started", null),
    SuperStepStartedEvent                  => null,
    SuperStepCompletedEvent                => new("superstep_completed", null),
    ExecutorInvokedEvent invoked           => new("executor_invoked",   invoked.ExecutorId),
    ExecutorCompletedEvent completed       => new("executor_completed", completed.ExecutorId),
    ExecutorFailedEvent failed             => new("executor_failed",
        $"{failed.ExecutorId}: {(failed.Data as Exception)?.GetBaseException().Message ?? failed.Data?.ToString()}"),
    InvestigationProgressEvent progress    => new("progress",          progress.Message),
    WorkflowOutputEvent                    => new("workflow_output",    "report ready"),
    _                                      => null,
};

    SuperStepStartedEvent 这一支返回 null，对 HTTP 客户端丢弃，因为它太频繁、只增噪声；它在 OTel 追踪里仍可见。原始事件流始终完整。

    目前还没有 RequestInfoEvent 这一支，它是审批暂停 event。F2 引入 approval port 时再加它的分支，在此之前它落到 _ 被跳过。

  5. 添加 InvestigationStatus 与 DriveAsync

    InvestigationStatus 是返回给 HTTP 调用方的形状：run id、status 字符串、报告文本和完整事件时间线。加到命名空间作用域，在类之外，与 WorkflowEventDto 放一起。Status 取 running、completed 或 failed 之一。

    Workflows/InvestigationService.cs — 命名空间作用域 （在 InvestigationService 之外） 
    /// <summary>HTTP-facing result of driving a run as far as it will go.</summary>
public sealed record InvestigationStatus(
    string RunId,
    string Status,
    string? Report,
    List<WorkflowEventDto> Events);

    把 DriveAsync 作为 private 方法加到 InvestigationService 内部。它是事件流的消费者：用 await foreach 读每个 event，过 ToDto，加进 events 列表，并盯住 WorkflowOutputEvent 捕获最终报告。它填的列表正是 StartAsync 返回给 /investigate 端点的内容。HITL 暂停在 F2 里加入。

    Workflows/InvestigationService.cs — 位于 InvestigationService 内部 
    /// <summary>
/// Consumes the raw WorkflowEvent stream until the run produces output or ends.
/// Human-in-the-loop pause (RequestInfoEvent) is wired in F2.
/// </summary>
private async Task<InvestigationStatus> DriveAsync(
    string runId, StreamingRun run, List<WorkflowEventDto> events, CancellationToken ct)
{
    string? report = null;
    try
    {
        await foreach (var evt in run.WatchStreamAsync(ct))
        {
            var dto = ToDto(evt);
            if (dto is not null) events.Add(dto);

            if (evt is WorkflowOutputEvent output)
                report = output.Data?.ToString();
        }
    }
    catch (Exception ex)
    {
        _logger.LogError(ex, "Investigation run {RunId} failed.", runId);
        events.Add(new("error", ex.Message));
        return new InvestigationStatus(runId, "failed", null, events);
    }

    return new InvestigationStatus(runId, report is null ? "failed" : "completed", report, events);
}

    循环 await 事件流：读取下一个 event 这个动作本身就在驱动运行前进，没有东西跑在你前面。图里再没有 node 可触发时流结束。B4 加 checkpoint 支持，F2 通过保存活跃 run 句柄并提前返回来处理审批暂停。

  6. 把 StartAsync 接到 DriveAsync

    StartAsync 是 /investigate 端点调用的 public 入口，加到 InvestigationService 内部。它用 _workflowFactory 创建全新的 StreamingRun，带空事件列表交给 DriveAsync。这里是无 checkpoint 的重载，checkpoint 在 B4 加入。

    Workflows/InvestigationService.cs — 位于 InvestigationService 内部 
    public async Task<InvestigationStatus> StartAsync(int days, CancellationToken ct)
{
    var runId = Guid.NewGuid().ToString("N");
    var run = await InProcessExecution.RunStreamingAsync(
        _workflowFactory(), new InvestigationRequest(days), runId, ct);
    return await DriveAsync(runId, run, [], ct);
}

  7. 在 Program.cs 里注册 InvestigationService

    把 InvestigationService 注册成单例（singleton），工厂构建 B1 的 ProbeWorkflow；B3 会把工厂改指向 InvestigationWorkflow。然后暴露 /investigate 端点，它是链条顶端的读取方：调用 StartAsync，把带完整事件时间线的 InvestigationStatus 作为 JSON 返回。

    Program.cs — 服务注册 
    builder.Services.AddSingleton(sp =>
    new InvestigationService(
        () => ProbeWorkflow.Build(sp.GetRequiredService<ClickHouseClient>()),
        sp.GetRequiredService<ILogger<InvestigationService>>()));

// ...

app.MapPost("/investigate", async (int days, InvestigationService svc, CancellationToken ct) =>
    Results.Ok(await svc.StartAsync(days, ct)));

为什么超步（superstep）能揭示并行

一个 超步（superstep） 就是一次前沿推进：所有输入消息已就绪的节点（node）都会在这一步内并发触发。在 B1/B2 的流水线里，三个探针（probe）执行器（executor）共享同一个超步，因为扇出（fan-out）的边（edge）会同时投递全部三条 ProbeJob 消息。事件流让这一结构性事实在运行时可被观察：去找三条连续的 executor_invoked 条目，它们对应的 executor_completed 条目全都落在同一个 superstep_completed 内。这就是免费的、可验证的并行，且零 LLM 成本。

验证

✅ 关卡（gate） — 未变绿前不要前进

用 Testing 环境启动智能体（agent），并向 investigation 端点（endpoint）发起 POST： 

dotnet run -- --environment Testing
# In another terminal:
curl -s -X POST "http://localhost:8124/investigate?days=7" | jq '.events[].type'

输出必须按顺序包含：

  • "workflow_started"
  • 针对 plan 的 "executor_invoked"
  • "progress" — "Planning 7-day investigation: 3 probes."
  • 三条针对 probe-0、probe-1、 probe-2 的 "executor_invoked" 条目（同一超步（superstep）内的顺序是任意的）
  • 三条 "progress" 条目，每个探针（probe）一条 — "Probe '…' running."
  • 针对 collector 的 "executor_invoked" — 只会在三个探针的 "executor_completed" 条目全部出现 之后 才登场（扇入屏障，fan-in barrier）
  • "workflow_output"

检查这些探针执行器（executor）的调用是否共享一个超步：比较它们在 events 数组中的下标；三者都应落在同一对 superstep_completed 边界之间。

反向测试 — 让 executor-failed 暴露出来：

在 ProbeExecutor.HandleAsync 里故意写坏 SQL，查询一个不存在的表： 

rows = await clickHouse.QueryAsync("SELECT * FROM nonexistent_table", cancellationToken);

重新跑 investigate 端点，events 数组里应出现一条 executor_failed： 

{ "type": "executor_failed", "detail": "probe-0: Table nonexistent_table doesn't exist." }

运行会继续：其他 probe 照常触发，collector 仍收到坏 probe 的 ProbeResult（hasData = false）。

确认 executor_failed 携带的是基础异常消息（表名），不是完整堆栈。如果看到多行转储，说明 ToDto 里的 GetBaseException().Message 没有触及该事件，请重查 switch 里的 ExecutorFailedEvent 分支。

⚠️ 常见坑
  • executor_failed 显示的是一堵堆栈墙，而不是根因 → failed.Data 是一个 Exception；要调用 .GetBaseException().Message，而不是 .ToString()。原始的 ToString() 会包含若干栈帧，把真正的错误埋在好几行运行时内部细节里面。
  • 自定义事件从未出现在事件流里 → 你的类必须调用 : WorkflowEvent(payload) ——正是这个基类构造函数才把对象注册进框架的事件总线（event bus）。一个继承了 WorkflowEvent 但没有向基类构造函数传任何东西的类，会被构造出来，却永远不会被发出。
  • 所有事件都在最后一次性到达，而不是逐步到达 → 你是在用 ToListAsync() 或 .Result 迭代，而不是 await foreach。事件流必须以异步方式消费；阻塞式的一次性物化（materialisation）会破坏实时事件的契约。
  • 事件流看起来是空的（完全没有事件） → 你在监听的是一个与实际执行工作流（workflow）的那个不同的 StreamingRun 实例。一个常见原因是：第二次调用 _workflowFactory()，然后去监听那个新句柄。记住：一个 Workflow 由恰好一个运行器（runner）所拥有——每次逻辑运行都重新构建（如工厂模式所保证的），但绝不要为同一次运行创建两个句柄。
  • 看不到探针（probe）的并行（三个探针全是顺序执行） → 来自 B1 的扇出（fan-out）边（edge）或分区器（partitioner）没有被沿用过来。确认工作流构建器仍然注册了全部三个探针执行器（executor）以及扇出边；超步（superstep）的分组是从边的接线中浮现出来的，而不是来自事件代码。
