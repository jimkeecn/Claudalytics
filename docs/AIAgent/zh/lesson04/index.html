第 04 课 · B1 · 模块 B — 在引入智能之前，先搭好图

执行器与边：一条无需 LLM 的扇出流水线

★★ 无需 LLM — 可免费重跑

你将学到什么

一次 Claudalytics 调查要跑多个 ClickHouse 探针（probe）。如果把这些活儿写成一坨缠在一起的方法，一旦结果出错或卡住，你就分不清是哪个探针出了问题、它们是否真的并行跑了。MAF 的工作流（workflow）运行时把工作拆成带类型的节点（node）——称为 执行器（executor）——再用 边（edge） 连接：每个执行器只收一种消息、只做一件事、再发一条消息给下一个节点，于是每一步都有名字、彼此隔离、可单独测试。

用这套运行时不需要 LLM。本课搭建一个规划器（planner）节点，把三个探针任务并行扇出（fan-out）到三个工作节点，再在一个扇入（fan-in）节点里汇合原始结果。整个过程不调用任何模型。 这是刻意为之：没有模型，每次运行都免费且确定，调试时可以随便重跑。这里搭的收集器是 ♻ 脚手架（scaffolding），会在 B3 中被一个 LLM 综合节点取代。先把管道显式搭出来，再往里放智能的东西。

📘 讲解

三个原语

  • Executor<T> — 一个代码节点。继承它，指定输入消息类型 T，实现 HandleAsync。在构造函数里给执行器一个唯一的字符串 id。一个执行器 = 针对一种消息类型的一个处理器。
  • 输出协议特性（Output protocol attributes） — 执行器 发送 的每一种消息都必须通过类上的 [SendsMessage(typeof(M))] 声明；执行器 作为最终输出产出 的消息则使用 [YieldsOutput(typeof(M))]。发送未声明的类型会在运行时抛出异常，并清楚地指出是哪个执行器、哪种类型。这是契约，不是提示。
  • 边（Edges） — 你在 WorkflowBuilder 上注册它们：
    • AddFanOutEdge — 一个源、N 个目标；一个分区器（partitioner）lambda 把每条消息映射到一个或多个目标索引。
    • AddFanInBarrierEdge — N 个源、一个汇（sink）；只有在每一个上游都投递之后，汇才会触发。这就是你汇合并行工作的方式。
    • AddEdge<T> — 带可选谓词的类型化直连边。消息类型决定路由；谓词可以进一步过滤。

本课用到的 MAF API 接口： Executor<T>、[SendsMessage]、 [YieldsOutput]、WorkflowBuilder、 AddFanOutEdge、AddFanInBarrierEdge、 AddEdge<T>、 IWorkflowContext.SendMessageAsync、 IWorkflowContext.YieldsOutputAsync、 builder.WithOutputFrom(...).Build()。

  1. 引入 ClickHouse 客户端

    B1 是第一节真正对 ClickHouse 跑查询的课。后面的探针执行器需要一个发 SQL 的工具，所以先加这个只读 HTTP 客户端。它把请求作为 HTTP POST 发给 ClickHouse，返回制表符分隔的文本（TSVWithNames）。连接设置来自配置；localhost 默认值让应用无需环境变量覆盖即可启动。

    Tools/ClickHouseClient.cs 
    using Microsoft.Extensions.Configuration;

namespace AiAgent.Tools;

/// <summary>
/// Thin HTTP client for ClickHouse, connecting as the read-only agent_ro user.
/// Per-query limits are sent as URL settings on every request.
/// </summary>
public sealed class ClickHouseClient(HttpClient http, IConfiguration config)
{
    private readonly string _baseUrl = config["CLICKHOUSE_URL"] ?? "http://localhost:8123";
    private readonly string _user = config["CLICKHOUSE_USER"] ?? "agent_ro";
    private readonly string _password = config["CLICKHOUSE_PASSWORD"] ?? "";

    public async Task<string> QueryAsync(string sql, CancellationToken ct = default)
    {
        var url = $"{_baseUrl}/?user={Uri.EscapeDataString(_user)}" +
                  $"&password={Uri.EscapeDataString(_password)}" +
                  "&database=claudalytics" +
                  "&max_execution_time=30" +
                  "&max_result_rows=1000" +
                  "&result_overflow_mode=break";

        var response = await http.PostAsync(url, new StringContent(sql + " FORMAT TSVWithNames"), ct);
        var body = await response.Content.ReadAsStringAsync(ct);

        if (!response.IsSuccessStatusCode)
            throw new InvalidOperationException($"ClickHouse error: {body.Trim()}");

        return string.IsNullOrWhiteSpace(body) ? "(no rows)" : body.Trim();
    }
}

    Program.cs — 在 var app = builder.Build(); 之前添加

  2. 定义消息类型

    消息是节点之间的契约，先定义它们，下面每个执行器才有可命名的输入输出。用 sealed record：结构化相等、构造清晰，且避免意外的子类路由。消息类型都要能往返 JSON，因为引擎可能对它们做检查点（checkpoint）。

    Workflows/InvestigationModels.cs 
    using Microsoft.Agents.AI.Workflows;

namespace AiAgent.Workflows;

/// <summary>Workflow input: how many days of telemetry to investigate.</summary>
public sealed record InvestigationRequest(int Days);

public sealed record ProbeJob(int Slot, string Name, string Sql, int Days);

public sealed record ProbeResult(string Name, string Rows, bool HasData);

    谁读谁：规划器发 ProbeJob，扇出（fan-out）分区器读它的 Slot 来路由；探针执行器发 ProbeResult，收集器读它来拼最终输出。HasData 供后续课程的校验器使用。

  3. 编写规划器执行器

    规划器是起始节点：把一个请求变成三条并行的探针任务。它收 InvestigationRequest，发三条 ProbeJob，后面的扇出边读每条的 Slot 决定路由。类上的 [SendsMessage] 特性声明允许发送的消息类型，省略它第一次 SendMessageAsync 就会在运行时抛异常。

    Workflows/InvestigationExecutors.cs 
    using Microsoft.Agents.AI;
using Microsoft.Agents.AI.Workflows;

namespace AiAgent.Workflows;

[SendsMessage(typeof(ProbeJob))]
public sealed class PlanExecutor() : Executor<InvestigationRequest>("plan")
{
    public override async ValueTask HandleAsync(
        InvestigationRequest request, IWorkflowContext context, CancellationToken cancellationToken = default)
    {
        var days = Math.Clamp(request.Days, 1, 90);

        ProbeJob[] jobs =
        [
            new(0, "cost-trend", $"""
                SELECT toDate(Timestamp) AS day,
                       round(sum(toFloat64OrZero(LogAttributes['cost_usd'])), 2) AS cost_usd
                FROM otel_logs
                WHERE LogAttributes['event.name'] = 'api_request'
                  AND Timestamp >= now() - INTERVAL {days} DAY
                GROUP BY day ORDER BY day
                """, days),
            new(1, "tool-failures", $"""
                SELECT LogAttributes['tool_name'] AS tool_name, count() AS calls,
                       countIf(LogAttributes['success'] != 'true') AS failures
                FROM otel_logs
                WHERE LogAttributes['event.name'] = 'tool_result'
                  AND Timestamp >= now() - INTERVAL {days} DAY
                GROUP BY tool_name ORDER BY failures DESC LIMIT 10
                """, days),
            new(2, "security-events", $"""
                SELECT pattern_category, count() AS exposures
                FROM credential_exposures
                WHERE timestamp >= now() - INTERVAL {days} DAY
                GROUP BY pattern_category ORDER BY exposures DESC
                """, days),
        ];

        foreach (var job in jobs)
            await context.SendMessageAsync(job, cancellationToken: cancellationToken);
    }
}

    来源： Workflows/InvestigationExecutors.cs — PlanExecutor。SQL 原样照搬；本课省略了自定义进度事件（那是 B2 的主题）。

  4. 编写探针执行器

    这是工作节点：一个类，三个实例。每个实例收一条 ProbeJob，对 ClickHouse 跑 SQL，发一条 ProbeResult 给收集器读取。由扇出（fan-out）边决定哪个实例拿哪个任务，执行器本身不管路由。

    Workflows/InvestigationExecutors.cs — 添加到同一个文件中，位于 PlanExecutor 的右花括号之后；步骤 2 已经在文件顶部放好了 using 语句。 
    [SendsMessage(typeof(ProbeResult))]
public sealed class ProbeExecutor(string id, ClickHouseClient clickHouse) : Executor<ProbeJob>(id)
{
    public override async ValueTask HandleAsync(
        ProbeJob job, IWorkflowContext context, CancellationToken cancellationToken = default)
    {
        string rows;
        try
        {
            rows = await clickHouse.QueryAsync(job.Sql, cancellationToken);
        }
        catch (Exception ex)
        {
            rows = $"QUERY FAILED: {ex.Message}";
        }

        var hasData = !rows.StartsWith("QUERY FAILED") && rows != "(no rows)" && rows.Any(char.IsDigit);
        await context.SendMessageAsync(new ProbeResult(job.Name, rows, hasData), cancellationToken: cancellationToken);
    }
}

    捕获查询失败可以防止扇入（fan-in）卡住：三个探针总会各自投递一个结果。应用这里还会写入工作流（workflow）状态——那是 B4 的内容。

  5. 编写收集器执行器（executor）（♻ 脚手架（scaffolding））

    收集器是汇合节点，位于扇入屏障（fan-in barrier）之后。它逐条收 ProbeResult，加入一个列表，三条到齐后拼成一个字符串，作为工作流输出产出。

    这个收集器是 ♻ 脚手架：只拼接原始行，让你零成本看到扇入工作，会在 B3 中被 SynthesisExecutor 取代。accumulated 存在实例字段里，是 B4 剖析的问题。

    Workflows/InvestigationExecutors.cs — 添加到同一个文件中，位于 ProbeExecutor 的右花括号之后；using 语句已在文件顶部。 
    [YieldsOutput(typeof(string))]
public sealed class CollectorExecutor() : Executor<ProbeResult>("collector")
{
    private readonly List<ProbeResult> accumulated = [];
    private const int ExpectedProbes = 3;

    public override async ValueTask HandleAsync(
        ProbeResult result, IWorkflowContext context, CancellationToken cancellationToken = default)
    {
        accumulated.Add(result);

        if (accumulated.Count < ExpectedProbes)
            return;

        var combined = string.Join("\n\n", accumulated.Select(probe =>
            $"=== {probe.Name} ===\n{probe.Rows}"));

        await context.YieldOutputAsync(combined, cancellationToken);
    }
}
    ℹ️

    accumulated 实例字段对于单进程中的单次运行是可行的。它正是 B4 中剖析的“状态存字段”陷阱：如果进程被杀死再恢复（resume），该字段会从空开始，输出就会缺失或不完整。眼下它能完成任务——让扇入（fan-in）变得可见、可测试。

    这是 B3 中取代 CollectorExecutor 的 v2 节点：它持有一个真实的 AIAgent，把探针数据写成 markdown 报告。这里只是预览，现在先别加。

    Workflows/InvestigationExecutors.cs — SynthesisExecutor 
    [YieldsOutput(typeof(string))]
public sealed class SynthesisExecutor(AIAgent writer) : Executor<Findings>("synthesis")
{
    public override async ValueTask HandleAsync(
        Findings findings, IWorkflowContext context, CancellationToken cancellationToken = default)
    {
        var probesText = string.Join("\n\n", findings.Results.Select(probe =>
            $"## {probe.Name}\n{probe.Rows}"));
        var notesText = findings.ValidationNotes.Count == 0
            ? "(none)"
            : string.Join("\n", findings.ValidationNotes);

        var response = await writer.RunAsync($"""
            Write a short markdown investigation report over the last {findings.Days} days of
            Claude Code telemetry. Cost spike detected: {findings.CostSpike}.

            Probe data (TSV):
            {probesText}

            Validator notes (mention them honestly):
            {notesText}

            Shape: headline numbers, findings, then 1-3 recommendations.
            Use only the numbers in the data above.
            """, cancellationToken: cancellationToken);

        await context.YieldOutputAsync(response.Text, cancellationToken);
    }
}

  6. 用 WorkflowBuilder 连接这张图

    上面的执行器互不知道彼此，这里注册的边（edge）才把它们连成一张图。这一块创建各节点和 builder，builder 把起始执行器（规划器）作为构造函数参数，边在后面两块加。

    Workflows/ProbeWorkflow.cs 
    using AiAgent.Tools;
using Microsoft.Agents.AI;
using Microsoft.Agents.AI.Workflows;

namespace AiAgent.Workflows;

/// <summary>
/// Probe pipeline — zero LLM:
///
///                     ┌─> probe-0 ─┐
///   plan ──fan-out────┼─> probe-1 ─┼──fan-in barrier──> collector ──> output
///                     └─> probe-2 ─┘
///
/// CollectorExecutor is ♻ scaffolding replaced by SynthesisExecutor in B3.
/// </summary>
public static class ProbeWorkflow
{
    public static Workflow Build(ClickHouseClient clickHouse)
    {
        var plan = new PlanExecutor();
        ProbeExecutor[] probes =
        [
            new("probe-0", clickHouse),
            new("probe-1", clickHouse),
            new("probe-2", clickHouse),
        ];
        var collector = new CollectorExecutor();

        var builder = new WorkflowBuilder(plan);

    扇出边把规划器的任务发给探针。分区器 lambda 收每条 ProbeJob，读它的 Slot 选一个探针，返回目标索引数组。job?.Slot ?? 0 容忍空消息——分区器绝不能因空值抛异常。

    Workflows/ProbeWorkflow.cs — 在 Build 内、builder 之后 
            builder.AddFanOutEdge<ProbeJob>(plan, probes.Select(p => (ExecutorBinding)p),
            (job, targetCount) => [(job?.Slot ?? 0) % targetCount]);

    扇入屏障把并行的探针汇回一个节点：三个探针都投递 ProbeResult 后收集器才触发。WithOutputFrom(collector) 把收集器标为终端节点；若指向某个探针，RunAsync 会在第一个探针后就返回，不等扇入。

    Workflows/ProbeWorkflow.cs — 在 Build 内、扇出边之后 
            builder.AddFanInBarrierEdge(probes.Select(p => (ExecutorBinding)p), collector);

        return builder.WithOutputFrom(collector).Build();
    }
}

  7. 暴露一个探针端点（endpoint）

    这是运行图的入口，每个请求构建一个全新的 Workflow。工作流实例由单个 runner 拥有，不能跨请求复用，否则一个请求的结果会串到另一个请求里。

    InProcessExecution.RunAsync(workflow, request) 把图跑到完成并返回一个 Run。收集器用 YieldOutputAsync 产出的字符串会作为 WorkflowOutputEvent 出现在 run.NewEvents 里，它的 Data 就是要返回的值，所以循环扫描事件取这个输出。

    Program.cs — 在 app.Run(); 之前添加 
    using Microsoft.Agents.AI.Workflows;

app.MapPost("/probe", async (InvestigationRequest request, ClickHouseClient clickHouse, CancellationToken ct) =>
{
    var workflow = ProbeWorkflow.Build(clickHouse);
    var run = await InProcessExecution.RunAsync(workflow, request, cancellationToken: ct);

    string? report = null;
    foreach (var evt in run.NewEvents)
        if (evt is WorkflowOutputEvent output)
            report = output.Data?.ToString();

    return Results.Ok(new { report });
});

    累积状态说明： ClickHouseClient 在本课（B1）引入——上面的步骤 1 添加了该文件，并在 var app = builder.Build(); 之前用 builder.Services.AddHttpClient<ClickHouseClient>() 注册了它。/probe 端点直接从 DI 参数注入它；无需再做任何注册。

🔄 演进脉络

CollectorExecutor 是第 1 弧（Arc 1）的 v1——刻意做得朴素。它以零 LLM 成本让扇入（fan-in）变得可观测（observability）。两个局限推动着接下来的课程：

  • 原始 TSV 不可读。 在 B3 中，你会把收集器替换成一个持有写作智能体（writer agent）的 SynthesisExecutor——同一张图，其中一个节点（node）现在变得智能了。
  • accumulated 字段熬不过一次崩溃。 在 B4 中，你会接入检查点（checkpoint）机制，在运行中途杀死进程，证明字段版本在恢复（resume）时失败；然后你会把状态搬进工作流（workflow）上下文。

验证

✅ 关卡（gate） — 未变绿前不要前进

正常路径：

curl -s -X POST http://localhost:8124/probe \
  -H "Content-Type: application/json" \
  -d '{"days": 7}' | jq .report

响应必须是一个非空字符串，包含全部三个探针名称（cost-trend、tool-failures、security-events）以及至少一行数据（如果 ClickHouse 尚未灌入数据，则为一行 QUERY FAILED）。关键检查点是三个小节都出现了——这就证明扇入（fan-in）是在三个并行探针全部投递之后才触发的。

刻意失败练习（不花一分钱——无需 LLM）：

从 PlanExecutor 上移除 [SendsMessage(typeof(ProbeJob))] 特性，重新编译，再次调用该端点（endpoint）。你应该会看到： 

System.InvalidOperationException: Executor 'plan' attempted to send message of type 'ProbeJob'
which is not declared in its [SendsMessage] attributes.

把特性放回去。这段错误文本正是输出协议按设计在工作——契约是被强制执行的，而不是建议性的。

负向测试 — 分区器的空值容忍：

移除空值守卫： (job, targetCount) => [job.Slot % targetCount]。来自上游的空消息会在分区器内部产生一个 NullReferenceException。恢复守卫。分区器必须始终容忍空值。

⚠️ 常见坑
  • 运行时抛出 "attempted to send message of type X, not declared" → 你忘了在执行器类上加 [SendsMessage(typeof(X))] 特性。检查每一个调用 SendMessageAsync 的执行器。
  • 收集器只触发了一次，但输出里少了两个探针 → 扇入屏障（fan-in barrier）没有正确注册；所有探针执行器（executor）都必须出现在传给 AddFanInBarrierEdge 的 sources 列表里。
  • 分区器抛出 NullReferenceException → 在 lambda 里防范空值： (job, n) => [(job?.Slot ?? 0) % n]。
  • 工作流（workflow）在多个请求间被复用，收集器看到了多余的结果 → 一个 Workflow 对象正好由一个 runner 拥有。用 ProbeWorkflow.Build(...) 为每个请求构建一个全新实例。 CollectorExecutor 的 accumulated 字段每次都从空开始，仅仅是因为执行器对象本身是新的。
  • WithOutputFrom 指向了错误的执行器 → RunAsync 会在第一个探针之后就返回，而不是等待扇入（fan-in）；始终把它指向最终的输出节点（node）。
