第 09 课 · C2 · 模块 C — 打造产品

可观测性：中间件 + OTel

★★ Haiku

你将学到什么

智能体（agent）自己决定调用哪些 SQL 工具、做多少次模型往返。一旦某次运行太贵 或调用了你没料到的工具，你却没有任何记录：调了哪些工具、付了多少 token、各自耗时多久，全都查不到。C2 让每次模型往返和每次工具调用事后都可见。 委托式聊天客户端（delegating chat client）把每次往返记进控制台日志， UseOpenTelemetry 则把结构化跨度（span）写入智能体已经在查询的同一个 ClickHouse。

一共两个切入点（seam），层级不同、看到的东西也不同。第一个是委托式聊天客户端， 它包裹模型提供方，看到每次原始往返：进去的消息、回来的工具调用（tool call）和 token 计数。 第二个是构建器上的 UseOpenTelemetry，它向任何 OpenTelemetry 后端发出 invoke_agent 和 execute_tool 跨度。两者都导出到智能体查询的同一个 ClickHouse，产品自己监控自己。埋点一次，之后永久可查。

📘 讲解

两个中间件（middleware）切入点

切入点 1 —— DelegatingChatClient。这是 Microsoft.Extensions.AI 的中间件模式：继承 DelegatingChatClient，重写 GetResponseAsync 和 GetStreamingResponseAsync，调用 base.* 转发给真正的提供方，转发后对结果随意处理。它通过 client.AsAIAgent(…) 的 clientFactory 参数接入。它在每次模型往返时运行， 包括单次 RunAsync 内部的工具调用循环，所以是按请求日志和成本追踪的理想位置。

切入点 2 —— UseOpenTelemetry(sourceName)。 在 agent.AsBuilder() 返回的 AIAgentBuilder 上调用， 它会把一个 OTel ActivitySource 接入智能体（agent）。它会自动发出两类跨度： invoke_agent（每次 RunAsync 调用一个）和 execute_tool （每次工具调用（tool call）一个）。你给这个源命名 —— 这个名字会成为 你 OTel 流水线配置中的 AddSource(…) 参数。

命名的 API 接口

  • DelegatingChatClient —— 基类， Microsoft.Extensions.AI
  • client.AsAIAgent(options, clientFactory: inner => …) —— 接入中间件（middleware）
  • agent.AsBuilder().UseOpenTelemetry(sourceName).Build() —— 添加 OTel 跨度
  • builder.Services.AddOpenTelemetry()…AddAspNetCoreInstrumentation()…AddSource(…)…AddOtlpExporter() —— 宿主侧的流水线

两个切入点有何不同

明确一下每个切入点看到什么、何时看到，会很有帮助：

切入点 粒度 你能拿到什么 接入位置
DelegatingChatClient 每一次模型 HTTP 调用 原始消息、FunctionCallContent、token 计数、 流式分块 AsAIAgent 中的 clientFactory
UseOpenTelemetry 每次智能体（agent）调用 + 每次工具执行 结构化的 OTel 跨度：invoke_agent、 execute_tool、模型 id 属性 AsBuilder().UseOpenTelemetry(…).Build()

凡是你想写进日志的内容，用委托式客户端 —— 它简单、 同步，并且在进程中始终可用。凡是你想查询、聚合或告警的内容，用 OTel —— 它会进入 ClickHouse，与你的 Claudalytics 会话（session）数据并存。

动手构建

  1. 步骤 1 — 编写委托式聊天客户端

    创建 Middleware/ToolCallLoggingChatClient.cs，这就是切入点 1。 步骤 2 把它接入智能体，控制台读它的日志行。它继承 DelegatingChatClient，构造函数接收内层客户端和一个 ILogger，是标准 .NET DI。

    🔧 准备 — 依赖包

    C2 引入 OpenTelemetry。在编写任何代码之前先添加三个包 （版本已在 AiAgent.csproj 中固定）： 

    dotnet add package OpenTelemetry.Extensions.Hosting --version 1.15.3
dotnet add package OpenTelemetry.Exporter.OpenTelemetryProtocol --version 1.15.3
dotnet add package OpenTelemetry.Instrumentation.AspNetCore --version 1.15.2

    先写非流式重写。它调用 base.GetResponseAsync 转发请求， 然后遍历响应消息，找出每个 FunctionCallContent 并记录工具名和参数； response.Usage 非空时再记录 token 用量。成本追踪就在这里。 项目开启了 implicit usings，但 ILogger 仍需显式 using Microsoft.Extensions.Logging;。

    Middleware/ToolCallLoggingChatClient.cs — 类 + 非流式重写 
    using Microsoft.Extensions.AI;
using Microsoft.Extensions.Logging;

namespace AiAgent.Middleware;

public sealed class ToolCallLoggingChatClient(IChatClient innerClient, ILogger logger)
    : DelegatingChatClient(innerClient)
{
    public override async Task<ChatResponse> GetResponseAsync(
        IEnumerable<ChatMessage> messages, ChatOptions? options = null,
        CancellationToken cancellationToken = default)
    {
        var response = await base.GetResponseAsync(messages, options, cancellationToken);

        foreach (var call in response.Messages
            .SelectMany(m => m.Contents)
            .OfType<FunctionCallContent>())
            logger.LogInformation("Tool call requested: {Tool} {Args}",
                call.Name, System.Text.Json.JsonSerializer.Serialize(call.Arguments));

        if (response.Usage is { } usage)
            logger.LogInformation("Model round-trip: in={Input} out={Output} tokens",
                usage.InputTokenCount, usage.OutputTokenCount);

        return response;
    }

    再写流式重写，并闭合类。流式路径走的是另一个方法，所以两个都要重写。 它原样 yield 每个 ChatResponseUpdate，从不缓冲。日志只是副作用，不改数据流。 委托式客户端的契约：保持透明、增加行为、不破坏流。

    ToolCallLoggingChatClient.cs — 流式重写（之后闭合类） 
        public override async IAsyncEnumerable<ChatResponseUpdate> GetStreamingResponseAsync(
        IEnumerable<ChatMessage> messages, ChatOptions? options = null,
        [System.Runtime.CompilerServices.EnumeratorCancellation]
        CancellationToken cancellationToken = default)
    {
        await foreach (var update in base.GetStreamingResponseAsync(
            messages, options, cancellationToken))
        {
            foreach (var call in update.Contents.OfType<FunctionCallContent>())
                logger.LogInformation("Tool call requested (stream): {Tool}", call.Name);
            yield return update;
        }
    }
}

  2. 步骤 2 — 把中间件接入智能体工厂

    这一步同时打开两个切入点。在 Agents/AgentFactory.cs 中向 client.AsAIAgent 传一个 clientFactory lambda， 它接收原始 IChatClient 并返回包裹它的步骤 1 的 ToolCallLoggingChatClient —— 这是切入点 1。然后链式调用 .AsBuilder().UseOpenTelemetry(OtelSourceName).Build() 添加 OTel 跨度 —— 这是切入点 2。源名是 public 常量，步骤 3 在 Program.cs 里读回它。

    🔧 说明 — 累积文件

    Agents/AgentFactory.cs 在 C1 中开始编写。保留 C1 的完整 文件 —— 所有 options/Tools 的接线保持原样不变。在 C2 中你只做两处新增：

    1. 添加 OtelSourceName 作为 public 常量 （在 Program.cs 中需要）。
    2. 向 client.AsAIAgent 传入 clientFactory:，并在其结果上链式调用 .AsBuilder().UseOpenTelemetry(OtelSourceName).Build()。

    AgentFactory.cs 顶部需要的 using （六个应该在 C1 中就已经全部存在；补上任何缺失的）： 

    using AiAgent.Middleware;
using AiAgent.Tools;
using Anthropic;
using Microsoft.Agents.AI;
using Microsoft.Agents.AI.Compaction;
using Microsoft.Extensions.AI;

    下面只展示 C2 的两处新增。OtelSourceName 常量是新的，步骤 3 会读它。 C1 的 options / Tools 接线保持原样。改动仅是给 AsAIAgent 加 clientFactory:，并在结果上链式调用 .AsBuilder().UseOpenTelemetry(...).Build()。

    Agents/AgentFactory.cs 节选 —— 仅展示 C2 的两处新增；保留全部 C1 内容 
    public static class AgentFactory
{
    public const string OtelSourceName = "Claudalytics.Agent";

    public static AIAgent Create(
        IConfiguration config,
        SchemaTools tools,
        AnalysisTools analysis,
        ILoggerFactory loggerFactory)
    {
        var apiKey = config["ANTHROPIC_API_KEY"]
            ?? throw new InvalidOperationException("ANTHROPIC_API_KEY is not set.");

        IAnthropicClient client = new AnthropicClient { ApiKey = apiKey };

        // ... ChatClientAgentOptions / Tools wiring unchanged from C1 ...

        var agent = client.AsAIAgent(
            options,
            clientFactory: inner => new ToolCallLoggingChatClient(
                inner, loggerFactory.CreateLogger<ToolCallLoggingChatClient>()),
            loggerFactory: loggerFactory);

        return agent.AsBuilder()
            .UseOpenTelemetry(OtelSourceName)
            .Build();
    }
}

  3. 步骤 3 — 在 Program.cs 中注册 OTel 流水线

    步骤 2 的切入点 2 只有在有人监听时才发出跨度。这一步加上这个监听者。在 Program.cs 中调用 builder.Services.AddOpenTelemetry() 并添加四样东西。 流水线末端的收集器把跨度写入 ClickHouse，也就是验证关卡要查的那张表。

    • 一个服务名 —— 它会成为每个跨度上的 service.name 资源属性。
    • AddAspNetCoreInstrumentation() —— 这是 下方常见坑一节描述的关键一行。
    • 为你命名的源以及两个 MAF 默认源调用 AddSource(…)。
    • AddOtlpExporter() —— 通过 OTEL_EXPORTER_OTLP_ENDPOINT 指向技术栈的 OTel 收集器。
    🔧 说明 — 放置位置 + using

    文件： Program.cs。
    放置位置：把这个代码块放在所有 builder.Services.* 注册之后、 var app = builder.Build(); 之前。
    using：在 Program.cs 顶部， 与现有的 using 语句一起加上这两个： 

    using OpenTelemetry.Resources;
using OpenTelemetry.Trace;

    三行 AddSource 顺序无所谓。第一行是步骤 2 的命名源，承载 UseOpenTelemetry 的跨度；第二行是 MAF 默认智能体源；第三行是 Microsoft.Extensions.AI 聊天客户端源。 AddAspNetCoreInstrumentation() 不可省，缺它会让整张 trace 表为空， 常见坑一节会解释原因。

    Program.cs 加在所有 builder.Services.* 之后 —— var app = builder.Build(); 之前 
    builder.Services.AddOpenTelemetry()
    .ConfigureResource(resource => resource.AddService("claudalytics-agent"))
    .WithTracing(tracing => tracing
        .AddAspNetCoreInstrumentation()
        .AddSource(AgentFactory.OtelSourceName)
        .AddSource("Experimental.Microsoft.Agents.AI")
        .AddSource("Experimental.Microsoft.Extensions.AI")
        .AddOtlpExporter());

    OTEL_EXPORTER_OTLP_ENDPOINT 环境变量在 docker-compose 中设置，指向技术栈中的 OpenTelemetry Collector 服务。该收集器扇出（fan-out）到 ClickHouse —— 也就是智能体（agent）用 SQL 工具（tool） 查询的同一张表。如果你通过 docker-compose up 运行， 在开发时就不需要手动配置该端点。

为什么吃自家狗粮在这里很重要

智能体（agent）的工作是回答关于 Claudalytics 遥测（telemetry）数据的问题。 通过把它自己的跨度导出到同一张 otel_traces 表，每一次智能体运行都会添加一行，供你 查询：调用了哪些工具（tool）、各自耗时多久、哪个模型 处理了哪一轮。你真的可以问智能体"过去一小时你做了多少次工具 调用？"，它会查询自己的 trace 数据来回答。这个反馈 闭环值得尽早构建 —— 它让 C3（工具审批） 这一课的 安全叙事变得具体得多，因为你能在 trace 表里看到那些危险的 调用，然后再去为它们设关卡（gate）。

验证

✅ 关卡（gate） — 未变绿前不要前进

以 Testing 模式启动技术栈：

dotnet run -- --environment Testing

发送一轮对话：

curl -s -X POST http://localhost:8124/chat \
  -H "Content-Type: application/json" \
  -d '{"message":"list my projects"}' | jq .

检查 1 —— 中间件（middleware）日志行。在控制台 你应该至少看到一行类似这样的输出： 

info: AiAgent.Middleware.ToolCallLoggingChatClient[0]
      Tool call requested: list_projects {"":""}
info: AiAgent.Middleware.ToolCallLoggingChatClient[0]
      Model round-trip: in=842 out=45 tokens

检查 2 —— ClickHouse 中的 OTel 跨度。等待几 秒让收集器刷新后，查询 otel_traces： 

SELECT ServiceName, SpanName, StatusCode
FROM otel_traces
WHERE ServiceName = 'claudalytics-agent'
  AND Timestamp > now() - INTERVAL 1 MINUTE
ORDER BY Timestamp DESC
LIMIT 20;

你应该看到若干行，其 SpanName 值包含 invoke_agent 和 execute_tool。

反向测试 —— 采样器的静默丢弃。注释 掉 .AddAspNetCoreInstrumentation()，重启，发送 同一轮对话，等 10 秒，重新运行 ClickHouse 查询。 otel_traces 表对该服务返回 零行 —— 即便智能体（agent）确实运行了、 控制台日志也出现了、HTTP 响应也是 正确的。智能体在工作而 trace 表却为空，正是 缺少 ASP.NET 埋点的确切症状。前进前请 恢复这一行。

⚠️ 常见坑
  • 智能体（agent）明明运行了，otel_traces 却为空 → 缺少 AddAspNetCoreInstrumentation()。 没有它，ASP.NET 自己的传入请求活动就是根 跨度，而 ParentBased 采样器（OTel 默认） 会以与父级相同的速率对其采样 —— 对于一个 未注册的源来说，这个速率是 0%。每个智能体子跨度都被静默 丢弃。没有任何警告；智能体工作正常；表却 为空。加上这一行，重启。
  • 日志行出现了，但 ClickHouse 行没出现 → OTEL_EXPORTER_OTLP_ENDPOINT 错误或不可达。 OTLP 导出器默认会静默吞掉导出错误。 检查环境中的 OTEL_EXPORTER_OTLP_ENDPOINT （在 Docker 内应为 http://otel-collector:4317，若在技术栈外 运行智能体则为 http://localhost:4317）。你可以 通过 OTEL_EXPORTER_OTLP_TRACES_ENDPOINT 和 OTEL_DIAGNOSTICS_FILE_DIRECTORY 启用导出器诊断。
  • 跨度存在，但归属到了错误的服务 名 → resource.AddService(…) 未调用，或调用时传了 错误的字符串。检查 ClickHouse 中的 ServiceName； 它应当是 claudalytics-agent。
  • 流式（streaming）对话没有产生工具调用（tool call）日志行 → GetStreamingResponseAsync 重写缺失， 或没有调用 yield return update。流式 路径走的是与非流式不同的方法 —— 两者都必须重写。
  • 编译时找不到 UseOpenTelemetry → 你直接在 AIAgent 上调用了它，而不是 在构建器上。调用链必须是 agent.AsBuilder().UseOpenTelemetry(sourceName).Build()。

接下来是什么

有了 ClickHouse 中的每一个智能体（agent）跨度，你现在就拥有了所需的数据， 可以让 C3 中的人工审批（approval）关卡（gate）变得有据可依：你可以 查询哪些 SQL 工具调用（tool call）最频繁、识别那些 触发大扫描的调用，并用这些证据来决定哪些工具 需要人工关卡。你在这里构建的中间件（middleware）直接为 那个决策提供输入。
