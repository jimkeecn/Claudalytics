第 02 课 · A2 · 模块 A — Hello agent

多轮记忆（会话（session））

★ Haiku

你将学到什么

A1 的 Claudalytics Copilot 每次只能单独回答一个问题。用户问完"本周最贵的项目"再追问"那前一天呢"， 模型却没有上一轮的记忆，追问就失败了。修复办法是 session。 AgentSession 为一次对话承载完整的消息历史，服务端把这些 session 放进一个 store，让模型在每次请求时都能看到之前的轮次。

本课你会加一个服务端 session store，以客户端回传的 session id 为键。你会验证：相同 id 给模型上下文，缺失 id 则给一张白纸。注意一个 已知局限：store 只存在进程内存里，服务器重启后所有 session 都会丢失。 本课接受这一点；B4 会让它持久化。

📘 讲解

AgentSession 与会话（session）存储

MAF 把一个对话线程表示为 AgentSession。你通过调用 agent.CreateSessionAsync() 来创建它，然后把它传入 后续每一次 agent.RunAsync(message, session) 调用。会话会累积 所有消息 —— 用户轮次、助手回复、工具调用（tool call）与结果 —— 因此模型在 后续的每一轮都能看到自己之前的推理。

会话对象本身只存活在内存中。要让它在多次 HTTP 请求之间存活下来， 你需要一个服务端存储。本项目使用一个注册为单例的 ConcurrentDictionary<string, AgentSession>， 以客户端在追问请求中回传的字符串 id 作为键。

本课涉及的关键 API 面：

  • agent.CreateSessionAsync(CancellationToken) —— 分配一个新的空线程。
  • agent.RunAsync(string message, AgentSession session, ...) —— 在线程内运行一轮。
  • ConcurrentDictionary<string, AgentSession> —— 服务端存储。
  • GetOrCreateSessionAsync —— 辅助模式：按 id 查找， 或新建一个。

为什么这两个概念必须分清

人们很容易以为"会话（session） id 就是会话"。其实不是。会话 id 是你的服务器凭空生成的一个字符串（一个 GUID），客户端 在第一次响应中收到它，并必须在追问时回传。会话 则是一个持有消息列表的、活生生的内存对象。你的存储把两者映射起来。 如果你跳过了存储，每个请求都会创建一个全新的会话，每次追问看起来都 像第一个问题 —— 模型没有任何记忆。

动手构建

  1. 把会话（session）存储注册为单例

    store 是每个 /chat 请求读写的唯一位置，必须是全应用 共享的单一实例，所以注册为单例。第 4 步的处理器会注入这同一个 字典。在 Program.cs 的 DI 块中、agent 注册之后、 var app = builder.Build(); 之前加一行。 ConcurrentDictionary 对并发请求安全，普通 Dictionary 会产生竞态。

    🔧 说明

    本步骤所需的 using —— 如果 Program.cs 顶部还没有，请加上：

    • using System.Collections.Concurrent; —— ConcurrentDictionary<,>
    • using Microsoft.Agents.AI; —— AgentSession（如果你在 A1 中已经加过，这里就已经有了）

    无需新增 NuGet 包 —— 这两个类型都随你在 A1 中安装的 Microsoft.Agents.AI 一起提供。

    Program.cs 
    builder.Services.AddSingleton<ConcurrentDictionary<string, AgentSession>>();

  2. 给聊天请求模型加上 sessionId

    第 3 步的辅助方法靠 SessionId 来决定复用还是新建 session，所以请求模型要带上它。客户端每次追问都回传它；缺失则表示 "开始一段新对话"。让这个 record 保持精简。

    🔧 说明

    用这个版本替换你 A1 中的 ChatRequest record —— 不要声明两次。把它放在 Program.cs 中 app.Run(); 之后的文件作用域处。

    Program.cs — 文件作用域，app.Run() 之后 
    internal sealed record ChatRequest(string Message, string? SessionId);

  3. 编写 GetOrCreate 辅助方法

    把"查找或新建"的逻辑集中在一处，让第 4 步的 /chat 处理器保持精简。它做两件事：先定 session id（客户端发来的，或新的 GUID），再在 store 里找对应的 AgentSession，找不到就 新建并存起来。它返回 id 和 session，供第 4 步使用。

    🔧 说明

    放置位置：这是一个文件作用域的 static 局部函数。把它放在 Program.cs 中 app.Run(); 之后 —— 放在 app.Run() 之前会触发 CS8803（"顶层语句 必须位于命名空间和类型声明之前"）。

    累积状态：你 A1 的 Program.cs 必须已经有 using Microsoft.Agents.AI;（用于 AgentSession）和 using System.Collections.Concurrent;（在上面 第 1 步加入）。

    Program.cs — 文件作用域 static，app.Run() 之后 
    static async Task<(string SessionId, AgentSession Session)> GetOrCreateSessionAsync(
    string? requestedSessionId, AIAgent agent,
    ConcurrentDictionary<string, AgentSession> sessions, CancellationToken ct)
{
    var sessionId = string.IsNullOrWhiteSpace(requestedSessionId)
        ? Guid.NewGuid().ToString("N")
        : requestedSessionId;

    if (!sessions.TryGetValue(sessionId, out var session))
    {
        session = await agent.CreateSessionAsync(ct);
        sessions[sessionId] = session;
    }

    return (sessionId, session);
}

    有两个细节值得注意：Guid.NewGuid().ToString("N") 会生成一个紧凑的 32 位十六进制字符串、不带连字符 —— 在 curl 里很容易复制。另外，TryGetValue 加上一次锁外赋值 在这里是安全的，因为 ConcurrentDictionary 的读取 路径是无锁的；两个针对同一 id 的并发首次请求之间的竞态是无害的 （其中一个会话胜出，另一个被 GC 回收）。

  4. 把辅助方法接入 /chat 端点（endpoint）

    这一步把第 1 到 3 步串起来。处理器注入第 1 步的 store，调用第 3 步的辅助方法，把返回的 session 传入 RunAsync，让模型 看到完整历史，并在响应中回传 session id。客户端下一轮再带上它， 对话就被串联起来。

    🔧 说明

    用这个版本替换你 A1 的 /chat 处理器 —— 不要把同一个 MapPost("/chat", ...) 路由注册两次，否则应用会 在启动时抛异常。把它放在 var app = builder.Build(); 之后的端点块中。

    Program.cs — 端点块，var app = builder.Build() 之后 
    app.MapPost("/chat", async (ChatRequest request, AIAgent agent,
    ConcurrentDictionary<string, AgentSession> sessions,
    CancellationToken ct) =>
{
    if (string.IsNullOrWhiteSpace(request.Message))
        return Results.BadRequest(new { error = "message is required" });

    var (sessionId, session) = await GetOrCreateSessionAsync(
        request.SessionId, agent, sessions, ct);

    var response = await agent.RunAsync(request.Message, session, cancellationToken: ct);

    return Results.Ok(new
    {
        sessionId,
        answer = response.Text,
    });
});

    上面的端点为了清晰起见做了精简。完整的 Program.cs 还接入了路由器（router）、审批（approval）请求以及 RecentUserMessages —— 这些会在后续课程中引入 （路由器见 D2，审批见 C3）。

  5. 如何端到端接入

    最终的 Program.cs 里，同步的 /chat 和 流式（streaming）的 /chat/stream 用同一套模式。流式 路径先调用 GetOrCreateSessionAsync，再把 session 传入 agent.RunStreamingAsync；无论阻塞还是流式，session 都是同一个对象、同一份历史。/chat/stream 是为将来的 Angular 聊天前端保留的。

    ℹ️ 仅预览 —— 现在先不要添加

    下面的代码片段仅供理解定位之用。它引用了三个 要到后续课程才会定义的类型：

    • PendingApproval —— 在 A3 中引入（工具审批（approval）的 HITL）。
    • SseEvent —— 在 A3 中引入（SSE 辅助方法）。
    • ToolApprovalRequestContent —— 在 C3 中引入（审批内容 类型）。

    现在不要把这个片段复制进你的 Program.cs。 等你学到 A3 时再完整添加 /chat/stream。会话存储 的接入（GetOrCreateSessionAsync）才是 A2 中唯一 需要新增的部分。

    Program.cs 
    app.MapPost("/chat/stream", async (HttpContext context, AIAgent agent,
    ConcurrentDictionary<string, AgentSession> sessions,
    ConcurrentDictionary<string, PendingApproval> approvals, CancellationToken ct) =>
{
    var request = await context.Request.ReadFromJsonAsync<ChatRequest>(ct);
    if (request is null || string.IsNullOrWhiteSpace(request.Message))
    {
        context.Response.StatusCode = StatusCodes.Status400BadRequest;
        return;
    }

    var (sessionId, session) = await GetOrCreateSessionAsync(
        request.SessionId, agent, sessions, ct);

    context.Response.Headers.ContentType = "text/event-stream";
    context.Response.Headers.CacheControl = "no-cache";
    await SseEvent.WriteAsync(context.Response, "session", new { sessionId }, ct);

    // ... token/tool_call/done events follow — see A3 for the full implementation
});

    session 事件最先发出，这样一个在没有先前 id 的 情况下打开流的客户端，就能在任何 token 到来之前立即获知它的新 id。

验证

✅ 关卡（gate） — 未变绿前不要前进

以 Testing 模式启动服务器（那个 -- 分隔符至关重要 —— 完整解释见 A1）： 

dotnet run -- --environment Testing

第 1 轮 —— 问一个对时间敏感的问题，并捕获会话 id： 

curl -s -X POST http://localhost:8124/chat \
  -H "Content-Type: application/json" \
  -d '{"message": "What was the most expensive project this week?"}' \
  | tee /tmp/t1.json

从响应中复制 sessionId 的值 —— 它是一个 32 位的 十六进制字符串。

第 2 轮 —— 用同一个 id 发起一个相对性的追问： 

curl -s -X POST http://localhost:8124/chat \
  -H "Content-Type: application/json" \
  -d '{"message": "And the day before that?", "sessionId": "PASTE_SESSION_ID_HERE"}' \
  | tee /tmp/t2.json

响应必须引用第 1 轮中相同的项目名称，或者连贯地承接日期的变化 —— 这证明模型同时看到了两条消息。如果答案令人困惑或答非所问， 说明会话没有被串联起来。

反向测试 —— 相同的追问但不带会话 id： 

curl -s -X POST http://localhost:8124/chat \
  -H "Content-Type: application/json" \
  -d '{"message": "And the day before that?"}' \
  | tee /tmp/t3.json

这必须产生一个困惑、含糊或反问式的回应 —— 模型对"前一天" 没有任何上下文（context）。如果它依然连贯作答，说明你的 GetOrCreateSessionAsync 复用了错误的会话 （检查：当 requestedSessionId 为 null 时，你是否 生成了一个全新的 GUID，而不是退回到某个固定的键）。

存储检查 —— 确认两个会话彼此独立： 

# The response from /tmp/t1.json and /tmp/t3.json must have DIFFERENT sessionId values.
jq -r .sessionId /tmp/t1.json
jq -r .sessionId /tmp/t3.json

两个不同的 GUID 证明：每个无会话 id 的请求都创建了自己的存储 条目。

⚠️ 常见坑
  • 会话存储被注册为 scoped 或 transient → 每个请求都会注入一个全新的字典；所有已存储的会话对下一个 请求都是不可见的。请把字典注册为 Singleton。
  • 向 RunAsync 传入 null 会话 → MAF 会在内部创建一个匿名的临时会话；响应没有可返回的 id， 而且即便字典里有正确的条目，每个请求仍是一张白纸。务必把 取出或新建的 AgentSession 显式传入。
  • 当 SessionId 缺失时不生成 id → 每个无会话 id 的请求都会复用同一个 "" 或 null 键，从而用每个用户的消息污染同一个共享会话。当调用方省略 id 时，无条件地生成一个全新的 GUID。
  • 会话存储无法在重启之间持久化（durable） → ConcurrentDictionary 只存活在进程内存中。在 dotnet run 重启之后，所有会话都会消失。对本课 而言这是预期行为；持久化将在 B4 中通过检查点（checkpoint）来解决。
