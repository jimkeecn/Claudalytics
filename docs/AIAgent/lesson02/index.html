Lesson 02 · A2 · Module A — Hello agent

Multi-turn memory (sessions)

★ Haiku

What you'll learn

In A1 the Claudalytics Copilot answered each question alone. A user could ask "What was the most expensive project this week?" and then "And the day before that?", but the model had no memory of the first question, so the follow-up failed. The fix is a session. A AgentSession holds the full message history for one conversation, and your server keeps these sessions in a store so the model sees the earlier turns on every new request.

In this lesson you add a server-side session store, keyed by a session id the client sends back. You prove that the same id gives the model context, and a missing id gives it a blank slate. Note one limit you accept here: the store lives in process memory, so every session is lost when the server restarts. That is fine for now; B4 makes it durable.

📘 Teach

AgentSession and the session store

MAF represents one conversation thread as an AgentSession. You create one by calling agent.CreateSessionAsync(), and you pass it into every subsequent agent.RunAsync(message, session) call. The session accumulates all messages — user turns, assistant replies, tool calls and results — so the model sees its own prior reasoning on every subsequent turn.

The session object itself lives only in memory. To make it survive across HTTP requests you need a server-side store. The project uses a ConcurrentDictionary<string, AgentSession> registered as a singleton, keyed by a string id that the client echoes on follow-up requests.

Key API surfaces in this lesson:

  • agent.CreateSessionAsync(CancellationToken) — allocates a new empty thread.
  • agent.RunAsync(string message, AgentSession session, ...) — runs one turn inside the thread.
  • ConcurrentDictionary<string, AgentSession> — the server-side store.
  • GetOrCreateSessionAsync — the helper pattern: look up by id or mint a new one.

Why two concepts must stay separate

It is easy to think "the session id is the session." It is not. The session id is a string your server makes (a GUID). The client gets it on the first response and sends it back on follow-ups. The session is a live in-memory object that holds the message list. Your store maps the id to the object. If you skip the store, every request creates a new session. Then every follow-up looks like a first question, and the model has no memory.

Build it

  1. Register the session store as a singleton

    The store is the one place every /chat request reads from and writes to. It must be a single shared instance for the whole app, so you register it as a singleton. The /chat handler in step 4 injects this same dictionary and uses it to find or save sessions.

    Add one line to Program.cs in the DI block, after your agent registration and before var app = builder.Build();. A ConcurrentDictionary is safe for concurrent HTTP requests. A plain Dictionary will race.

    🔧 Note

    Required usings for this step — add to the top of Program.cs if not already present:

    • using System.Collections.Concurrent; — ConcurrentDictionary<,>
    • using Microsoft.Agents.AI; — AgentSession (already in A1 if you added it there)

    No new NuGet packages — both types ship in Microsoft.Agents.AI which you installed in A1.

    Program.cs 
    builder.Services.AddSingleton<ConcurrentDictionary<string, AgentSession>>();

  2. Add sessionId to the chat request model

    The helper in step 3 reads SessionId to decide whether to reuse a session or make a new one. So the request model needs a place to carry it. The client sends its session id on every follow-up. When the id is missing, that means "start a new conversation." Keep the record small.

    🔧 Note

    Replace your A1 ChatRequest record with this version — do not declare it twice. Place it at file scope in Program.cs after app.Run();.

    Program.cs — file scope, after app.Run() 
    internal sealed record ChatRequest(string Message, string? SessionId);

  3. Write the GetOrCreate helper

    This helper holds the lookup-or-create logic in one place, so the /chat handler in step 4 stays short. It does two jobs. First it picks a session id: the one the client sent, or a new GUID if none was sent. Then it finds the AgentSession for that id in the store, or creates one and saves it. It returns both the id and the session. The handler in step 4 uses the id in its reply and passes the session to RunAsync.

    🔧 Note

    Placement: this is a file-scope static local function. Place it in Program.cs after app.Run(); — putting it before app.Run() causes CS8803 ("Top-level statements must precede namespace and type declarations").

    Cumulative state: your A1 Program.cs must already have using Microsoft.Agents.AI; (for AgentSession) and using System.Collections.Concurrent; (added in step 1 above).

    Program.cs — file-scope static, after app.Run() 
    static async Task<(string SessionId, AgentSession Session)> GetOrCreateSessionAsync(
    string? requestedSessionId, AIAgent agent,
    ConcurrentDictionary<string, AgentSession> sessions, CancellationToken ct)
{
    var sessionId = string.IsNullOrWhiteSpace(requestedSessionId)
        ? Guid.NewGuid().ToString("N")
        : requestedSessionId;

    if (!sessions.TryGetValue(sessionId, out var session))
    {
        session = await agent.CreateSessionAsync(ct);
        sessions[sessionId] = session;
    }

    return (sessionId, session);
}

    Two details are worth noticing. Guid.NewGuid().ToString("N") makes a compact 32-character hex string with no dashes, which is easy to copy in curl. And TryGetValue followed by a plain assignment is safe here, because the read path of ConcurrentDictionary is lock-free. If two first requests for the same id arrive at once, the race is harmless. One session wins and the other is collected by the GC.

  4. Wire the helper into the /chat endpoint

    This step connects the pieces from steps 1 to 3. The handler injects the store from step 1, calls the helper from step 3, and passes the returned session into RunAsync so the model sees the full history. It sends the session id back in the response. The client reads that id and sends it again on the next turn, which is what keeps the conversation threaded.

    🔧 Note

    Replace your A1 /chat handler with this version — do not register the same MapPost("/chat", ...) route twice or the app will throw on startup. Place this in the endpoints block after var app = builder.Build();.

    Program.cs — endpoints block, after var app = builder.Build() 
    app.MapPost("/chat", async (ChatRequest request, AIAgent agent,
    ConcurrentDictionary<string, AgentSession> sessions,
    CancellationToken ct) =>
{
    if (string.IsNullOrWhiteSpace(request.Message))
        return Results.BadRequest(new { error = "message is required" });

    var (sessionId, session) = await GetOrCreateSessionAsync(
        request.SessionId, agent, sessions, ct);

    var response = await agent.RunAsync(request.Message, session, cancellationToken: ct);

    return Results.Ok(new
    {
        sessionId,
        answer = response.Text,
    });
});

    The endpoint above is trimmed for clarity. The full Program.cs also wires the router, approval requests, and RecentUserMessages — those are introduced in later lessons (D2 for the router, C3 for approvals).

  5. How it wires together end-to-end

    In the final Program.cs the same pattern is used for both the synchronous /chat endpoint and the streaming /chat/stream endpoint. The streaming path calls GetOrCreateSessionAsync first, then passes the session into agent.RunStreamingAsync. The session is the same object with the same history, whether the turn is blocking or streaming. This /chat/stream endpoint is kept for the future Angular chatbot front-end.

    The snippet below is shown for orientation only. It references three types that are not defined until later lessons:

    • PendingApproval — introduced in A3 (tool-approval HITL).
    • SseEvent — introduced in A3 (SSE helpers).
    • ToolApprovalRequestContent — introduced in C3 (approval content type).

    Program.cs 
    app.MapPost("/chat/stream", async (HttpContext context, AIAgent agent,
    ConcurrentDictionary<string, AgentSession> sessions,
    ConcurrentDictionary<string, PendingApproval> approvals, CancellationToken ct) =>
{
    var request = await context.Request.ReadFromJsonAsync<ChatRequest>(ct);
    if (request is null || string.IsNullOrWhiteSpace(request.Message))
    {
        context.Response.StatusCode = StatusCodes.Status400BadRequest;
        return;
    }

    var (sessionId, session) = await GetOrCreateSessionAsync(
        request.SessionId, agent, sessions, ct);

    context.Response.Headers.ContentType = "text/event-stream";
    context.Response.Headers.CacheControl = "no-cache";
    await SseEvent.WriteAsync(context.Response, "session", new { sessionId }, ct);

    // ... token/tool_call/done events follow — see A3 for the full implementation
});

    The session event is sent first. A client that opened the stream without an id learns its new id right away, before any tokens arrive.

Verify

✅ Gate — do not advance until green

Start the server in Testing mode (the -- separator is load-bearing — see A1 for the full explanation): 

dotnet run -- --environment Testing

Turn 1 — ask a time-sensitive question, capture the session id: 

curl -s -X POST http://localhost:8124/chat \
  -H "Content-Type: application/json" \
  -d '{"message": "What was the most expensive project this week?"}' \
  | tee /tmp/t1.json

Copy the sessionId value from the response — it is a 32-char hex string.

Turn 2 — follow up with a relative question using the same id: 

curl -s -X POST http://localhost:8124/chat \
  -H "Content-Type: application/json" \
  -d '{"message": "And the day before that?", "sessionId": "PASTE_SESSION_ID_HERE"}' \
  | tee /tmp/t2.json

The response must reference the same project name from turn 1, or acknowledge the date shift coherently — proof the model saw both messages. A confused or topic-changing answer means the session was not threaded.

Negative test — same follow-up WITHOUT the session id: 

curl -s -X POST http://localhost:8124/chat \
  -H "Content-Type: application/json" \
  -d '{"message": "And the day before that?"}' \
  | tee /tmp/t3.json

This must produce a confused, vague, or clarifying-question response — the model has no context for "the day before that." If it answers coherently anyway, your GetOrCreateSessionAsync is reusing the wrong session (check that you are generating a fresh GUID when requestedSessionId is null, not falling back to a fixed key).

Store check — confirm both sessions are independent: 

# The response from /tmp/t1.json and /tmp/t3.json must have DIFFERENT sessionId values.
jq -r .sessionId /tmp/t1.json
jq -r .sessionId /tmp/t3.json

Two different GUIDs confirm each sessionless request created its own store entry.

⚠️ Pitfalls
  • Session store registered as scoped or transient → a fresh dictionary is injected per request; all stored sessions are invisible to the next request. Register the dictionary as a Singleton.
  • Passing null session to RunAsync → MAF creates an anonymous ephemeral session internally; the response has no id to return, and each request is a blank slate even if the dictionary contains the right entry. Always pass the retrieved or created AgentSession explicitly.
  • Generating no id when SessionId is absent → every sessionless request reuses the same "" or null key, contaminating a single shared session with every user's messages. Mint a fresh GUID unconditionally when the caller omits the id.
  • Session store is not persistent across restarts → a ConcurrentDictionary lives only in process memory. After dotnet run restarts, all sessions are gone. For this lesson that is expected; persistence is addressed in B4 via checkpoints.
