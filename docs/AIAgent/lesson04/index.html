Lesson 04 · B1 · Module B — The graph, before intelligence

Executors & edges: a no-LLM fan-out pipeline

★★ No LLM — free to rerun

What you'll learn

A Claudalytics investigation runs several ClickHouse probes against telemetry, and if you wire that work as one tangled method, a wrong result or a stuck run gives you no way to tell which probe failed or whether they even ran in parallel. The MAF workflow runtime fixes this by splitting the work into typed nodes called executors joined by edges: each executor receives one message type, does one job, and emits a message to the next node, so every step is named, isolated, and testable on its own.

You do not need an LLM to use this runtime. This lesson wires a planner node that fans out three probe jobs across three worker nodes in parallel, then joins the raw results in a fan-in node. No model is called at any point. That is deliberate. With no model, every run is free and deterministic, so you can rerun the graph as many times as you need while debugging it. The collector you build here is ♻ scaffolding. It gets replaced in B3 by an LLM synthesis node. First, make the plumbing visible before anything intelligent lives in it.

📘 Teach

The three primitives

  • Executor<T> — a code node. Subclass it, specify the input message type T, implement HandleAsync. Give the executor a unique string id in its constructor. One executor = one handler for one message type.
  • Output protocol attributes — every message an executor sends must be declared via [SendsMessage(typeof(M))] on the class; messages an executor yields as final output use [YieldsOutput(typeof(M))]. Sends of undeclared types throw at runtime with a clear error naming the executor and the type. This is the contract, not a hint.
  • Edges — you register them on a WorkflowBuilder:
    • AddFanOutEdge — one source, N targets; a partitioner lambda maps each message to one or more target indices.
    • AddFanInBarrierEdge — N sources, one sink; the sink fires only after every upstream has delivered. This is how you join parallel work.
    • AddEdge<T> — typed direct edge with an optional predicate. The message type picks the route; the predicate can filter further.

MAF API surfaces used here: Executor<T>, [SendsMessage], [YieldsOutput], WorkflowBuilder, AddFanOutEdge, AddFanInBarrierEdge, AddEdge<T>, IWorkflowContext.SendMessageAsync, IWorkflowContext.YieldsOutputAsync, builder.WithOutputFrom(...).Build().

The graph shape for this lesson

A simplified version of the investigation graph. The full app adds a validator, a HITL port, and a deep-dive branch (covered in later lessons). 

                        ┌─> probe-0 ─┐
  plan ──fan-out────────┼─> probe-1 ─┼──fan-in barrier──> collector ──> output
                        └─> probe-2 ─┘

  1. Introduce the ClickHouse client

    B1 is the first lesson that runs real queries against ClickHouse. The probe executor you write later needs something to send SQL with, so add that client first. It is a read-only HTTP client that every probe executor calls. It sends each request as an HTTP POST to the ClickHouse native interface and returns tab-separated text (TSVWithNames), which is the format the executors read. Connection settings come from configuration (CLICKHOUSE_URL, CLICKHOUSE_USER, CLICKHOUSE_PASSWORD). The localhost defaults let the app start with no environment override.

    Tools/ClickHouseClient.cs 
    using Microsoft.Extensions.Configuration;

namespace AiAgent.Tools;

/// <summary>
/// Thin HTTP client for ClickHouse, connecting as the read-only agent_ro user.
/// Per-query limits are sent as URL settings on every request.
/// </summary>
public sealed class ClickHouseClient(HttpClient http, IConfiguration config)
{
    private readonly string _baseUrl = config["CLICKHOUSE_URL"] ?? "http://localhost:8123";
    private readonly string _user = config["CLICKHOUSE_USER"] ?? "agent_ro";
    private readonly string _password = config["CLICKHOUSE_PASSWORD"] ?? "";

    public async Task<string> QueryAsync(string sql, CancellationToken ct = default)
    {
        var url = $"{_baseUrl}/?user={Uri.EscapeDataString(_user)}" +
                  $"&password={Uri.EscapeDataString(_password)}" +
                  "&database=claudalytics" +
                  "&max_execution_time=30" +
                  "&max_result_rows=1000" +
                  "&result_overflow_mode=break";

        var response = await http.PostAsync(url, new StringContent(sql + " FORMAT TSVWithNames"), ct);
        var body = await response.Content.ReadAsStringAsync(ct);

        if (!response.IsSuccessStatusCode)
            throw new InvalidOperationException($"ClickHouse error: {body.Trim()}");

        return string.IsNullOrWhiteSpace(body) ? "(no rows)" : body.Trim();
    }
}

    Register it in Program.cs before var app = builder.Build();:

  2. Define the message types

    Messages are the contracts between nodes. Define them first so every executor below has a typed input and output to name. Use sealed record. Records give structural equality and clear constructors, and sealed prevents accidental subclass routing. All message types must round-trip through JSON, because the workflow engine may checkpoint them.

    Workflows/InvestigationModels.cs 
    using Microsoft.Agents.AI.Workflows;

namespace AiAgent.Workflows;

/// <summary>Workflow input: how many days of telemetry to investigate.</summary>
public sealed record InvestigationRequest(int Days);

public sealed record ProbeJob(int Slot, string Name, string Sql, int Days);

public sealed record ProbeResult(string Name, string Rows, bool HasData);

    Here is who reads each field. The planner sends ProbeJob, and the fan-out partitioner reads its Slot to route each job to the right probe executor. The probe executor sends ProbeResult, which the collector reads to build the final output. HasData is true when the rows hold usable numbers; the validator added in a later lesson reads it.

  3. Write the planner executor

    The planner is the start node. It turns one request into the three probe jobs the rest of the graph runs in parallel. It receives an InvestigationRequest and sends three ProbeJob messages. The fan-out edge you wire later reads each job's Slot to pick which probe executor gets it.

    The [SendsMessage] attribute on the class is not optional. It declares which message types this executor is allowed to send. Omit it and the first SendMessageAsync call throws at runtime.

    Workflows/InvestigationExecutors.cs 
    using Microsoft.Agents.AI;
using Microsoft.Agents.AI.Workflows;

namespace AiAgent.Workflows;

[SendsMessage(typeof(ProbeJob))]
public sealed class PlanExecutor() : Executor<InvestigationRequest>("plan")
{
    public override async ValueTask HandleAsync(
        InvestigationRequest request, IWorkflowContext context, CancellationToken cancellationToken = default)
    {
        var days = Math.Clamp(request.Days, 1, 90);

        ProbeJob[] jobs =
        [
            new(0, "cost-trend", $"""
                SELECT toDate(Timestamp) AS day,
                       round(sum(toFloat64OrZero(LogAttributes['cost_usd'])), 2) AS cost_usd
                FROM otel_logs
                WHERE LogAttributes['event.name'] = 'api_request'
                  AND Timestamp >= now() - INTERVAL {days} DAY
                GROUP BY day ORDER BY day
                """, days),
            new(1, "tool-failures", $"""
                SELECT LogAttributes['tool_name'] AS tool_name, count() AS calls,
                       countIf(LogAttributes['success'] != 'true') AS failures
                FROM otel_logs
                WHERE LogAttributes['event.name'] = 'tool_result'
                  AND Timestamp >= now() - INTERVAL {days} DAY
                GROUP BY tool_name ORDER BY failures DESC LIMIT 10
                """, days),
            new(2, "security-events", $"""
                SELECT pattern_category, count() AS exposures
                FROM credential_exposures
                WHERE timestamp >= now() - INTERVAL {days} DAY
                GROUP BY pattern_category ORDER BY exposures DESC
                """, days),
        ];

        foreach (var job in jobs)
            await context.SendMessageAsync(job, cancellationToken: cancellationToken);
    }
}

    Source: Workflows/InvestigationExecutors.cs — PlanExecutor. SQL is verbatim; this lesson omits custom progress events (B2's topic).

  4. Write the probe executor

    This is the worker node. It runs one probe's SQL against ClickHouse and reports the rows back. You write the class once and create three instances of it. Each instance receives a ProbeJob and sends a ProbeResult that the collector reads later. The fan-out edge decides which instance gets which job, so the executor itself does not need to care about routing.

    Workflows/InvestigationExecutors.cs — add to the SAME file, after PlanExecutor's closing brace; usings are already at the top of the file from step 2. 
    [SendsMessage(typeof(ProbeResult))]
public sealed class ProbeExecutor(string id, ClickHouseClient clickHouse) : Executor<ProbeJob>(id)
{
    public override async ValueTask HandleAsync(
        ProbeJob job, IWorkflowContext context, CancellationToken cancellationToken = default)
    {
        string rows;
        try
        {
            rows = await clickHouse.QueryAsync(job.Sql, cancellationToken);
        }
        catch (Exception ex)
        {
            rows = $"QUERY FAILED: {ex.Message}";
        }

        var hasData = !rows.StartsWith("QUERY FAILED") && rows != "(no rows)" && rows.Any(char.IsDigit);
        await context.SendMessageAsync(new ProbeResult(job.Name, rows, hasData), cancellationToken: cancellationToken);
    }
}

    Catching query failures keeps the fan-in from stalling: all three probes always deliver a result. The app also writes to workflow state here — that comes in B4.

  5. Write the collector executor (♻ scaffolding)

    The collector is the join node. It sits behind the fan-in barrier and turns the three separate probe results into one output. It receives ProbeResult messages one at a time as each probe finishes. It adds each one to a list, and once all three have arrived, it joins them into a single string and yields that string as the workflow output.

    This collector is ♻ scaffolding. It just concatenates the raw rows so you can see the fan-in work with no LLM cost. It gets replaced in B3 by a SynthesisExecutor that writes a real report. The accumulated list lives in an instance field, which is a problem dissected in B4.

    Workflows/InvestigationExecutors.cs — add to the SAME file, after ProbeExecutor's closing brace; usings already at top. 
    [YieldsOutput(typeof(string))]
public sealed class CollectorExecutor() : Executor<ProbeResult>("collector")
{
    private readonly List<ProbeResult> accumulated = [];
    private const int ExpectedProbes = 3;

    public override async ValueTask HandleAsync(
        ProbeResult result, IWorkflowContext context, CancellationToken cancellationToken = default)
    {
        accumulated.Add(result);

        if (accumulated.Count < ExpectedProbes)
            return;

        var combined = string.Join("\n\n", accumulated.Select(probe =>
            $"=== {probe.Name} ===\n{probe.Rows}"));

        await context.YieldOutputAsync(combined, cancellationToken);
    }
}
    ℹ️

    The accumulated instance field works for a single run in a single process. It is the exact state-in-field trap dissected in B4: if the process is killed and resumed, the field starts empty and the output is missing or incomplete. Right now it does its job — makes the fan-in visible and testable.

    This is the v2 node that replaces CollectorExecutor in B3. It holds a real AIAgent and turns the probe data into a markdown report. It is shown here only for context. Do not add it yet.

    Workflows/InvestigationExecutors.cs — SynthesisExecutor 
    [YieldsOutput(typeof(string))]
public sealed class SynthesisExecutor(AIAgent writer) : Executor<Findings>("synthesis")
{
    public override async ValueTask HandleAsync(
        Findings findings, IWorkflowContext context, CancellationToken cancellationToken = default)
    {
        var probesText = string.Join("\n\n", findings.Results.Select(probe =>
            $"## {probe.Name}\n{probe.Rows}"));
        var notesText = findings.ValidationNotes.Count == 0
            ? "(none)"
            : string.Join("\n", findings.ValidationNotes);

        var response = await writer.RunAsync($"""
            Write a short markdown investigation report over the last {findings.Days} days of
            Claude Code telemetry. Cost spike detected: {findings.CostSpike}.

            Probe data (TSV):
            {probesText}

            Validator notes (mention them honestly):
            {notesText}

            Shape: headline numbers, findings, then 1-3 recommendations.
            Use only the numbers in the data above.
            """, cancellationToken: cancellationToken);

        await context.YieldOutputAsync(response.Text, cancellationToken);
    }
}

  6. Wire the graph with WorkflowBuilder

    The executors above do not know about each other. The edges you register here are what connect them into one graph. This step creates the nodes and the builder. The builder takes the starting executor, the planner, as its constructor argument. You add the edges in the next two blocks.

    Workflows/ProbeWorkflow.cs 
    using AiAgent.Tools;
using Microsoft.Agents.AI;
using Microsoft.Agents.AI.Workflows;

namespace AiAgent.Workflows;

/// <summary>
/// Probe pipeline — zero LLM:
///
///                     ┌─> probe-0 ─┐
///   plan ──fan-out────┼─> probe-1 ─┼──fan-in barrier──> collector ──> output
///                     └─> probe-2 ─┘
///
/// CollectorExecutor is ♻ scaffolding replaced by SynthesisExecutor in B3.
/// </summary>
public static class ProbeWorkflow
{
    public static Workflow Build(ClickHouseClient clickHouse)
    {
        var plan = new PlanExecutor();
        ProbeExecutor[] probes =
        [
            new("probe-0", clickHouse),
            new("probe-1", clickHouse),
            new("probe-2", clickHouse),
        ];
        var collector = new CollectorExecutor();

        var builder = new WorkflowBuilder(plan);

    The fan-out edge sends the planner's jobs to the probes. The partitioner lambda receives each emitted ProbeJob and returns an array of target indices. It reads the job's Slot to pick one probe. The job?.Slot ?? 0 guards against a null message; a partitioner must never throw on null.

    Workflows/ProbeWorkflow.cs — inside Build, after the builder 
            builder.AddFanOutEdge<ProbeJob>(plan, probes.Select(p => (ExecutorBinding)p),
            (job, targetCount) => [(job?.Slot ?? 0) % targetCount]);

    The fan-in barrier joins the parallel probes back into one node. The collector fires only after all three probes have delivered a ProbeResult. WithOutputFrom(collector) marks the collector as the terminal node. Point it at a probe executor instead, and RunAsync returns after the first probe rather than waiting for the fan-in.

    Workflows/ProbeWorkflow.cs — inside Build, after the fan-out edge 
            builder.AddFanInBarrierEdge(probes.Select(p => (ExecutorBinding)p), collector);

        return builder.WithOutputFrom(collector).Build();
    }
}

  7. Expose a probe endpoint

    This is the entry point that runs the graph. It builds a fresh Workflow per request. A workflow instance is owned by one runner and cannot be reused across requests, so a shared instance would let one request's results leak into another.

    InProcessExecution.RunAsync(workflow, request) runs the graph to completion and returns a Run. The string the collector yields with YieldOutputAsync appears in run.NewEvents as a WorkflowOutputEvent. Its Data is the value to return to the caller, so the loop scans the events for that one output. The using line imports InProcessExecution, Run, and WorkflowOutputEvent.

    Program.cs — add before app.Run(); 
    using Microsoft.Agents.AI.Workflows;

app.MapPost("/probe", async (InvestigationRequest request, ClickHouseClient clickHouse, CancellationToken ct) =>
{
    var workflow = ProbeWorkflow.Build(clickHouse);
    var run = await InProcessExecution.RunAsync(workflow, request, cancellationToken: ct);

    string? report = null;
    foreach (var evt in run.NewEvents)
        if (evt is WorkflowOutputEvent output)
            report = output.Data?.ToString();

    return Results.Ok(new { report });
});

    Cumulative state note: ClickHouseClient is introduced in this lesson (B1) — step 1 above adds the file and registers it with builder.Services.AddHttpClient<ClickHouseClient>() before var app = builder.Build();. The /probe endpoint parameter-injects it directly from DI; no further registration is needed.

🔄 Evolution arc

CollectorExecutor is Arc 1, v1 — deliberately naive. It makes the fan-in observable with zero LLM cost. Two limitations drive the next lessons:

  • Raw TSV is unreadable. In B3 you swap the collector for a SynthesisExecutor that holds a writer agent — same graph, one node now intelligent.
  • The accumulated field does not survive a crash. In B4 you wire checkpointing, kill the process mid-run, and prove the field version fails on resume; then you move state into the workflow context.

Verify

✅ Gate — do not advance until green

Normal path:

curl -s -X POST http://localhost:8124/probe \
  -H "Content-Type: application/json" \
  -d '{"days": 7}' | jq .report

The response must be a non-empty string containing all three probe names (cost-trend, tool-failures, security-events) and at least one row of data (or a QUERY FAILED line if ClickHouse is not seeded). The important check is that all three sections appear — that proves the fan-in fired after all three parallel probes delivered.

Deliberate-failure exercise (costs nothing — no LLM):

Remove the [SendsMessage(typeof(ProbeJob))] attribute from PlanExecutor, recompile, and call the endpoint again. You should see: 

System.InvalidOperationException: Executor 'plan' attempted to send message of type 'ProbeJob'
which is not declared in its [SendsMessage] attributes.

Put the attribute back. This error text is the output protocol working as designed — the contract is enforced, not advisory.

Negative test — partitioner null tolerance:

Remove the null guard: (job, targetCount) => [job.Slot % targetCount]. A null message from upstream produces a NullReferenceException inside the partitioner. Restore the guard. Partitioners must always be null-tolerant.

⚠️ Pitfalls
  • Runtime throws "attempted to send message of type X, not declared" → you forgot a [SendsMessage(typeof(X))] attribute on the executor class. Check every executor that calls SendMessageAsync.
  • Collector only fires once but the output is missing two probes → the fan-in barrier is not registered correctly; all probe executors must be in the sources list passed to AddFanInBarrierEdge.
  • Partitioner throws NullReferenceException → guard against null in the lambda: (job, n) => [(job?.Slot ?? 0) % n].
  • Workflow reused across requests and the collector sees extra results → a Workflow object is owned by exactly one runner. Build a fresh instance per request with ProbeWorkflow.Build(...). The CollectorExecutor's accumulated field starts fresh each time only because the executor object itself is new.
  • WithOutputFrom points at the wrong executor → RunAsync returns after the first probe instead of waiting for the fan-in; always point it at the final output node.
