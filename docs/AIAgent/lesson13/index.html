Lesson 13 · D3 · Module D — Composition & orchestration

Agent-as-tool + model tiering

★★ Haiku + 1 real-tier check

What you'll learn

This lesson fixes two real problems in this app. First problem: the telemetry-report workflow you built in D1 can only run from its own /report endpoint. A user chatting with the DataAnalyst cannot ask for the report mid-conversation. You fix this by wrapping the whole report workflow as one callable tool on the DataAnalyst, so the LLM itself decides when to run it (agent-as-tool, AsAIFunction). Second problem: there is no cheap way to run the gates. Every model id already flows through ModelTiers (from A1), but with no Testing override each gate hits the production tier — Analyst is Sonnet, Reasoning is Opus — so the test loop costs real money. You fix this by adding an appsettings.Testing.json that collapses all three tiers to Haiku, so one --environment Testing switch makes every agent cheap with no code change.

The first move handles who calls whom; the second handles which model runs the call. By the end of this lesson every agent in the project reads its model from one helper, and the telemetry-report workflow is callable mid-conversation without a dedicated dispatch step.

📘 Teach

Agent-as-tool (AsAIFunction): any AIAgent exposes a .AsAIFunction(AIFunctionFactoryOptions) method that wraps the entire agent — its tools, its session, its instructions — as a single AIFunction. Register it in another agent's ChatOptions.Tools and the outer LLM will call it like any other function, passing a natural-language prompt and receiving the inner agent's final text as the result. This is LLM-chosen dispatch: the model picks when to invoke the sub-agent based on the tool description, in contrast to D2's code-chosen router which dispatches by pattern-matching a typed route decision.

Model tiering (ModelTiers): a three-line static helper that maps a job's reasoning demand to a model string read from IConfiguration. Tiers: Light (classification, compaction summarization), Analyst (SQL-over-schema work), Reasoning (cross-domain synthesis). Default values are baked in as fallbacks; appsettings.json overrides per tier, and appsettings.Testing.json overrides all three to Haiku so every gate runs cheaply. Without this indirection, hardcoded model ids at each call site are invisible to the Testing override — the Testing environment sets Models:Light, Models:Analyst, and Models:Reasoning, not individual string literals.

    Agents/ModelTiers.cs (introduced in A1/lesson01) 
    using Microsoft.Extensions.Configuration;

namespace AiAgent.Agents;

/// <summary>
/// Model tiering: one place that maps a job's reasoning demand to a model.
/// Light = classification/summarization, Analyst = SQL-over-schema work,
/// Reasoning = cross-domain synthesis and recommendations.
/// Defaults live here; appsettings "Models" section overrides per tier.
/// </summary>
public static class ModelTiers
{
    public static string Light(IConfiguration config)
        => config["Models:Light"] ?? "claude-haiku-4-5";

    public static string Analyst(IConfiguration config)
        => config["Models:Analyst"] ?? "claude-sonnet-4-6";

    public static string Reasoning(IConfiguration config)
        => config["Models:Reasoning"] ?? "claude-opus-4-8";
}

    What does belong to this lesson: wiring the Testing override in appsettings.Testing.json so all tiers collapse to Haiku during gates. Every model id across AgentFactory.cs, Router.cs, and ReportWorkflow.cs already reads from ModelTiers.* (you wired those in A1, D1, and D2), so the override reaches all of them.

    The keys you set here are read back by the three ModelTiers methods. When the app runs with --environment Testing, the .NET config loader merges this file on top of appsettings.json. After that merge, config["Models:Analyst"] returns "claude-haiku-4-5" instead of the production default. So every call site that reads from ModelTiers.Analyst(config) now gets Haiku, with no code change.   4. Add a guardrail description to the sub-agent tool

    The description you pass to AsAIFunction is the only signal the outer model has to decide when to call this tool. Two rules: name what it does precisely, and add an explicit cost warning so the model does not reach for it on casual questions. You use:

    "Expensive — only when the user asks for the weekly report."

    Without that sentence the LLM will call the multi-agent workflow for any question that touches cost or tools — burning Analyst-tier credits on a Haiku-tier clarification.

Model tiering and the Testing override

Every model id in this project already flows through ModelTiers — introduced in A1 and used since D1 and D2. AgentFactory.cs reads ModelTiers.Analyst(config) for the DataAnalyst and ModelTiers.Light(config) for the compaction summarizer. Router.cs reads ModelTiers.Light(config). ReportWorkflow.cs reads ModelTiers.Analyst(config) for the analysts and ModelTiers.Reasoning(config) for the summarizer.

Because the choice lives in one helper, a single config change reaches every agent. appsettings.Testing.json sets all three tiers to Haiku. So dotnet run -- --environment Testing makes every agent run cheap, with no code change. A literal model string at a call site would be invisible to that override: the Testing file sets Models:Light, Models:Analyst, and Models:Reasoning, not individual literals. That is the reason the choice is centralized in ModelTiers.

Why AsAIFunction vs D2's router dispatch

D2 dispatches with code: the router returns a typed RouteDecision and a switch statement picks the handler. This lesson's AsAIFunction dispatches with the model: the outer agent reads the tool description and decides whether and when to invoke the sub-agent during its own tool-call loop. The two mechanisms are complementary:

  • Code-chosen (router): deterministic, auditable, correct for capability menus where the catalog is known at build time.
  • LLM-chosen (AsAIFunction): flexible mid-conversation composition — the model can chain the sub-agent with other tools in a single turn, pass it a computed prompt, or skip it based on context the code-level router cannot see.

Both coexist: the router dispatches to the DataAnalyst session, and within that session the DataAnalyst can call the report workflow via run_weekly_report — two layers, two different dispatch mechanisms.

Verify

✅ Gate — do not advance until green

Check 1 — agent-as-tool fires on the chat stream (Haiku)

Start with the Testing environment (dotnet run -- --environment Testing). POST to /chat/stream with a nudging prompt: 

curl -s -N -X POST http://localhost:8124/chat/stream \
  -H "Content-Type: application/json" \
  -d '{"message": "please run the weekly report for the last 7 days"}'

You must see a tool_call SSE event with name: "run_weekly_report" in the stream, followed by a token event containing the report narrative, then done.

Check 2 — tiering (the ONE real-tier check)

Run without the Testing override for one turn only: 

dotnet run

POST one message to /chat (router turn) and one to /report (summarizer turn). Then query your OTel traces table — both span types must be present and their model_id attributes must differ: 

-- In ClickHouse (or your OTel viewer)
SELECT
    SpanAttributes['gen_ai.request.model'] AS model_id,
    count() AS spans
FROM otel_traces
WHERE ServiceName = 'claudalytics-agent'
  AND Timestamp > now() - INTERVAL 5 MINUTE
GROUP BY model_id;

You should see at least two distinct model ids — the Light-tier router and the Analyst/Reasoning-tier summarizer. Return to Testing immediately after this check.

Negative test

Back on Testing, POST a data question that does NOT mention the weekly report: "which project spent the most last week?" The stream must NOT contain a tool_call event named run_weekly_report. Identical model ids in the real-tier check means the config is not flowing — verify that you did not pass --environment Testing for that check, that appsettings.json holds the real (non-Haiku) Models values, and that every agent call site uses ModelTiers.* and not a literal string.

⚠️ Pitfalls
  • Sub-agent called on casual questions → description is too vague. Add "Expensive — only when the user explicitly asks for the weekly report" to the AsAIFunction description.
  • Identical model ids in the tiering check → a call site has a stray literal model string instead of a ModelTiers.* call. Search for "claude- across all .cs files; every hit outside ModelTiers.cs is one to fix.
  • Testing override has no effect → check the -- separator and environment name; full details in L0.
  • Report agent keyed service not resolved → the DataAnalyst factory receives null for reportAgent. Ensure GetRequiredKeyedService<AIAgent>("report") — not GetRequiredService<AIAgent> — is used when building the DataAnalyst.
  • Inner agent re-uses the outer session → when called via AsAIFunction the sub-agent runs a fresh ephemeral session each invocation (no session parameter is passed). This is correct. Do not pass the outer agent's AgentSession into the sub-agent's tool options.
