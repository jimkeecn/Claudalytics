Lesson 12 · D2 · Module D — Composition & orchestration

The router + menu registry

★★★ Haiku

What you'll learn

Right now POST /chat sends every message straight to the DataAnalyst. So "what can you do?" pays full analyst-tier cost and gets a made-up answer, because the analyst has no list of real capabilities. And there is no way to run a named action like the weekly report from D1 without the analyst guessing what you meant. You need a cheap step in front that reads the message and decides where it should go.

The orchestrator pattern adds that step: a small classifier agent — the router — in front of the more expensive analyst. In this lesson you build the classifier twice. The first version (v1) works, but it creates three separate lists that must stay in sync: the router's prompt catalog, the hand-written menu endpoint, and the dispatch switch. The second version (v2) collapses all three into one MenuRegistry — the single source of truth — so adding a capability is one entry, not three edits.

📘 Teach

The orchestrator pattern in MAF means a small, cheap, tool-less agent that classifies intent and routes to the appropriate handler — it never answers the question itself. The key MAF surface is RunAsync<T> (structured output), which forces the router to return a typed RouteDecision record rather than prose. The router is registered like any other agent via client.AsAIAgent(...) and .AsBuilder().UseOpenTelemetry(...).Build() — but it is deliberately kept at the Light model tier (cheapest, fastest) because it classifies, not reasons.

The MenuRegistry is not a MAF class — it is the application pattern that tames the router. It holds a dictionary of MenuItem records, each carrying an id, display metadata, a params hint, and an Invoke delegate. Two generated views emerge from it automatically: CatalogForPrompt() (injected into the router's system instructions) and the /menu JSON response (iterated at the HTTP layer). The dispatch switch becomes a single menu.TryGet(route.TargetId) call.

How the router fits the system

Every POST /chat turn runs through the router first. The router returns one of three intents:

  • chat — forward to the DataAnalyst with its full session; pay Analyst-tier cost.
  • menu — return the capability catalog directly; no further LLM call.
  • dispatch — invoke the named catalog item; the analyst is not involved.

The router never sees the full session history — it only sees the last few user messages (a RecentUserMessages ring buffer). This is intentional: the router's job is intent classification, not conversation understanding.

Build it

  1. Define the typed route decision

    The router must return data the /chat endpoint can branch on, not prose. So you give it a typed shape to fill in. Create Models/RouteDecision.cs. This is what the router returns via RunAsync<RouteDecision>, and the /chat switch (Step 5) reads route.Intent from it. The [Description] attributes are the schema hints that guide the model to fill each field correctly. Without them the model will guess.

    Models/RouteDecision.cs 
    using System.ComponentModel;

namespace AiAgent.Models;

/// <summary>
/// The router's structured-output verdict for one user turn.
/// </summary>
public sealed record RouteDecision(
    [property: Description("One of: 'chat' (free-form data question or follow-up — send to the analyst), " +
        "'menu' (user asks what the copilot can do, or wants to see the available actions), " +
        "'dispatch' (the message clearly requests one specific catalog item).")]
    string Intent,

    [property: Description("When intent is 'dispatch': the id of the catalog item to run. Otherwise null.")]
    string? TargetId,

    [property: Description("When intent is 'dispatch': parameters extracted from the message, " +
        "e.g. the time window like 'the last 7 days'. Otherwise null.")]
    string? Parameters);

    Note TargetId and Parameters are nullable — the model should leave them null for non-dispatch intents. The description constraint on Intent is the guard against the model inventing new intent strings.

  2. Build the MenuRegistry — single source of truth

    The registry collapses those three hand-synced lists into one source of truth. It is a plain class, not a MAF type. One entry drives three consumers: the router prompt, the /menu endpoint, and dispatch. Create Orchestration/MenuRegistry.cs. First the MenuItem record. Each item carries display fields and an Invoke delegate that runs the real agent/workflow and returns text:

    Orchestration/MenuRegistry.cs 
    namespace AiAgent.Orchestration;

public sealed record MenuItem(
    string Id,
    string Title,
    string Description,
    string ParamsHint,
    string TargetKind,
    string ModelTier,
    Func<string?, CancellationToken, Task<string>> Invoke);

    Next the registry itself. It indexes the items by id in a case-insensitive dictionary, and exposes three reads — one for each consumer. Items is read by the /menu endpoint, TryGet is called by the dispatch branch, and CatalogForPrompt() is the text the router prompt interpolates: 

    public sealed class MenuRegistry(IEnumerable<MenuItem> items)
{
    private readonly Dictionary<string, MenuItem> _items =
        items.ToDictionary(item => item.Id, StringComparer.OrdinalIgnoreCase);

    public IReadOnlyCollection<MenuItem> Items => _items.Values;

    public bool TryGet(string id, out MenuItem item) => _items.TryGetValue(id, out item!);

    public string CatalogForPrompt() => string.Join("\n", _items.Values.Select(item =>
        $"- {item.Id}: {item.Description} (params: {item.ParamsHint})"));
}

    TryGet is case-insensitive on purpose. The router might return "Weekly-Report" even though the id is "telemetry-report", and the lookup must still match. CatalogForPrompt() renders one bullet per item. The router reads this as its dispatch catalog.

  3. v1: router with a hardcoded prompt catalog and switch

    Compare that registry against the naive version it improves on. The v1 below is shown only to expose the problem the registry solves — you would not ship it. Read it, then look at where it breaks.

    In v1 the router's instructions hardcode the catalog as a literal string, the menu endpoint returns a second hardcoded list, and the dispatch handler is a switch with one case per capability: 

    // v1 Router — prompt catalog hardcoded (naive approach — do not ship)
var instructions = """
    Classify the user message into: chat | menu | dispatch.
    Catalog:
    - telemetry-report: runs the full multi-agent weekly report
    - cost-audit: detailed cost breakdown and savings advice
    Output only the structured decision.
    """;

// v1 /menu endpoint — SECOND copy of the same list
app.MapGet("/menu", () => Results.Ok(new {
    items = new[] {
        new { id = "telemetry-report", title = "Weekly report" },
        new { id = "cost-audit",    title = "Cost audit" },
    }
}));

// v1 /chat dispatch branch — THIRD copy
case "dispatch":
    return route.TargetId switch {
        "telemetry-report" => await RunWeeklyReport(route.Parameters, ct),
        "cost-audit"    => await RunCostAudit(route.Parameters, ct),
        _               => Results.BadRequest(new { error = "unknown target" }),
    };

    This works — until you add a capability. Then you must update the router's instructions string, the menu endpoint list, AND the dispatch switch. Three diffs, three chances to drift out of sync.

    In v2 the registry is the only place a capability is declared. The router's instructions are generated from menu.CatalogForPrompt(), the menu endpoint iterates menu.Items, and dispatch is menu.TryGet(route.TargetId). You build Agents/Router.cs in three parts. First the class takes the MenuRegistry as an argument and reads the API key, so the catalog is available when the prompt is built:

    Agents/Router.cs 
    using AiAgent.Orchestration;
using Anthropic;
using Microsoft.Agents.AI;

namespace AiAgent.Agents;

public static class Router
{
    public static AIAgent Create(IConfiguration config, MenuRegistry menu, ILoggerFactory loggerFactory)
    {
        var apiKey = config["ANTHROPIC_API_KEY"]
            ?? throw new InvalidOperationException("ANTHROPIC_API_KEY is not set.");

        IAnthropicClient client = new AnthropicClient { ApiKey = apiKey };

    Next the instructions string. It interpolates menu.CatalogForPrompt() directly, so the prompt IS the registry, rendered as text. The three intent names here — dispatch, menu, chat — are the same strings the /chat switch matches on in Step 5: 

            var instructions = $"""
            You are the router for the Claudalytics copilot. Classify each user message
            into exactly one intent:

            - "dispatch": the message clearly asks to run ONE of these catalog items.
              Set targetId to the item id and extract parameters (e.g. a time window)
              from the message into parameters. Catalog:
            {menu.CatalogForPrompt()}
            - "menu": the user asks what the copilot can do, what actions/reports are
              available, or for help/options.
            - "chat": everything else — ad-hoc data questions, follow-ups, analysis
              requests that do not name a catalog item. When in doubt, choose "chat".

            Output only the structured decision. Never answer the question yourself.
            """;

    Last, build the agent at the Light model tier and wrap it with OpenTelemetry. The router is cheap on purpose. Its spans carry the Light-tier model id, which is the proof in otel_traces that the cheap tier handled the turn: 

            var agent = client.AsAIAgent(
            model: ModelTiers.Light(config),
            instructions: instructions,
            name: "router",
            description: "Classifies each turn into chat | menu | dispatch.");

        return agent.AsBuilder()
            .UseOpenTelemetry(AgentFactory.OtelSourceName)
            .Build();
    }
}

    IConfiguration and ILoggerFactory come from Microsoft.Extensions.* implicit usings (.NET 9). No new NuGet package — Anthropic and Microsoft.Agents.AI were added in A1.

  4. Register the registry and wire the first catalog item

    The registry is empty until you fill it. So you register it as a singleton with one starting item, then register the router after it because the router takes the registry as an argument. The first item is the weekly report from D1 — already a workflow-as-agent, so its Invoke delegate just calls ReportRunner.RunAsync. This one entry is what the router prompt, the /menu endpoint, and dispatch all read.

    ℹ️ DI registration order

    The MenuRegistry factory calls sp.GetRequiredKeyedService<AIAgent>("report") — this is resolved at first use (singleton factory is lazy), but keeping the registration order explicit avoids surprises during startup or in tests:

    1. Register the "report" keyed agent (AddKeyedSingleton<AIAgent>("report", ...)) — from D1.
    2. Register MenuRegistry (below).
    3. Register the "router" keyed agent last — it takes MenuRegistry as a constructor argument.
    Program.cs — DI section (before var app = builder.Build()) 
    builder.Services.AddSingleton<MenuRegistry>(sp =>
{
    var reportAgent = sp.GetRequiredKeyedService<AIAgent>("report");

    return new MenuRegistry(
    [
        new MenuItem(
            Id: "telemetry-report",
            Title: "Weekly report",
            Description: "Full multi-agent telemetry report: cost, security and tooling " +
                         "analysts run concurrently, a summarizer writes the report.",
            ParamsHint: "time window and optionally a project, e.g. 'last 7 days, project claudalytics'",
            TargetKind: "workflow",
            ModelTier: "Analyst+Reasoning",
            Invoke: async (parameters, ct) =>
            {
                var window = string.IsNullOrWhiteSpace(parameters) ? "the last 7 days" : parameters;
                var (report, _) = await ReportRunner.RunAsync(reportAgent, window, ct);
                return report;
            }),
    ]);
});
    Program.cs — DI section, after MenuRegistry registration (before var app = builder.Build()) 
    builder.Services.AddKeyedSingleton<AIAgent>("router", (sp, _) => Router.Create(
    sp.GetRequiredService<IConfiguration>(),
    sp.GetRequiredService<MenuRegistry>(),
    sp.GetRequiredService<ILoggerFactory>()));

  5. Rewire the /chat endpoint to run through the router

    This is where the classifier earns its place. The chat endpoint now runs the router first, then branches on route.Intent. The analyst path becomes the default case. It is not thrown away — it is the same direct-chat path from before, now guarded by the classification step. You build this one endpoint in four parts.

    First the handler signature and the router call. It injects the keyed "router" agent and the menu, gets the session, builds a small prompt from the recent messages, and runs the router to get a RouteDecision:

    [FromKeyedServices] is in Microsoft.Extensions.DependencyInjection — covered by .NET 9 implicit usings. No extra using needed.

    Program.cs — endpoint section (after var app = builder.Build()) 
    app.MapPost("/chat", async (ChatRequest request, AIAgent agent,
    [FromKeyedServices("router")] AIAgent router, MenuRegistry menu,
    ConcurrentDictionary<string, AgentSession> sessions,
    ConcurrentDictionary<string, PendingApproval> approvals,
    RecentUserMessages recent, CancellationToken ct) =>
{
    if (string.IsNullOrWhiteSpace(request.Message))
        return Results.BadRequest(new { error = "message is required" });

    var (sessionId, session) = await GetOrCreateSessionAsync(request.SessionId, agent, sessions, ct);

    var routerPrompt = $"""
        Recent user messages in this session:
        {recent.Describe(sessionId)}

        New user message: {request.Message}
        """;
    var route = (await router.RunAsync<RouteDecision>(routerPrompt, cancellationToken: ct)).Result;
    recent.Add(sessionId, request.Message);

    switch (route.Intent.ToLowerInvariant())
    {

    The menu case returns the catalog directly, with no further LLM call. It reads menu.Items — the same registry the router prompt was built from: 

            case "menu":
            return Results.Ok(new
            {
                sessionId,
                kind = "menu",
                answer = (string?)null,
                menu = menu.Items.Select(item => new
                {
                    id = item.Id,
                    title = item.Title,
                    description = item.Description,
                    paramsHint = item.ParamsHint,
                }),
                toolCalls = Array.Empty<object>(),
                approvalRequest = (object?)null,
            });

    The dispatch case looks up the target id with menu.TryGet and runs that item's Invoke delegate. The pattern-match guard (when route.TargetId is not null && menu.TryGet(...)) means an unknown target id does not match this case at all. It falls through to default instead of throwing: 

            case "dispatch" when route.TargetId is not null && menu.TryGet(route.TargetId, out var item):
            var dispatched = await item.Invoke(route.Parameters, ct);
            return Results.Ok(new
            {
                sessionId,
                kind = "answer",
                answer = dispatched,
                menu = (object?)null,
                toolCalls = new[] { new { name = item.Id, arguments = (object?)route.Parameters } },
                approvalRequest = (object?)null,
            });

    The default case is the original direct-chat path. It handles three things: genuine chat, a dispatch with an unknown target that fell through, and any made-up intent the model returns. So the endpoint never returns a 500 because of a bad classification: 

            default:
            var response = await agent.RunAsync(request.Message, session, cancellationToken: ct);
            return Results.Ok(ToChatResponse(sessionId, session, response, approvals));
    }
});

  6. Add the /menu and /menu/invoke endpoints

    The same registry powers two more endpoints, so the catalog is reachable without going through the router. GET /menu is the machine-readable catalog a future UI renders as action buttons. POST /menu/invoke runs one item directly, which is useful for scripted workflows or tests. GET /menu reads menu.Items; /menu/invoke uses menu.TryGet then the item's Invoke delegate:

    Program.cs — endpoint section (after var app = builder.Build()) 
    app.MapGet("/menu", (MenuRegistry menu) => Results.Ok(new
{
    items = menu.Items.Select(item => new
    {
        id = item.Id,
        title = item.Title,
        description = item.Description,
        paramsHint = item.ParamsHint,
        targetKind = item.TargetKind,
        modelTier = item.ModelTier,
    }),
}));

app.MapPost("/menu/invoke", async (MenuInvokeRequest request, MenuRegistry menu, CancellationToken ct) =>
{
    if (string.IsNullOrWhiteSpace(request.ItemId) || !menu.TryGet(request.ItemId, out var item))
        return Results.NotFound(new { error = $"unknown menu item '{request.ItemId}'" });

    var answer = await item.Invoke(request.Params, ct);
    return Results.Ok(new
    {
        sessionId = request.SessionId,
        kind = "answer",
        answer,
        menu = (object?)null,
        toolCalls = new[] { new { name = item.Id, arguments = (object?)request.Params } },
        approvalRequest = (object?)null,
    });
});

    MenuInvokeRequest is the request body for /menu/invoke. It is an internal sealed record — place it at file scope after app.Run();, not inside the endpoint lambda:

    internal sealed record MenuInvokeRequest(string ItemId, string? Params, string? SessionId);

  7. Add a RecentUserMessages helper for router context

    A follow-up like "now for last month" makes no sense to the router with no history. So the router gets the last 3 user messages, not the full session. This keeps router calls cheap and keeps analyst-tier context out of a Light-tier call. The /chat handler in Step 5 reads this through recent.Describe(sessionId) when it builds the router prompt, and writes to it with recent.Add after each turn. Add this helper to Program.cs:

    First, register it in the DI section (before var app = builder.Build();):

    Program.cs — DI section (before var app = builder.Build()) 
    builder.Services.AddSingleton<RecentUserMessages>();

    Then add the class definition at file scope after app.Run(); — like other helper types in Program.cs, it lives at the bottom:

    Program.cs — file scope, after app.Run() 
    /// <summary>
/// Last few user messages per session — given to the router so follow-ups
/// ("now for last month") classify correctly without a full agent session.
/// </summary>
internal sealed class RecentUserMessages
{
    private const int Keep = 3;
    private readonly ConcurrentDictionary<string, Queue<string>> _store = new();

    public void Add(string sessionId, string message)
    {
        var queue = _store.GetOrAdd(sessionId, _ => new Queue<string>());
        lock (queue)
        {
            queue.Enqueue(message);
            while (queue.Count > Keep) queue.Dequeue();
        }
    }

    public string Describe(string sessionId)
    {
        if (!_store.TryGetValue(sessionId, out var queue)) return "(none)";
        lock (queue)
        {
            return queue.Count == 0 ? "(none)" : string.Join("\n", queue.Select(m => $"- {m}"));
        }
    }
}

    Without the recent-message context, a follow-up like "now for last month" arrives to the router with no history — it cannot tell whether the user is following up on a weekly report or asking for a cost query. The ring buffer solves this without threading the whole session through the router.

🔄 Evolution arc

This lesson resolves two evolution arcs simultaneously:

  • Arc 4 (D2): the direct chat endpoint had no classifier in front of it — it could not expose a capability catalog or dispatch to named workflows. The router adds that layer. The original direct-chat path is NOT thrown away — it becomes the default branch, surviving as the chat intent.
  • Arc 5 (D2): the v1 router's hardcoded prompt catalog, menu list, and dispatch switch are three places that drift every time a capability is added. The MenuRegistry collapses all three into one entry. Those three lists are thrown away.

In D3 the registry grows with insight specialists and more workflow items; the registry pattern absorbs every new entry with zero structural change.

⚠️ Pitfalls
  • Router returns plain prose instead of JSON → tools are registered on the router. RunAsync<T> structured output conflicts with tool use in a single run — the router must be tool-less. Remove any tool registrations from the router's AsAIAgent call.
  • Dispatch always falls through to chat even for known capabilities → the RouteDecision.TargetId casing doesn't match the registry key. The MenuRegistry constructor uses StringComparer.OrdinalIgnoreCase — verify that TryGet is called with the raw route.TargetId, not a manually lowercased copy.
  • "What can you do?" is answered by the analyst with fabricated capabilities → the router is not wired. Confirm [FromKeyedServices("router")] is on the /chat handler parameter and the router is registered with the matching key "router".
  • Router prompt catalog and menu list differ → a registry entry was modified directly as a string somewhere outside the registry. Always add capabilities by adding a MenuItem to the registry constructor; never hardcode the same information elsewhere.
  • Follow-up messages route to menu instead of dispatch/chat → RecentUserMessages is not registered or not injected. Without session context, the router sees each message in isolation and misclassifies "run that for last month" as a menu request.
