Lesson 05 · B2 · Module B — The graph

Watching the graph: workflow events

★★ No LLM

What you'll learn

A Claudalytics Copilot investigation runs many steps inside the graph: it plans probes, runs them, validates, and writes a report. Without events you cannot see which probe is running, why one failed, or stream progress to the UI. The run is a black box until it ends.

Every workflow run emits a live stream of typed events. You read it from the same StreamingRun you already hold. In this lesson you wire a driver that reads that stream and builds a typed event timeline next to the final result. You also learn to emit your own events from inside executors. After B2 you have a debugging window that travels with the graph through every later lesson.

📘 Teach

The built-in event stream

When you call InProcessExecution.RunStreamingAsync(…) you get back a StreamingRun. Call run.WatchStreamAsync(ct) on it to get an IAsyncEnumerable<WorkflowEvent>. The framework emits these concrete subtypes automatically:

  • WorkflowStartedEvent — run has begun.
  • SuperStepStartedEvent / SuperStepCompletedEvent — one frontier advance: the concurrent batch of nodes that fired together.
  • ExecutorInvokedEvent — a named executor is about to run; carries ExecutorId.
  • ExecutorCompletedEvent — that executor finished normally.
  • ExecutorFailedEvent — the executor threw; the exception lives in evt.Data. Call .GetBaseException().Message to surface the root cause — the default .ToString() is a stack trace wall.
  • WorkflowOutputEvent — a [YieldsOutput] executor produced the final result; read it from evt.Data.
  • RequestInfoEvent — the run is paused waiting for a human response (covered fully in F2).

Custom events from inside executors

Any executor can call await context.AddEventAsync(new MyEvent(…), ct). The event appears in the stream between the surrounding ExecutorInvokedEvent and ExecutorCompletedEvent. Your custom class must extend WorkflowEvent and pass its payload to the base constructor.

How events map to the graph you built in B1

Recall the B1 pipeline from B1: a planner node fans out three probe jobs, three probe executors run in parallel, a fan-in barrier feeds the collector, then output. The event stream makes that structure visible at runtime:

  • The three ExecutorInvokedEvents for the probe executors share the same SuperStepStartedEvent / SuperStepCompletedEvent bracket — proof that fan-out parallelism is real.
  • The collector's ExecutorInvokedEvent appears only after all three probe ExecutorCompletedEvents — that is the fan-in barrier enforcing its "wait for all" contract.
  • If you break one probe's SQL, an ExecutorFailedEvent names the executor and carries the exception — no guessing which node failed.

Build it

  1. Define the custom progress event

    Extend WorkflowEvent with a string payload. Pass the message to the base constructor (the framework stores it) and also expose it as a typed property so consuming code does not have to cast Data.

    🔧 Placement

    File: Workflows/InvestigationModels.cs — the file already exists from B1 and starts with using Microsoft.Agents.AI.Workflows; at the top and namespace AiAgent.Workflows; below it. Append the class below inside the same namespace AiAgent.Workflows block, after the existing record declarations. No new NuGet needed — Microsoft.Agents.AI.Workflows was added in B1.

    Workflows/InvestigationModels.cs 
    /// <summary>Custom workflow event — executors narrate their progress with these.</summary>
public sealed class InvestigationProgressEvent(string message) : WorkflowEvent(message)
{
    public string Message { get; } = message;
}

    The base constructor call is what routes the event into WatchStreamAsync. Without it the object exists but the stream never sees it.

  2. Emit custom events from executors

    Inside any executor's HandleAsync, call context.AddEventAsync with your event instance. The planner announces how many probes it plans. Each probe announces when it starts running. Both events land in the same stream DriveAsync reads later in this lesson, so the progress lines show up in the timeline next to the framework's own events.

    Add the first line in PlanExecutor.HandleAsync, as the first line after clamping days:

    Workflows/InvestigationExecutors.cs — in PlanExecutor.HandleAsync 
    await context.AddEventAsync(
    new InvestigationProgressEvent($"Planning {days}-day investigation: 3 probes."),
    cancellationToken);

    Add the second line in ProbeExecutor.HandleAsync, before the ClickHouse call:

    Workflows/InvestigationExecutors.cs — in ProbeExecutor.HandleAsync 
    await context.AddEventAsync(
    new InvestigationProgressEvent($"Probe '{job.Name}' running."),
    cancellationToken);

    The validator and synthesis nodes added in B3 emit progress the same way. They pass a new InvestigationProgressEvent to context.AddEventAsync from inside their own HandleAsync.

    The raw WorkflowEvent hierarchy is an internal type. Map it to a simple record before you return it to HTTP callers or buffer it into a timeline. This record lives at namespace scope — outside the class — so it is available to any file in the same namespace.

    No new NuGet needed — Microsoft.Agents.AI.Workflows was added in B1. Checkpoint support is added in B4; do not import Microsoft.Agents.AI.Workflows.Checkpointing yet.

    Workflows/InvestigationService.cs — at namespace scope, before the class 
    /// <summary>One simplified workflow event, as returned to HTTP clients.</summary>
public sealed record WorkflowEventDto(string Type, string? Detail);

  4. Add ToDto — map raw events to DTO

    Add ToDto as a private static method inside InvestigationService. It is read by DriveAsync in the next step: every raw event from the stream is passed through ToDto before it goes into the timeline. Use a switch expression so every event type is handled on purpose. An unhandled type returns null and is skipped.

    Workflows/InvestigationService.cs — inside InvestigationService 
    /// <summary>The raw-event-stream lesson, flattened for JSON/SSE consumers.</summary>
private static WorkflowEventDto? ToDto(WorkflowEvent evt) => evt switch
{
    WorkflowStartedEvent                   => new("workflow_started", null),
    SuperStepStartedEvent                  => null,
    SuperStepCompletedEvent                => new("superstep_completed", null),
    ExecutorInvokedEvent invoked           => new("executor_invoked",   invoked.ExecutorId),
    ExecutorCompletedEvent completed       => new("executor_completed", completed.ExecutorId),
    ExecutorFailedEvent failed             => new("executor_failed",
        $"{failed.ExecutorId}: {(failed.Data as Exception)?.GetBaseException().Message ?? failed.Data?.ToString()}"),
    InvestigationProgressEvent progress    => new("progress",          progress.Message),
    WorkflowOutputEvent                    => new("workflow_output",    "report ready"),
    _                                      => null,
};

    The SuperStepStartedEvent arm returns null, so it is dropped for HTTP clients. It fires too often and only adds noise. It is still visible in OTel traces. You decide the signal-to-noise ratio at this mapping layer. The raw stream is always complete.

    There is no arm for RequestInfoEvent yet. That is the approval-pause event. F2 adds its arm when the approval port is introduced. Until then it falls through to the _ case and is skipped.

  5. Add InvestigationStatus and DriveAsync

    InvestigationStatus is the shape returned to the HTTP caller. It carries the run id, a status string, the report text, and the full event timeline. Add it at namespace scope, outside the class, next to WorkflowEventDto. The Status string holds one of three values: running, completed, or failed.

    Workflows/InvestigationService.cs — namespace scope (outside InvestigationService) 
    /// <summary>HTTP-facing result of driving a run as far as it will go.</summary>
public sealed record InvestigationStatus(
    string RunId,
    string Status,
    string? Report,
    List<WorkflowEventDto> Events);

    Now add DriveAsync as a private method inside InvestigationService. It is the consumer of the event stream. It reads each event with await foreach, passes it through ToDto, and adds the result to the events list. It also watches for WorkflowOutputEvent to capture the final report. The list it fills is what StartAsync returns to the /investigate endpoint. Human-in-the-loop pause handling is added in F2.

    Workflows/InvestigationService.cs — inside InvestigationService 
    /// <summary>
/// Consumes the raw WorkflowEvent stream until the run produces output or ends.
/// Human-in-the-loop pause (RequestInfoEvent) is wired in F2.
/// </summary>
private async Task<InvestigationStatus> DriveAsync(
    string runId, StreamingRun run, List<WorkflowEventDto> events, CancellationToken ct)
{
    string? report = null;
    try
    {
        await foreach (var evt in run.WatchStreamAsync(ct))
        {
            var dto = ToDto(evt);
            if (dto is not null) events.Add(dto);

            if (evt is WorkflowOutputEvent output)
                report = output.Data?.ToString();
        }
    }
    catch (Exception ex)
    {
        _logger.LogError(ex, "Investigation run {RunId} failed.", runId);
        events.Add(new("error", ex.Message));
        return new InvestigationStatus(runId, "failed", null, events);
    }

    return new InvestigationStatus(runId, report is null ? "failed" : "completed", report, events);
}

    The loop awaits the stream. The act of reading the next event is what drives the run forward. Nothing runs ahead of you. The stream completes when the workflow graph has no more nodes to fire. B4 will add checkpoint support. F2 will handle the human-approval pause by storing the live run handle and returning early.

  6. Wire StartAsync to DriveAsync

    StartAsync is the public entry point that the /investigate endpoint calls. Add it inside InvestigationService. It creates a fresh StreamingRun with _workflowFactory, then hands it to DriveAsync with an empty event list. This is the no-checkpoint overload. Checkpoint support is added in B4.

    Workflows/InvestigationService.cs — inside InvestigationService 
    public async Task<InvestigationStatus> StartAsync(int days, CancellationToken ct)
{
    var runId = Guid.NewGuid().ToString("N");
    var run = await InProcessExecution.RunStreamingAsync(
        _workflowFactory(), new InvestigationRequest(days), runId, ct);
    return await DriveAsync(runId, run, [], ct);
}

    Register InvestigationService as a singleton. The factory builds the B1 ProbeWorkflow. B3 will repoint this factory to InvestigationWorkflow once the validator and synthesis nodes are wired. Then expose a /investigate endpoint. This endpoint is the reader at the top of the chain: it calls StartAsync, which returns the InvestigationStatus with the full event timeline as JSON.

    builder.Services.AddSingleton(sp =>

        () => ProbeWorkflow.Build(sp.GetRequiredService<ClickHouseClient>()),
        sp.GetRequiredService<ILogger<InvestigationService>>()));

// ...

app.MapPost("/investigate", async (int days, InvestigationService svc, CancellationToken ct) =>
    Results.Ok(await svc.StartAsync(days, ct)));

Why supersteps reveal parallelism

A superstep is a single frontier advance. All nodes whose input messages are ready fire at the same time within it. In the B1/B2 pipeline, the three probe executors share one superstep. This is because the fan-out edge delivers all three ProbeJob messages at once. The event stream makes this fact observable at runtime. Look for three executor_invoked entries whose executor_completed entries all land inside the same superstep_completed. That is free, verifiable parallelism with zero LLM cost.

Verify

✅ Gate — do not advance until green

Start the agent with the Testing environment and POST to the investigation endpoint: 

dotnet run -- --environment Testing
# In another terminal:
curl -s -X POST "http://localhost:8124/investigate?days=7" | jq '.events[].type'

The output must contain, in order:

  • "workflow_started"
  • "executor_invoked" for plan
  • "progress" — "Planning 7-day investigation: 3 probes."
  • Three "executor_invoked" entries for probe-0, probe-1, probe-2 (order within the superstep is arbitrary)
  • Three "progress" entries, one per probe — "Probe '…' running."
  • "executor_invoked" for collector — appears only after all three probe "executor_completed" entries (fan-in barrier)
  • "workflow_output"

Check that the probe executor invocations share a superstep: compare their indices in the events array; all three should appear between the same pair of superstep_completed boundaries.

Negative test — surface executor-failed:

In ProbeExecutor.HandleAsync, break the SQL on purpose by querying a table that does not exist: 

rows = await clickHouse.QueryAsync("SELECT * FROM nonexistent_table", cancellationToken);

Re-run the investigate endpoint. The events array should now hold an executor_failed entry like this one: 

{ "type": "executor_failed", "detail": "probe-0: Table nonexistent_table doesn't exist." }

The run continues. The other probes still fire. The collector still receives a ProbeResult with hasData = false for the broken probe.

Check that executor_failed carries the base exception message, which is the table name. It must not carry a full stack trace. If you see a multi-line dump, the GetBaseException().Message extraction in ToDto is not reaching the event. Recheck the ExecutorFailedEvent arm of the switch expression.

⚠️ Pitfalls
  • executor_failed shows a stack trace wall, not the root cause → failed.Data is an Exception; call .GetBaseException().Message, not .ToString(). The raw ToString() includes frames that conceal the actual error inside several lines of runtime internals.
  • Custom event never appears in the stream → Your class must call : WorkflowEvent(payload) — the base constructor is what registers the object with the framework's event bus. A class that extends WorkflowEvent but passes nothing to the base constructor is constructed but never emitted.
  • All events arrive at the end, not incrementally → You are iterating with ToListAsync() or .Result instead of await foreach. The stream must be consumed asynchronously; blocking materialisation defeats the live-event contract.
  • Stream appears empty (no events at all) → You are watching the stream on a different StreamingRun instance than the one executing the workflow. One common cause: calling _workflowFactory() a second time and watching the new handle. Remember: a Workflow is owned by exactly one runner — build fresh per logical run (as the factory pattern ensures), but never create two handles for the same run.
  • Probe parallelism not visible (all three probes sequential) → The fan-out edge or partitioner from B1 was not carried forward. Confirm the workflow builder still registers all three probe executors and the fan-out edge; the superstep grouping emerges from the edge wiring, not from the event code.
