Lesson 09 · C2 · Module C — The product

Observability: middleware + OTel

★★ Haiku

What you'll learn

The agent runs on its own. It picks which SQL tools to call and how many model round-trips to make. When a run costs too much or calls a tool you did not expect, you have no record of it. You cannot say which tools ran, how many tokens you paid for, or how long each call took. C2 makes every model round-trip and every tool call visible after the fact. A delegating chat client logs each round-trip in the console, and UseOpenTelemetry writes structured spans into the same ClickHouse the agent already queries.

There are two seams. They sit at different levels and see different things. The first is a delegating chat client. It wraps the model provider and sees every raw round-trip: the messages going in, the tool calls and token counts coming back. The second is UseOpenTelemetry on the agent builder. It emits invoke_agent and execute_tool spans into any OpenTelemetry backend. In Claudalytics both seams export to the same ClickHouse the agent queries. The product monitors itself. You instrument once, then query the data forever.

📘 Teach

Two middleware seams

Seam 1 — DelegatingChatClient. This is the Microsoft.Extensions.AI middleware pattern. You subclass DelegatingChatClient, override GetResponseAsync and GetStreamingResponseAsync, and call base.* to forward to the real provider. After the forward you can do whatever you like with the result. The client is wired into an agent through the clientFactory parameter of client.AsAIAgent(…). The factory receives the raw inner client and returns your wrapper. This runs for every model round-trip. That includes the tool-calling loops inside a single RunAsync call. So it is the right place for per-request logging and cost tracking.

Seam 2 — UseOpenTelemetry(sourceName). Called on the AIAgentBuilder returned by agent.AsBuilder(), this wires an OTel ActivitySource into the agent. It emits two span kinds automatically: invoke_agent (one per RunAsync call) and execute_tool (one per tool invocation). You name the source. That name becomes the AddSource(…) argument in your OTel pipeline configuration.

Named API surfaces

  • DelegatingChatClient — base class, Microsoft.Extensions.AI
  • client.AsAIAgent(options, clientFactory: inner => …) — wires the middleware
  • agent.AsBuilder().UseOpenTelemetry(sourceName).Build() — adds OTel spans
  • builder.Services.AddOpenTelemetry()…AddAspNetCoreInstrumentation()…AddSource(…)…AddOtlpExporter() — the host-side pipeline

How the two seams differ

It helps to be concrete about what each seam sees and when:

Seam Granularity What you get Wired at
DelegatingChatClient Every model HTTP call Raw messages, FunctionCallContent, token counts, streaming chunks clientFactory in AsAIAgent
UseOpenTelemetry Per agent invocation + per tool execution Structured OTel spans: invoke_agent, execute_tool, model-id attributes AsBuilder().UseOpenTelemetry(…).Build()

Use the delegating client for anything you want in logs — it's simple, synchronous, and always available in the process. Use OTel for anything you want to query, aggregate, or alert on — it goes to ClickHouse and lives alongside your Claudalytics session data.

Build it

  1. Step 1 — Write the delegating chat client

    Create Middleware/ToolCallLoggingChatClient.cs. This class is Seam 1. It sits between the agent and the Anthropic provider. The agent factory in Step 2 wires it in, and the console reads its log lines. The class extends DelegatingChatClient and takes the inner client plus an ILogger through its constructor. This is standard .NET DI, with nothing MAF-specific.

    🔧 Setup — packages

    C2 introduces OpenTelemetry. Add three packages before writing any code (versions are pinned in AiAgent.csproj): 

    dotnet add package OpenTelemetry.Extensions.Hosting --version 1.15.3
dotnet add package OpenTelemetry.Exporter.OpenTelemetryProtocol --version 1.15.3
dotnet add package OpenTelemetry.Instrumentation.AspNetCore --version 1.15.2

    The non-streaming override comes first. It calls base.GetResponseAsync to forward the request to the real provider. Then it walks the response messages, finds each FunctionCallContent item, and logs the tool name and arguments. When response.Usage is present, it also logs the input and output token counts. This is where per-request cost tracking lives. The project enables implicit usings, but ILogger does not resolve without the explicit using Microsoft.Extensions.Logging; line.

    Middleware/ToolCallLoggingChatClient.cs — class + non-streaming override 
    using Microsoft.Extensions.AI;
using Microsoft.Extensions.Logging;

namespace AiAgent.Middleware;

public sealed class ToolCallLoggingChatClient(IChatClient innerClient, ILogger logger)
    : DelegatingChatClient(innerClient)
{
    public override async Task<ChatResponse> GetResponseAsync(
        IEnumerable<ChatMessage> messages, ChatOptions? options = null,
        CancellationToken cancellationToken = default)
    {
        var response = await base.GetResponseAsync(messages, options, cancellationToken);

        foreach (var call in response.Messages
            .SelectMany(m => m.Contents)
            .OfType<FunctionCallContent>())
            logger.LogInformation("Tool call requested: {Tool} {Args}",
                call.Name, System.Text.Json.JsonSerializer.Serialize(call.Arguments));

        if (response.Usage is { } usage)
            logger.LogInformation("Model round-trip: in={Input} out={Output} tokens",
                usage.InputTokenCount, usage.OutputTokenCount);

        return response;
    }

    The streaming override comes next, and it closes the class. The streaming path goes through a different method than the non-streaming one, so you must override both. It yields every ChatResponseUpdate unchanged and never buffers. The logging is a side effect that does not change the data flow. This is the contract for any delegating client: stay transparent, add behavior, and do not break the stream.

    ToolCallLoggingChatClient.cs — streaming override (then close the class) 
        public override async IAsyncEnumerable<ChatResponseUpdate> GetStreamingResponseAsync(
        IEnumerable<ChatMessage> messages, ChatOptions? options = null,
        [System.Runtime.CompilerServices.EnumeratorCancellation]
        CancellationToken cancellationToken = default)
    {
        await foreach (var update in base.GetStreamingResponseAsync(
            messages, options, cancellationToken))
        {
            foreach (var call in update.Contents.OfType<FunctionCallContent>())
                logger.LogInformation("Tool call requested (stream): {Tool}", call.Name);
            yield return update;
        }
    }
}

  2. Step 2 — Wire the middleware into the agent factory

    This step turns on both seams. In Agents/AgentFactory.cs, pass a clientFactory lambda to client.AsAIAgent. The lambda receives the raw IChatClient (the Anthropic provider) and returns your ToolCallLoggingChatClient from Step 1 wrapping it. That is Seam 1. After that, chain .AsBuilder().UseOpenTelemetry(OtelSourceName).Build() to add the OTel spans. That is Seam 2. The source name is a public constant. The OTel pipeline in Step 3 reads it back from Program.cs.

    🔧 Note — cumulative file

    Agents/AgentFactory.cs was started in C1. Keep the complete file from C1 — all the options/Tools wiring stays exactly as-is. In C2 you make two additions only:

    1. Add OtelSourceName as a public constant (needed in Program.cs).
    2. Pass clientFactory: to client.AsAIAgent and chain .AsBuilder().UseOpenTelemetry(OtelSourceName).Build() on the result.

    Required usings at the top of AgentFactory.cs (all six should already be present from C1; add any that are missing): 

    using AiAgent.Middleware;
using AiAgent.Tools;
using Anthropic;
using Microsoft.Agents.AI;
using Microsoft.Agents.AI.Compaction;
using Microsoft.Extensions.AI;

    The code below shows only the two C2 additions. The OtelSourceName constant is new. Step 3 reads it from Program.cs. The ChatClientAgentOptions and Tools wiring from C1 stays exactly as it was. The clientFactory: argument is the only change to the AsAIAgent call. The .AsBuilder().UseOpenTelemetry(...).Build() chain on the result is new.

    Agents/AgentFactory.cs excerpt — two C2 additions shown; keep all C1 content 
    public static class AgentFactory
{
    public const string OtelSourceName = "Claudalytics.Agent";

    public static AIAgent Create(
        IConfiguration config,
        SchemaTools tools,
        AnalysisTools analysis,
        ILoggerFactory loggerFactory)
    {
        var apiKey = config["ANTHROPIC_API_KEY"]
            ?? throw new InvalidOperationException("ANTHROPIC_API_KEY is not set.");

        IAnthropicClient client = new AnthropicClient { ApiKey = apiKey };

        // ... ChatClientAgentOptions / Tools wiring unchanged from C1 ...

        var agent = client.AsAIAgent(
            options,
            clientFactory: inner => new ToolCallLoggingChatClient(
                inner, loggerFactory.CreateLogger<ToolCallLoggingChatClient>()),
            loggerFactory: loggerFactory);

        return agent.AsBuilder()
            .UseOpenTelemetry(OtelSourceName)
            .Build();
    }
}

  3. Step 3 — Register the OTel pipeline in Program.cs

    Seam 2 from Step 2 only emits spans if something listens for them. This step adds that listener. In Program.cs, call builder.Services.AddOpenTelemetry() and add four things. The collector at the end of this pipeline writes the spans to ClickHouse, which is the table the Verify gate queries.

    • A service name — this becomes the service.name resource attribute on every span.
    • AddAspNetCoreInstrumentation() — this is the critical line described in the pitfalls section below.
    • AddSource(…) for your named source and the two MAF default sources.
    • AddOtlpExporter() — points to the stack's OTel collector via OTEL_EXPORTER_OTLP_ENDPOINT.
    🔧 Note — placement + usings

    File: Program.cs.
    Placement: add this block after all builder.Services.* registrations and before var app = builder.Build();.
    Usings: add these two at the top of Program.cs alongside the existing using statements: 

    using OpenTelemetry.Resources;
using OpenTelemetry.Trace;

    The order of the three AddSource lines does not matter. The first is your named source from Step 2, which carries the UseOpenTelemetry spans. The second is the MAF default agent source. The third is the Microsoft.Extensions.AI chat-client source. AddAspNetCoreInstrumentation() is not optional. The pitfalls section explains why a missing line here empties the whole trace table.

    Program.cs add after all builder.Services.* — before var app = builder.Build(); 
    builder.Services.AddOpenTelemetry()
    .ConfigureResource(resource => resource.AddService("claudalytics-agent"))
    .WithTracing(tracing => tracing
        .AddAspNetCoreInstrumentation()
        .AddSource(AgentFactory.OtelSourceName)
        .AddSource("Experimental.Microsoft.Agents.AI")
        .AddSource("Experimental.Microsoft.Extensions.AI")
        .AddOtlpExporter());

    The OTEL_EXPORTER_OTLP_ENDPOINT env var is set in docker-compose to point at the OpenTelemetry Collector service in the stack. That collector fans out to ClickHouse — the same table the agent queries with its SQL tools. You do not need to configure the endpoint manually in development if you run via docker-compose up.

Why dogfooding matters here

The agent's job is to answer questions about Claudalytics telemetry. By exporting its own spans to the same otel_traces table, every agent run adds a row you can query: which tools were called, how long each took, which model handled which turn. You can literally ask the agent "how many tool calls did you make in the last hour?" and it will query its own trace data to answer. That feedback loop is worth building early — it makes the C3 (tool approval) lesson's safety story much more concrete because you can see the dangerous calls in the trace table before you gate them.

Verify

✅ Gate — do not advance until green

Start the stack in Testing mode:

dotnet run -- --environment Testing

Send one chat turn:

curl -s -X POST http://localhost:8124/chat \
  -H "Content-Type: application/json" \
  -d '{"message":"list my projects"}' | jq .

Check 1 — middleware log lines. In the console you should see at least one line like: 

info: AiAgent.Middleware.ToolCallLoggingChatClient[0]
      Tool call requested: list_projects {"":""}
info: AiAgent.Middleware.ToolCallLoggingChatClient[0]
      Model round-trip: in=842 out=45 tokens

Check 2 — OTel spans in ClickHouse. After a few seconds for the collector to flush, query otel_traces: 

SELECT ServiceName, SpanName, StatusCode
FROM otel_traces
WHERE ServiceName = 'claudalytics-agent'
  AND Timestamp > now() - INTERVAL 1 MINUTE
ORDER BY Timestamp DESC
LIMIT 20;

You should see rows with SpanName values including invoke_agent and execute_tool.

Negative test — the silent sampler drop. Comment out .AddAspNetCoreInstrumentation(), restart, send the same chat turn, wait 10 seconds, re-run the ClickHouse query. The otel_traces table returns zero rows for this service — even though the agent ran, the console logs appeared, and the HTTP response was correct. An empty trace table while the agent is working is the exact symptom of the missing ASP.NET instrumentation. Restore the line before advancing.

⚠️ Pitfalls
  • Empty otel_traces even though the agent ran → AddAspNetCoreInstrumentation() is missing. Without it, ASP.NET's own incoming-request activity is the root span and the ParentBased sampler (the OTel default) samples it at the same rate as the parent — which for an unregistered source is 0 %. Every agent child span is silently dropped. There is no warning; the agent works fine; the table is empty. Add the line, restart.
  • Log lines appear but ClickHouse rows do not → Wrong or unreachable OTEL_EXPORTER_OTLP_ENDPOINT. The OTLP exporter silently swallows export errors by default. Check OTEL_EXPORTER_OTLP_ENDPOINT in your environment (should be http://otel-collector:4317 inside Docker, or http://localhost:4317 if running the agent outside the stack). You can enable exporter diagnostics with OTEL_EXPORTER_OTLP_TRACES_ENDPOINT and OTEL_DIAGNOSTICS_FILE_DIRECTORY.
  • Spans present but attributed to the wrong service name → resource.AddService(…) not called or called with the wrong string. Check ServiceName in ClickHouse; it should be claudalytics-agent.
  • Streaming chat produces no tool-call log lines → The GetStreamingResponseAsync override is missing or not calling yield return update. The streaming path goes through a different method than the non-streaming one — both must be overridden.
  • UseOpenTelemetry not found at compile time → You called it on the AIAgent directly instead of on the builder. The call chain must be agent.AsBuilder().UseOpenTelemetry(sourceName).Build().

What comes next

With every agent span in ClickHouse you now have the data you need to make the human approval gate in C3 evidence-based: you can query which SQL tool calls were most frequent, identify the ones that hit large scans, and use that evidence to decide which tools need a human gate. The middleware you built here feeds directly into that decision.
